### 5. 你觉得问题出在哪、和 Linux 比有什么不同、有没有解决思路
**面试官问题**
- 你觉得现在的问题是什么？
- Linux 本身的机制已经足够完美了吗？
- 如果要解决你说的这块问题，你有思路吗？

**我的回答**
- 我先讲了自己对 Linux 的理解：Linux 面向服务器，需要向前兼容，因此积累了很多历史设计和冗余接口，例如 clone 系列调用。
- 而我们这个新系统用 Rust 重写、又还没有背负历史兼容包袱，可以不用兼顾很多旧代码，也有机会针对一些地方做优化。
- 之后我补充了一类具体问题：早期为了让系统先跑起来，在 Jovi OS 里用了大量自旋锁，导致在 tty 等场景里，多个进程同时跑时很容易死锁。
- 现在在逐步把很多自旋锁改成读写锁和原子操作。
- 之前主要是为了先让系统可用、先能跑出 hello world，现在开始逐步做优化。

**追问 / 澄清**
- 面试官将我的表达总结为：你认为 Linux 因为历史兼容导致结构重，而你们的新系统有机会从零做得更轻、更好。

### 6. Linux 在这类并发 / 锁问题上是怎么做的
**面试官问题**
- Linux 在系统级也会面对同样的问题，它是怎么做的？

**我的回答**
- 我认为 Linux 做得比较好的地方在于锁的颗粒度会尽量细，不会随便上一把很大的锁。
- 它会尽量只锁 inode 里的某几个字段，保证串行化但又尽量颗粒化。

- 也会通过更完善的异步函数、软中断和硬中断机制，尽量减少锁的使用。
- 调度上，主流做法还是围绕时间片和优先级，同时通过多级缓存让 CPU 尽量保持工作状态。

**追问 / 澄清**

### 9. cgroup 在 Linux / 操作系统层面是怎么生效的
**面试官问题**
- 你写 cgroup 这块时，了解它在操作系统层面、或者在 Linux 上是怎么生效的吗？它怎么做到这件事？

**我的回答**
- cgroup 在内核里本质上是一个伪文件系统，挂在内核里。
- 我目前实现的一个 controller，是通过 cgroup namespace 去管理 pid，对 pid 进行限额。
- 我的做法是：在进程管理器对应的数据结构里，给每个进程挂一个 task cgroup 结构体，让每个进程都能指向一个 cgroup node。
- 同时给 namespace 注册节点，表示当前 namespace 属于哪个 cgroup。
- 当 fork 一个新进程时，就会检查这个 task cgroup 对应的 cgroup node 当前计数是否超过 max 值。
- 如果超过，就拒绝创建进程并回收资源；如果没有超过，就允许创建并把它加入到对应 cgroup。

**追问 / 澄清**
- 面试官继续追问：这只是启动时的控制，那进程运行过程中的 limit 又怎么控制。

### 10. 运行过程中的 limit 怎么控制
**面试官问题**
- 在运行过程中，你怎么控制 limit？因为 cgroup 的语义里不只是启动，还有 request / limit 这类管理。

**我的回答**
- 我回答说，进程运行中的变化大概有几类：
  1. fork 新进程，默认属于同一个 cgroup；
  2. 进程迁移，把一个进程从 A cgroup 搬到 B cgroup；
  3. 进程结束。
- 对于迁移，我会检查被迁移对象是不是单线程、是不是整个进程组，以及相关权限是否通过。
- 检查通过后，才会把它从一个 cgroup 搬到另一个 cgroup，并更新 pcb 上对应的结构体引用。
- 对于进程结束，我的设计是：在 cgroup 相关的遍历 / 观察路径上，会对整条 cgroup tree 做一次更新，清理已经消失的任务，把最新状态同步到缓存里。
- 因此每次通过伪文件系统去查看 cgroup 目录时，看到的都是最新状态。

**追问 / 澄清**
- 面试官总结：从进程出生、fork、迁移到消失，这些过程你都能看见，也能做到限额控制。

### 11. cgroup 这块为性能和并发正确性做了什么
**面试官问题**
- 这和进程调度相关，对性能要求应该也很高，不然系统调用开销大了会影响整个系统。你用了什么高性能机制？

**我的回答**
- 我提到用了读写锁，也在某些地方用了自旋锁。
- 在迁移场景里，实际修改动作很短，比如改 inode 里对应的 cgroup、改 pcb 里的弱引用。
- 我举了一个并发例子：假设某个 cgroup 当前有 9 个进程，限额是 10，同时线程 A 和线程 B 都想 fork 一个新进程；如果它们检查时都看到是 9，就可能都通过，最终变成 11。
- 为了避免这种问题，我给“检查 + 搬迁”这段逻辑套了一把较大的 spin lock，把检查和修改放在一个原子临界区里。
- 对于像 cgroup.procs 这种只读展示文件，我会套读锁，让多个读取并发进行；真正要修改时再等待读者退出，用写锁保证安全。

**追问 / 澄清**
- 面试官随后继续追问 cgroup 版本演进和边界问题。

### 12. cgroup v1 / v2 的差异，以及现在还限制不了什么
**面试官问题**
- Linux 的 cgroup 发展到现在有几个版本？
- 每个版本有什么差异？
- 现在的 cgroup 还有什么限制不了的？

**我的回答**
- 我先讲标准实现：最开始是 v1，现在主流是 v2，我写的也是 v2 风格。
- v1 的特点是每个 controller 都有自己的一棵树，例如 CPU、memory、pid 各有各的树。
- 这样同一个线程可能同时存在于多棵树里，迁移、权限检查、节点维护都比较复杂，而且空间开销也更大。
- v2 的思路是把这些东西统一到一棵树上，以 cgroup node 为层级，在每个节点里管理一组任务，并在这个层级上配置 CPU、memory、pid 等限制。
- 我还提到 v2 支持更自然的层级化分配，例如在一个大的 cgroup 里再划一个更小的工作区，把部分 CPU / 内存限额继续分给它。
- 之后我尝试说明一个边界：对于 CPU / memory 这种 domain controller，如果一个节点已经把资源继续往下分配了，那么这个节点本身就不再适合直接承载任务，否则会破坏层级语义。
- 后来面试官打断，希望我用“实际场景”而不是“数据结构 / 规则定义”来回答“它解决不了什么”。
- 我想了一会，给了一个极端例子：如果想让一个容器和容器外面的某个进程共同享受同一份 CPU 调度预算，这在当前 cgroup 体系里就不太好表达。
- 之后也承认，这种需求在真实的 Kubernetes / 容器编排体系里并不常见，因为 pod / 容器本身就是最小管理单元。

**追问 / 澄清**
- 面试官强调：缺陷一定要落到“满足不了什么具体需求 / 场景”上，而不是只停留在实现机制层面。

**追问 / 澄清**
