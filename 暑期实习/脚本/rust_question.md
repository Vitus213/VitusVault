## 所有权系统

### 所有权系统是干什么用的？
- 解决双重删除（Double Free）问题
- 每个变量都归属唯一的所有人，在脱离作用域自动释放（如果是 move 机制）
- 避免旧的指针可以继续访问同一段内存（悬垂指针）

### 为什么 String 会 Move，而 i32 却不会？
核心：**Copy trait vs Drop trait**。

- `i32` 实现了 `Copy` trait。它的大小固定且存在栈上，复制成本极低。
- `String` 拥有堆内存的所有权。如果允许简单的位拷贝（Shallow Copy），会导致两个变量指向同一块堆内存。当它们离开作用域时，会触发两次释放（Double Free），这是严重的内存安全隐患。因此，String 默认执行 Move（所有权转移）。

### 为什么有了可变借用就不能有不可变借用？（读写锁）
防范：**数据竞争（Data Race）和迭代器失效**。

如果允许同时存在，当你通过 `&mut T` 修改数据时，持有 `&T` 的人看到的数据会瞬间改变（甚至内存地址失效）。

**读写互斥规则**：要么多个读者（共享），要么一个作者（独占）。这保证了指针的稳定性。

## Trait 与多态

### 什么是孤儿规则 (Orphan Rules)？
**规则**：实现 Trait 时，Trait 本身或类型本身至少有一个必须是在当前 crate 内定义的。

**目的**：防止生态系统的混乱。如果全世界的人都能给 `Vec<T>` 实现 `Display`，编译器在遇到 `println!("{}", my_vec)` 时就不知道该听谁的了。（防止跨过当前的 crate 直接给别的类型定义 trait）

### 静态分派与动态分派在汇编层面的区别？

**静态分派**：
- 编译器进行单态化（每一份特征实现一份代码），直接调用函数地址
- 汇编指令通常是 `call <具体函数地址>`
- 因为地址确定，CPU 的分支预测器表现极佳，且支持内联（直接把代码插进去）

**动态分派**：
- 汇编指令通常是 `call *RAX`（间接跳转）
- 程序需要先从胖指针里取出 vtable 地址，再从 vtable 偏移量中找到函数指针
- 这会造成缓存污染和流水线停顿

**C++ vs Rust 虚表实现对比**：

| 特性 | C++ | Rust |
|------|-----|------|
| vptr 位置 | 直接插入对象头部 | 使用胖指针，对象保持纯粹 |
| 修改源码 | 需要修改类定义 | 不需要修改类型定义 |
| 胖指针大小 | 无 | `&dyn Trait` 占用 16 字节（数据指针 + 虚表指针） |

## 指针和引用的区别

指针和引用内部存的都是一个内存地址，但有以下区别：

| 特性 | 指针 | 引用 |
|------|------|------|
| 初始化 | 可以不初始化 | 必须初始化 |
| 重新赋值 | 可以 | 不能 |
| 安全性 | 极低，容易产生野指针 | 高，受编译器严格监控 |

## 生命周期 (Lifetimes)

### 生命周期的目的是什么？
在静态编译期就让编译器知道变量能否在作用域内被资源回收。

### 生命周期标注 `<'a>` 是给谁看的？
它是给**编译器**看的"契约"。
- 它**不改变**变量的实际存活时间（那是 Scope 决定的）
- 它的作用是告诉编译器：引用 A 的寿命至少要和引用 B 一样长，从而确保不会出现"人死了，魂还在"（悬垂指针）

### 为什么包含引用的结构体必须标生命周期？
结构体可能被传来传去。编译器必须知道：这个结构体实例的寿命，绝对不能超过它内部那个引用的寿命。如果不标，编译器无法追踪这个约束，安全性就会失控。

## 智能指针与内存布局

### Box vs Rc vs Arc

| 类型 | 用途 | 线程安全 |
|------|------|----------|
| `Box<T>` | 独占所有权，把数据存在堆上 | 是（可移动到其他线程） |
| `Rc<T>` | 引用计数，允许多个所有者 | 否，仅单线程 |
| `Arc<T>` | 原子引用计数，多线程共享 | 是，但原子操作有轻微性能开销 |

### Rust 与 C++ 智能指针对比

| 特性 | Rust | C++ |
|------|------|-----|
| 独占指针 | `Box<T>` | `std::unique_ptr<T>` |
| 共享指针 | `Rc<T>` / `Arc<T>` | `std::shared_ptr<T>` |
| 弱引用 | `Weak<T>` | `std::weak_ptr<T>` |
| 借用检查 | **编译期**强制 | 运行期检查/无检查 |
| 循环引用 | 编译器不阻止，需手动用 `Weak` | 同左 |
| 空指针 | 需要 `Option<Box<T>>` | `unique_ptr` 可为 nullptr |

**关键区别**：
- Rust 的借用规则在**编译期**强制执行，C++ 依赖程序员自律
- C++ `shared_ptr` 控制块包含 deleter 和 allocator，Rust 更轻量
- C++ 允许从裸指针创建 `shared_ptr`（危险），Rust 不允许从裸指针直接创建 `Rc`

### 什么是内部可变性？RefCell 是零成本吗？

**内部可变性**：在持有不可变引用 `&T` 时修改内部数据。

**原理**：`RefCell` 将借用检查从编译期推迟到了**运行期**。

**它不是零成本**：
- 内部维护了借用计数器 `borrow: Cell<isize>`，每次访问都有额外的性能开销
- 运行期借用冲突会导致 **panic**（崩溃）

### RefCell 在多线程中是安全的还是不安全的？

**RefCell 本身不是线程安全的**，它**不实现 `Send` 和 `Sync`**。

- 在多线程中应该使用 `Mutex<T>` 或 `RwLock<T>` 配合 `Arc`
- 如果需要在多线程中使用内部可变性，用 `std::sync::RwLock` 或 `std::sync::Mutex`

```rust
// 单线程内部可变性
let data = RefCell::new(5);

// 多线程内部可变性
let data = Arc::new(Mutex::new(5));
```

### RwLock 适用于读多写少的场景

RwLock 需要追踪：
- 当前是"多个读者"还是"一个写者"？
- 当前有多少个读者（需要一个计数器）？
- 是否有写者正在排队（为了防止"读者饥饿"，通常需要记录等待队列）？

## 并发与 Unsafe

### 指针和引用有什么区别？

| 特性 | 引用 `&T` | 裸指针 `*const T` / `*mut T` |
|------|-----------|------------------------------|
| 借用检查 | 编译期强制 | 无 |
| 空值 | 不允许（Option 可选） | 允许为 null |
| 生命周期 | 必须标注 | 无保证 |
| 解引用 | 安全，随处可解 | 只能在 unsafe 块中解引用 |
| 别名规则 | 编译期保证 | 无保证（需手动遵守） |
| 内存布局 | 与指针相同 | 原始内存地址 |

**总结**：引用是带有编译期安全保证的指针，裸指针是没有任何保证的原始地址。

### Send 与 Sync 的区别？

| Trait | 含义 | 自动实现条件 |
|-------|------|--------------|
| `Send` | 该类型的**所有权**可以跨线程转移（Move） | 所有字段都是 Send |
| `Sync` | 该类型的**引用**可以在多线程间共享（即 `&T` 是 Send 的） | 所有字段都是 Sync |

**例子**：
- `Rc<T>`：既不是 Send 也不是 Sync（引用计数非原子）
- `Arc<T>`：通常两者都是
- `Mutex<T>`：是 Send + Sync（只要 T 是 Send）
- `RefCell<T>`：不是 Sync（运行期借用检查非线程安全）

### unsafe 块关闭了借用检查吗？

**错！** `unsafe` 只是赋予了你 **5 种超能力**。

原有的借用检查器（Borrow Checker）在 `unsafe` 块里**依然有效**。你依然不能随意违反 Rust 的安全规则，除非你通过原始指针手动绕过。

### unsafe 能干什么？（5 种超能力）

1. **解引用裸指针** `*const T` / `*mut T`
2. **调用 unsafe 函数**（包括 FFI 调用 C 函数）
3. **访问或修改可变静态变量** `static mut`
4. **实现 unsafe trait**
5. **访问 union 的字段**

```rust
unsafe {
    // 1. 解引用裸指针
    let ptr: *const i32 = &x;
    let val = *ptr;

    // 2. 调用 unsafe 函数
    unsafe_fn();

    // 3. 访问可变静态变量
    STATIC_MUT = 10;

    // 4. 实现 unsafe trait（在 impl 块外）
    // unsafe impl Send for MyType {}

    // 5. 访问 union 字段
    let u = MyUnion { f1: 1 };
    let val = u.f1;
}
```

**记住**：`unsafe` 的责任是程序员手动保证内存安全，编译器不再为你背书。
