# Claude Code 最佳实践指南统一整合设计

- 日期：2026-03-26
- 目标文件：`Claude Code 最佳实践指南（BeatAI·整理版）.md`
- 整合来源：
  - `AI Coding 工程实践经验.md`
  - `AI Coding 方法论对比：BeatAI vs 工程实践经验.md`
  - `Claude Code 最佳实践指南（BeatAI·整理版）.md`

## 1. 目标

将现有的 `Claude Code 最佳实践指南（BeatAI·整理版）.md` 从“围绕 Claude Code 的工具实践整理稿”重构为一篇统一的 AI Coding 方法论主文档，使其同时覆盖：

1. 个人开发者如何高质量使用 Claude Code
2. 团队如何把 AI Coding 做成可治理、可验证、可持续的工程流程

最终产物应是一篇单文档、单主线的完整指南，而不是三篇材料的拼接或对照汇编。

## 2. 读者与定位

### 目标读者

- 想把 Claude Code 用顺的个人开发者
- 想为团队建立 AI Coding 规范的技术负责人
- 需要兼顾工具落地与工程治理的人

### 文档定位

这篇文档将被定位为：

> 一份围绕 Claude Code 的 AI Coding 最佳实践与工程治理指南。

它不再强调“BeatAI 整理版”与“工程实践经验”的来源差异，而是将这些内容融合为一套统一的方法论。

## 3. 整合原则

### 3.1 统一主线

整篇文档围绕以下主线展开：

- Claude Code 是执行平台
- 文件是长期状态与约束的载体
- 验证体系负责建立质量闭环
- session 是临时执行流，不是长期记忆
- 人负责决策、边界与验收

### 3.2 术语统一规则

最终文档采用以下规范术语，避免不同来源文档命名不一致：

- `AGENTS.md`：工具中立的项目合约，承载项目概览、关键约束、分层规则、构建测试命令、反模式清单等高优先级规则
- `CLAUDE.md`：Claude Code 专用运行说明，承载 Claude Code 使用时的项目特有操作约束、命令、工作流提醒和工具边界
- `spec.md`：需求与验收标准
- `plan.md`：技术方案
- `tasks.md`：执行拆解
- `verify.json`：机器可执行的结构化验收定义
- `verify-report.md`：验证结果沉淀

对于来源文档中出现的 `agents.md`、`task.md` 等写法，最终正文只在首次说明时作为来源别名提及一次，后续统一采用 `AGENTS.md` 与 `tasks.md`。

如果项目同时存在 `AGENTS.md` 与 `CLAUDE.md`，应明确边界：

- `AGENTS.md` 负责工具中立、跨生态可复用的项目合约
- `CLAUDE.md` 负责 Claude Code 专用的运行指导
- 两者不要重复堆叠同一条规则

### 3.3 不做简单拼接

不会保留“BeatAI 观点”和“工程实践观点”的并列写法，而是：

- 对重合内容合并为一个版本
- 对差异内容按“工具实践层”与“治理层”自然融入主线
- 将“方法论对比”中的结论转化为文中的解释性内容

### 3.4 保留价值，删除对照痕迹

保留三份材料中的高价值结论，但删除会破坏成文性的内容，例如：

- “哪篇更强”
- “哪篇更适合谁”
- 明显面向比较文章的对照结构

## 5. 新的文档结构

整篇文档将重构为如下章节：

1. 这篇指南解决什么问题
2. AI Coding 的四个底层约束
3. 人、AI、文件分别负责什么
4. 文件体系：把状态、约束、验收写进文件
5. 运行流程：从需求到验收的标准闭环
6. 渐进式规范：按任务规模选择流程强度
7. 上下文管理：避免会话失控
8. 验证体系：把主观判断变成机器判断
9. Claude Code 落地：把方法论接到具体工具上
10. 常见失败模式与规避策略
11. 推荐工作流模板
12. 总结：把 Claude Code 用成执行引擎，而不是聊天工具

## 6. 关键新增章节设计

### 6.1 人、AI、文件分别负责什么

新增这一章，明确角色边界：

- 人负责做什么/不做什么、方案拍板、定义验收标准、查看验收证据
- AI 负责探索、执行、生成、回报
- 文件负责承载长期状态、约束、计划和可审计结果

目的：将“人的职责”与“session 不是长期记忆”连接起来，避免文档只谈工具，不谈责任边界。

### 6.2 文件体系：中立协议与 Claude Code 生态的映射

新增明确映射关系，例如：

- `AGENTS.md`：工具中立的项目合约，承载高优先级规则与跨生态可复用约束
- `CLAUDE.md`：Claude Code 专用运行说明，承载项目特有操作约束、命令与工作流提醒
- `spec.md`：需求与验收标准
- `plan.md`：技术实现方案
- `tasks.md`：执行拆解
- `verify.json`：机器可执行的结构化验收定义
- `verify-report.md`：验证结果沉淀
- hooks / skills / subagents：执行这些流程的自动化与隔离手段

目的：让“Claude Code 怎么用”和“工程文件怎么设计”成为一套体系，而不是两种语言。

### 6.4 同时服务个人与团队

为确保文档同时适用于个人开发者与团队方法论落地，最终成稿需要在关键章节中显式体现双重视角：

- 在“运行流程”“验证体系”“推荐工作流模板”中分别给出个人使用与团队协作的落地方式
- 个人视角强调：如何把 Claude Code 用顺、如何降低上下文污染、如何自我验证
- 团队视角强调：如何沉淀规范、如何分离职责、如何通过文件与验证机制实现协作与审计

最终文档不要求把个人版与团队版完全拆成两篇，但必须让读者清楚看到同一套方法如何从单人工作流平滑扩展到团队工作流

## 7. 核心改写方向

### 7.1 上下文章节

从“上下文是最贵的资源”扩展为：

- 上下文由哪些层组成
- 哪些内容是固定层、半固定层、动态层
- 为什么 `AGENTS.md` / `CLAUDE.md` 必须短而硬
- 为什么 Prompt Caching 要求稳定前缀
- 为什么应通过 subagents、/clear、新 session 控制污染

### 7.2 验证章节

从“让 Claude 验证自己”扩展为：

- 轻量验证：test / lint / typecheck / UI / hook
- 重量验证：`verify.json` + `verify-report.md`
- 核心原则：把主观判断变成机器判断，尽量消灭 AI 的自由裁量空间
- 结构化验证结果如何支持团队协作与审计

### 7.3 Spec-Driven Development 章节

从原来的 `spec.md / plan.md / tasks.md` 三层模型扩展为更完整的工程协议，并补充：

- `AGENTS.md` / `CLAUDE.md` 的定位区别
- review 与 verify 最好与 implement 保持一定隔离
- 通过文件而不是会话沉淀状态

### 7.4 工具配置章节

保留 Claude Code 的具体工具介绍，但重写成“在整套方法论中的作用”：

- 权限：降低执行阻力但不放弃安全边界
- CLI：轻量、低上下文负担的外部交互方式
- MCP：按需启用，审计成本
- Hooks：确定性执行轻量检查
- Skills：按需加载工作流与知识
- Subagents：上下文防火墙与并行执行单元
- Worktree：隔离任务线与并行开发环境
