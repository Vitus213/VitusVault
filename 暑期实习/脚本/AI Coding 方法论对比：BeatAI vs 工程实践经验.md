# AI Coding 方法论对比：BeatAI vs《AI Coding 工程实践经验》

> 对比对象：
>
> 1. `Claude Code 最佳实践指南（BeatAI·整理版）`
> 2. `AI Coding 工程实践经验`
>
> 目的：提炼两篇文档的共同主线、差异化视角，以及可直接落地到工作流中的规则与文件结构。

---

## 1. 总体结论

这两篇文档**不是互相冲突**，而是站在不同抽象层次讨论同一件事：

- **BeatAI 文档** 更像一份围绕 Claude Code 的“官方实践解读 + 工作流手册”，强调：
  - 如何正确使用 Claude Code
  - 如何控制上下文
  - 如何做探索、计划、编码、验证
  - 如何配置 CLAUDE.md / Hooks / Skills / 子代理 / worktree / headless automation

- **《AI Coding 工程实践经验》** 更像一份“工程治理方法论”，强调：
  - AI Coding 中哪些文件应该承担状态与约束
  - 为什么验证必须结构化、可执行、可审计
  - 为什么 session 不应该承担长期记忆
  - 为什么流程需要按需求复杂度分级
  - 人在 AI Coding 中应该承担什么角色

一句话总结：

> **BeatAI 更偏“怎么用 Claude Code 这个工具”，**
> **《AI Coding 工程实践经验》更偏“怎么设计一套长期可持续的 AI 工程流程”。**

两者合起来，才更像一套完整方法论。

---

## 2. 共同核心观点

两篇文档在最重要的原则上高度一致。

### 2.1 上下文是稀缺资源

两篇都认为：
- 模型能力不是无限的
- 上下文窗口是固定且昂贵的
- 一旦上下文被历史错误、噪声信息、无关探索污染，输出质量会明显下降

共同落点：
- 需要精细管理上下文
- 需要把真正重要的信息留在上下文中
- 需要让无关噪声尽可能少进入主会话

### 2.2 验证比“感觉做对了”更重要

两篇都强烈反对“AI 说做完了就算完成”。

共同观点：
- AI 的自我汇报不可靠
- 必须引入测试、命令、截图、检查结果等机器可观测证据
- 没有验证就不能宣称完成

### 2.3 先研究/规划，再执行

两篇都认为：
- 直接让 AI 开写，很容易做错题
- 需求不清时，应该先问清楚、先做计划、先理解代码库
- 计划和执行最好拆开

### 2.4 长会话不是优势，而是风险

两篇都在强调：
- session 不是“越长越聪明”
- 长会话会积累噪声
- 历史失败方案会污染后续决策
- 应该把会话当临时执行流，而不是长期记忆载体

## 3. 视角上的主要差异

## 3.1 BeatAI：工具实践视角

BeatAI 文档最大的特点是：

> 它围绕 **Claude Code 这个具体产品** 来组织知识。

它重点讨论的是：
- Plan Mode
- AskUserQuestion
- CLAUDE.md
- MCP
- Hooks
- Skills
- 子代理
- Worktree
- Headless 模式
- `/clear`、`/compact`、`/rewind`

也就是说，它回答的是：

> **“如果你已经在用 Claude Code，应该怎么用得更稳、更强？”**

## 3.2 《AI Coding 工程实践经验》：工程治理视角

这篇文档的特点是：

> 它不是从某个产品功能出发，而是从“AI 工程流程的可治理性”出发。

它关注的是：
- `agents.md`
- `spec.md`
- `plan.md`
- `task.md`
- `verify.json`
- `verify-report.md`
- Prompt Caching
- 文件与 session 的边界
- 流程强度分级
- 人在协作中的职责

它回答的是：

> **“如果你要长期做 AI Coding，什么样的流程设计才稳定？”**

## 4. 在文件体系设计上的差异

## 4.1 BeatAI 的文件体系

BeatAI 更强调：
- `CLAUDE.md`
- `.claude/settings.json`
- `.claude/rules/`
- `.claude/skills/`
- `.claude/agents/`
- `.mcp.json`

也就是一种围绕 Claude Code 原生生态构建的项目配置结构。

### 优点
- 与工具强集成
- 可直接落地在 Claude Code 中
- 功能边界清楚

### 局限
- 偏工具绑定
- 对“跨产品通用状态文件”的抽象相对较弱

## 4.2 《AI Coding 工程实践经验》的文件体系

这篇更强调：
- `agents.md`
- `spec.md`
- `plan.md`
- `task.md`
- `verify.json`
- `verify-report.md`

这是一种更“中立”的文件协议视角。

### 优点
- 不强绑定单一 AI 厂商或单一工具
- 适合做跨生态的工程规范
- 更强调状态外置与验收外置

### 局限
- 工具接入细节需要自己再补
- 如果没有和具体执行环境结合，容易停留在概念层

---

## 5. 在验证体系上的差异

这部分是两篇文档最值得互补的地方。

## 5.1 BeatAI 的验证体系

BeatAI 强调：
- 测试
- typecheck
- lint
- UI 验证
- Hook 自动化验证
- Stop Hook 拦截未完成状态

它更偏：
> **把验证嵌入工作流和环境配置中。**

## 5.2 《AI Coding 工程实践经验》的验证体系

这篇提出了更强的文件化、结构化思路：
- `verify.json`
- `verify-report.md`

而且点出了一个特别重要的工程原则：

> **把主观判断变成机器判断，消灭 AI 的自由裁量空间。**

它更偏：
> **把验证变成可执行、可审计、可追踪的结构化资产。**

## 5.3 哪个更强？

如果只看“在 Claude Code 里好不好用”，BeatAI 的环境集成更强。

但如果看“长期工程化治理”，《AI Coding 工程实践经验》的这套：
- `verify.json`
- `verify-report`

实际上更值得进一步制度化。

### 最佳组合方式

最好的做法不是二选一，而是：

- 用 BeatAI 的 Hooks / CLI / Skills 把验证动作自动化
- 用《AI Coding 工程实践经验》的 `verify.json / verify-report` 把验证结果结构化沉淀

也就是：

> **BeatAI 负责“怎么执行验证”，**
> **工程实践文负责“怎么定义和记录验证”。**

## 6. 在 session / 记忆观上的差异

## 共识
两篇都明确认为：
- session 不是长期记忆
- 文件才是稳定状态
- 会话应该可销毁、可重开、可隔离

## BeatAI 的表达方式

BeatAI 倾向于用这些手段控制 session：
- `/clear`
- `/compact`
- `/rewind`
- 子代理
- worktree
- session resume/continue

它更像在讲：
> **怎么操作会话生命周期。**

## 工程实践文的表达方式

它强调：
- session 不该承担项目状态
- 真正的状态要写进文件
- review 和编码要拆 session
- 不同阶段要有不同 session

它更像在讲：
> **为什么状态必须文件化，而不是会话化。**

---

## 7. 在流程分级上的差异

## BeatAI

BeatAI 当然也区分任务规模，比如：
- 小修小补可以直接做
- 大需求建议 Explore → Plan → Implement → Commit
- 更大的需求用 SDD

但它更多是经验层面的建议。

## 工程实践文

它更进一步提出了：

> **流程强度应该按需求复杂度做“渐进式规范”。**

例如：
- 小 bug fix：直接改 + hook 验证
- 单模块需求：build + verify
- 跨模块/架构变更：完整流程（spec/plan/tasks/verify）

这点我认为是这篇文档比 BeatAI 更“治理化”的地方。

---

## 8. 在“人”的角色定位上的差异

## BeatAI

BeatAI 强调：
- 你要像问资深工程师一样提问
- 给 Claude 具体上下文
- 用挑战式提示提高质量
- 在复杂任务里做计划审计

它默认人是：
- 使用者
- 指挥者
- reviewer

## 工程实践文

它把“人”的职责写得更明确，也更制度化：

人应该负责：
- 做什么 / 不做什么
- 方案拍板
- 定义验收标准
- 查看验收结果

它甚至进一步指出：
- AI 可能过度工作
- AI 可能幻觉 API
- AI 可能只会迎合你
- 人必须补齐这些缺陷

这一部分，我认为《AI Coding 工程实践经验》比 BeatAI 讲得更透。

## 9. 哪篇文档更适合作为什么用途

## 如果你是 Claude Code 用户，想快速把工具用起来
优先看：
- **BeatAI 文档**

因为它直接告诉你：
- 用什么模式
- 配什么文件
- 开哪些功能
- 怎么做 Plan / Hook / Skill / 子代理 / Worktree

## 如果你在搭团队 AI Coding 方法论
优先看：
- **《AI Coding 工程实践经验》**

因为它在定义：
- 文件协议
- 流程分层
- 验收机制
- session 与状态边界
- 人的治理职责

## 如果你想要一套长期可运行的方法
最好的方式是：
- **两篇结合**

即：
- 用 BeatAI 解决工具实践
- 用《AI Coding 工程实践经验》解决工程治理

## 10. 对当前工作流的直接启发

如果把两篇文档映射到一个现实工作流，我会建议这样做：

### 10.1 文件分层
- `agents.md` / `AGENTS.md`：项目合约，短而硬
- `spec.md` / `requirements.md`：需求定义
- `plan.md`：技术方案
- `tasks.md`：执行拆解
- `verify.json`：机器可执行验收定义
- `verify-report.md`：验收结果沉淀

### 10.2 运行分层
- 主会话：协调、判断、验收
- 子代理 / session workers：隔离探索与执行
- Hooks：自动执行轻量确定性检查
- Skills：沉淀高频工作流

### 10.3 上下文分层
- 固定层：系统提示、最小合约、必要技能描述
- 半固定层：项目合约、关键规则
- 动态层：任务上下文、代码、日志、执行结果

### 10.4 验证分层
- 小改动：Hook 自动验证
- 中改动：`tasks.md` + 命令检查
- 大改动：`verify.json` + `verify-report`

## 11. 我认为《AI Coding 工程实践经验》比 BeatAI 更强的地方

1. **把验证文件化、结构化**
2. **明确 session 不是状态容器**
3. **明确提出流程分级**
4. **把“人”的职责说得更清楚**
5. **更适合作为跨厂商/跨工具的方法论**

---

## 12. 我认为 BeatAI 比《AI Coding 工程实践经验》更强的地方

1. **工具细节丰富，直接可操作**
2. **Claude Code 生态配置讲得很全**
3. **Plan Mode / AskUserQuestion / Hook / Worktree 等实践更具体**
4. **更适合新手快速进入真实 AI Coding 节奏**

---

## 13. 最终综合判断

如果只让我给一句话评价：

> **BeatAI 像一本 Claude Code 使用手册，**
> **《AI Coding 工程实践经验》像一份 AI 工程治理白皮书。**

前者解决：
- 工具怎么用
- 功能怎么配
- 流程怎么跑

后者解决：
- 规则怎么设计
- 文件怎么分层
- 状态怎么沉淀
- 验收怎么约束
- 人该在哪些关键环节拍板

两篇文档最好的关系不是替代，而是：

> **BeatAI 提供“术”，**
> **工程实践文提供“法”。**

如果能把两者合并成一套工作流，AI Coding 才更有机会长期稳定地产生真正可信的工程结果。
