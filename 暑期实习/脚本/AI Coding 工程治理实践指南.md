## 1. 这篇指南解决什么问题

这篇指南讨论的是** 怎么把 Claude Code 放进一套对工程真正有利的工作流里。**

AI Coding 真正难的地方，通常不是模型不会写代码，而是以下问题反复出现：

- 需求没想清楚，AI 很快写错题
- 上下文被历史错误、搜索噪声、无关日志污染
- AI 口头说“完成了”，但其实没有验证
- 会话越拖越长，质量越来越差
- 团队把状态放在聊天里，换个会话就丢了
- 简单需求套复杂流程，复杂需求又缺少治理

所以这份文档的目标不是教你“更会聊天”，而是帮助你建立一套可持续的 AI Coding 方法：

- **对个人开发者**：让 Claude Code 真正成为高质量执行器，而不是不稳定的代码生成器
- **对团队**：把规范、状态、计划和验收写进文件，做成可治理、可审计、可复盘的流程

整篇主线只有一条：

> **Claude Code 负责高效执行，文件负责沉淀状态，验证负责闭环质量，人负责做关键判断。**

## 2. AI Coding 的四个底层约束

### 2.1 上下文是稀缺资源

模型的上下文窗口不是无限的。一次会话里装进去的东西越多，越可能出现：

- 旧方案污染新判断
- 失败尝试压过有效信息
- 约束变得模糊
- 输出质量下降甚至产生幻觉

因此，AI Coding 的核心不是“给更多上下文”，而是：

> **给足够但精准的上下文，让真正重要的信息留下来，让无关噪声少进来。**

### 2.2 验证比自我汇报更重要

AI 的自我汇报不可靠。

它可能：

- 说“已经修复”，但根本没有运行测试
- 说“看起来没问题”，但只是主观判断
- 为了迎合提问，给出过度乐观结论

所以要坚持一个硬原则：

> **没有机器可观测的验证证据，就不能算完成。**

### 2.3 session 不是长期记忆

我们要记住：在ai agent中 上下文是最核心的领地，我们要充分优化上下文空间

会话适合做当前任务的执行流，不适合承担长期状态。

长会话的主要问题不是“记得多”，而是“噪声也一起积累”。一旦会话里混入：

- 过时约束
- 废弃方案
- 大量搜索结果
- 不再相关的日志

后续决策就会持续被污染。

因此，长期状态应该写进文件，而不是寄希望于某个 session “越来越懂项目”。

### 2.4 流程强度必须随任务复杂度变化

不是所有需求都值得走同样重的流程。

- 一个两行改动的小 bug fix，如果也要写 spec、plan、tasks、verify-report，流程就比问题本身更重
- 一个跨模块、涉及权限或并发安全的需求，如果只靠一句对话直接改，就很容易出事故

所以合理做法不是统一套模板，而是：

> **按任务复杂度、影响面和风险等级，选择不同强度的流程。**

## 3. 人、AI、文件分别负责什么

AI Coding 高效的前提，是边界清楚。

### 3.1 人负责什么

人在流程里至少要负责四类事情：

1. **决定做什么和不做什么**
2. **在多种方案之间拍板**
3. **定义验收标准**
4. **查看验收证据并决定是否接受结果**

换句话说，人不一定要亲自写实现，但必须掌握：

- 目标边界
- 风险判断
- 验收口径
- 最终裁决权

### 3.2 AI 负责什么

AI 适合承担这些高频执行类工作：

- 阅读代码和文档
- 搜索相关实现模式
- 生成计划草案
- 修改代码或文档
- 运行测试和命令
- 输出执行结果与差异总结

AI 的强项是：**高速度地消费上下文并执行明确任务**。

AI 的弱项是：

- 容易迎合提问者
- 容易过度设计
- 容易幻觉 API、依赖或实现细节
- 容易把“看起来合理”当成“已经验证”

### 3.3 文件负责什么

文件才是长期状态载体。

文件应当承担：

- 项目约束
- 需求定义
- 技术方案
- 执行拆解
- 验收定义
- 验收结果沉淀

这也是为什么高质量 AI Coding 不是靠“会话记忆”，而是靠**文件化治理**。

### 3.4 一个实用判断标准

如果一个信息满足以下任意条件，就不应该只留在对话里：

- 下个会话还会用到
- 别的成员也要看
- 它决定实现边界
- 它影响验收判断
- 它可以作为规范沉淀

这类信息都应该写进文件。

## 4. 文件体系：把状态、约束、验收写进文件

如果要让 AI Coding 可持续，至少要区分“项目合约”“需求”“方案”“执行”“验收”这几层。

### 4.1 `AGENTS.md`：工具中立的项目合约

`AGENTS.md` 负责描述跨工具、跨生态都成立的项目约束。

适合放进去的内容：

- 项目概览
- 技术栈和版本
- 目录结构与职责
- 项目特有编码规范
- 构建和测试命令
- 分层调用规则
- 明确禁止的反模式

一个好的 `AGENTS.md` 应当：

- 短而硬
- 每一行都真实影响 AI 行为
- 尽量少放经常变化的信息
- 更像“合约”，而不是百科全书

推荐结构：

```md
# 项目名称

## 技术栈
## 项目结构
## 项目特有规范
## 构建和测试命令
## 分层调用规则
## 不要做的事
```

### 4.2 `CLAUDE.md`：Claude Code 专用运行说明

如果 `AGENTS.md` 负责工具中立规则，那么 `CLAUDE.md` 更适合承载 **Claude Code 专用** 的运行指导。

适合放进去的内容：

- Claude Code 常用命令
- 本项目推荐的工作流提醒
- 需要特别注意的 Claude Code 工具边界
- 项目特有但仅对 Claude Code 有意义的操作说明

边界要明确：

- `AGENTS.md` 负责跨生态可复用约束
- `CLAUDE.md` 负责 Claude Code 专用运行细节
- 两者不要重复堆叠同一条规则

### 4.3 `spec.md`：定义需求与验收标准

`spec.md` 解决的是 **做什么**。

它应该回答：

- 目标是什么
- 用户价值是什么
- 成功标准是什么
- 边界和非目标是什么
- 哪些情况算完成

对于大需求，越早把需求偏差暴露在 `spec.md` 里，越省成本。

### 4.4 `plan.md`：定义技术方案

`plan.md` 解决的是 **怎么做**。

它适合包含：

- 模块划分
- 关键数据流
- 接口设计
- 关键实现策略
- 风险与取舍
- 需要修改哪些文件

如果 `spec.md` 是 WHAT，`plan.md` 就是 HOW。

### 4.5 `tasks.md`：定义可执行任务拆解

`tasks.md` 解决的是 **按什么顺序执行**。

它应该把 `plan.md` 拆成可独立推进的动作，例如：

- 先补失败测试
- 再写最小实现
- 跑指定验证命令
- 做自检
- 进入 review

拆解越明确，AI 的偏航空间越小。

### 4.6 `verify.json`：结构化验收定义

`verify.json` 的核心不是描述性文字，而是**可执行的验收命令**。

例如：

```json
{
  "id": "AC-1",
  "name": "用户注册接口返回201",
  "acceptance": "POST /api/register 返回 HTTP 201，body 含 userId 字段",
  "test_cmd": "mvn test -Dtest=UserApiTest#testRegisterSuccess",
  "status": "passing"
}
```

它的价值在于：

- 结构严格，不容易被误读
- 可以直接执行命令
- 不给 AI 留太多主观解释空间
- 适合后续自动化、审计和回归

### 4.7 `verify-report.md`：沉淀验收证据

`verify-report.md` 负责记录：

- 跑了哪些检查
- 结果是什么
- 输出片段是什么
- 哪些项通过，哪些项失败
- 是否满足验收条件

它不是“主观总结”，而是**结果存档**。

### 4.8 一份推荐的目录结构

```text
your-project/
├── AGENTS.md
├── CLAUDE.md
├── .claude/
│   ├── settings.json
│   ├── skills/
│   ├── agents/
│   └── worktrees/
├── .mcp.json
└── specs/
    └── 001-feature-name/
        ├── spec.md
        ├── plan.md
        ├── tasks.md
        ├── verify.json
        └── verify-report.md
```

不是每个需求都要把所有文件补齐，但一旦需求复杂到需要治理，这个分层就很有价值。

## 5. 运行流程：从需求到验收的标准闭环

一套稳定的 AI Coding 流程，至少应包含下面几个阶段。

### 5.1 Explore：先理解真实上下文

不要一上来就写。

先做这些事情：

- 读相关文件
- 找已有模式
- 看测试和配置
- 确认影响范围
- 找出约束和边界

这一步的目标不是产出代码，而是避免“写错问题”。

### 5.2 Plan：先把路线讲清楚

探索结束后，应该先出计划，而不是直接实现。

计划至少要回答：

- 改哪些文件
- 为什么改这些地方
- 数据流和调用关系会怎么变
- 风险点是什么
- 怎么验证结果

### 5.3 Implement：按计划实现

实现阶段应尽量遵循：

1. 先写失败测试或明确复现方式
2. 再写最小实现
3. 运行验证命令
4. 修复失败
5. 再汇报结果

这里最重要的不是“写得快”，而是**实现必须和计划、验收一致**。

### 5.4 Review：不要把自我审查当成审查

如果同一个上下文既负责实现，又负责评审，AI 很容易默认自己前面的路线是对的。

所以 review 最好具备一定隔离：

- 新 session
- 子代理
- 独立 reviewer
- 至少重新阅读变更与验收条件

### 5.5 Verify：以可观测证据收口

真正的结束条件不是“感觉差不多”，而是：

- 测试通过
- 命令输出符合预期
- UI 截图符合预期
- `verify.json` 中定义的检查通过
- `verify-report.md` 里有明确记录

### 5.6 Commit / Merge：把结果并入长期状态

提交或合并不是为了“保存”，而是为了让结果进入长期可追踪状态。

不过要注意：

- commit 是流程结果，不是每次对话都必须做的动作
- 是否提交、何时提交，取决于你的协作方式和风险控制

### 5.7 Spec-Driven Development 的位置

对于大需求，推荐显式采用 Spec-Driven Development：

- `spec.md` 定义需求
- `plan.md` 定义方案
- `tasks.md` 定义执行步骤
- `verify.json` / `verify-report.md` 定义和记录验收

它的核心价值是：

> **把发现问题的时机，尽量前移到文档层，而不是留到代码层。**

## 6. 渐进式规范：按任务规模选择流程强度

好的流程不是越完整越好，而是越匹配越好。

### 6.1 小改动：直接改 + 轻量验证

适合：

- 一两个文件的小改动
- 影响边界清楚
- 没有明显架构风险

推荐做法：

- 直接修改
- 跑最小必要验证
- 依赖 hook 做基础兜底

### 6.2 单模块任务：Build + Verify

适合：

- 改动涉及几个文件
- 仍集中在一个模块内
- 需求相对明确

推荐做法：

- 先明确局部方案
- 做模块级实现
- 用测试命令或 `verify.json` 做验收

### 6.3 跨模块或架构变更：完整流程

适合：

- 影响多个模块
- 修改关键数据流
- 涉及权限、安全、并发、缓存、一致性等问题
- 需求本身存在多种实现路径

推荐做法：

- 明确 `spec.md`
- 产出 `plan.md`
- 拆 `tasks.md`
- 使用结构化验证
- 把 review 和 verify 从实现上下文中隔离出来

### 6.4 什么时候应该“升档”

流程强度不能只看文件数，还要看风险。

即使只改一两个文件，如果涉及：

- 并发安全
- 权限校验
- 认证鉴权
- 核心数据流
- 安全边界

也应该提升流程强度。

反过来，即使改了多个文件，如果本质只是机械填充、风险低、边界清楚，也不一定需要最重流程。

## 7. 上下文管理：避免会话失控

上下文管理是 AI Coding 质量管理的核心。

### 7.1 上下文由哪些层组成

可以把上下文粗略分成三层：

#### 固定层

这部分通常每次都会进入上下文，变化很少：

- 系统提示
- Claude Code 工具定义
- skills 描述

#### 半固定层

这部分由项目维护，变化频率较低：

- `AGENTS.md`
- `CLAUDE.md`
- 必要的项目规则文档

#### 动态层

这部分会随着会话迅速膨胀：

- 对话历史
- 文件读取结果
- 工具执行结果
- 错误日志
- 测试输出
- 临时分析过程

真正最容易失控的是动态层。

### 7.2 为什么 `AGENTS.md` / `CLAUDE.md` 要短而硬

因为它们会高频进入上下文。

如果这类文件写成百科全书，就会：

- 破坏 Prompt Caching 的稳定前缀
- 稀释真正重要的约束
- 抬高每次会话的基础成本

好的写法应该是：

- 只写项目特有的重要规则
- 能引用现成文件就不要大段复制
- 能一句说清就不要三句

### 7.3 Prompt Caching 的意义

现代 AI API 普遍支持 Prompt Caching。简化理解：

```text
固定层 + 半固定层 = 更容易命中缓存的前缀
动态层 = 每次变化的部分
```

所以：

- 稳定、精简的前缀更省成本
- 经常改来改去的“长规则文件”会破坏缓存收益

### 7.4 给 Claude 足够具体的上下文

“具体化”不是把所有东西都塞进去，而是给它**足够但精准**的信息。

一个高质量任务描述通常包含四层：

1. 任务描述
2. 上下文
3. 约束
4. 验证标准

例如：

```text
实现 [功能描述]。

上下文：
- 相关文件：@path/to/files
- 参考实现：@path/to/example

要求：
1. xxx
2. xxx

验证：
- 运行测试
- 运行类型检查
```

### 7.5 什么时候该清会话

有几个很实用的信号：

- 你已经纠正 Claude 两次了，它还在原路线打补丁
- 当前任务已经和最初目标无关
- 会话里堆了大量探索结果和失败尝试
- 你自己都记不清哪些约束还有效

此时更好的做法通常是：

- `/clear`
- 用更清楚的新提示重开
- 只带必要文件和约束进入新会话

### 7.6 `/compact`、`/rewind`、新 session 和子代理

这些都属于上下文治理手段：

- `/compact`：压缩上下文，但前提是你知道保留了什么
- `/rewind`：回退到更干净的状态，而不是在错误路线继续叠上下文
- 新 session：彻底切断噪声
- 子代理：把探索、审计、批量分析等高噪声任务隔离出去

### 7.7 会话不是项目状态容器

如果某条关键信息只能在聊天记录里找到，那这条信息就没有真正被管理。

项目状态应当：

- 可重开
- 可切换 session
- 可让不同成员复用
- 可让 AI 在新上下文里重新读取

这些都要求状态写进文件，而不是留在聊天里。

## 8. 验证体系：把主观判断变成机器判断

验证体系的核心目标只有一个：

> **把“我觉得已经完成”变成“机器已经给出可观测证据”。**

### 8.1 轻量验证：确定性检查

这类检查适合日常小改动：

- 单元测试
- 集成测试
- 类型检查
- lint
- 构建检查
- 命令输出比对
- UI 截图验证

它们的共同特点是：

- 有明确的通过/失败结果
- 不依赖 AI 主观解释
- 可以高频执行

### 8.2 Hook：轻量级自动兜底

Hook 最适合做编辑后的自动检查。

好的 hook 特征是：

- 命令可直接运行
- 退出码明确
- 结果是机器给出的

例如：

```yaml
after_edit:
  - "pnpm lint"
  - "pnpm typecheck"
```

坏的 hook 则是这种：

```yaml
after_edit:
  - "请检查是否存在性能问题"
```

因为它还是把裁量权交回给了 AI。

### 8.3 重量验证：结构化验收

当任务已经不只是“代码能跑”，而是“是否满足验收定义”，就应该把验证提升到结构化层。

推荐组合：

- `verify.json`：定义应该怎么验收
- `verify-report.md`：记录实际验收结果

这样可以把验证拆成两层：

- **执行层**：Claude Code、测试命令、hook、脚本
- **定义与沉淀层**：`verify.json` 与 `verify-report.md`

### 8.4 UI / Screenshot 验证

很多结果不是只靠测试就能判断，尤其是前端或交互变更。

这时应该引入：

- 截图对比
- 实际页面检查
- 可视结果确认

这类验证虽然不是代码测试，但仍然属于**可观测证据**，比口头描述可靠得多。

### 8.5 一条必须坚持的原则

如果你不能回答下面这三个问题，就不该宣称完成：

1. 做什么算结束？
2. 怎么检查？
3. 检查结果的证据是什么？

## 9. Claude Code 落地：把方法论接到具体工具上

方法论只有落到工具上，才真正有用。

### 9.1 先建立正确使用姿势

Claude Code 更适合从这些事情开始：

- 代码库概览
- 单文件讲解
- 小改动加验证
- 局部探索

而不是一上来就让它“帮我重构整个系统”。

### 9.2 `AskUserQuestion` / 采访模式

当需求本身不清楚时，Claude Code 不应该急着实现，而应该先帮你把问题问清楚。

适合场景：

- 大功能前需求梳理
- 架构边界确认
- 风险与取舍澄清
- 事故复盘与盲点排查

它真正的价值不是“AI 在问问题”，而是：

> **把 Claude 从执行器，变成结构化提问顾问。**

### 9.3 权限系统

Claude Code 的权限系统不是障碍，而是风险控制工具。

推荐做法：

- 预批准安全命令
- 对共享状态、高风险操作保持谨慎
- 不要用“直接跳过权限”替代流程治理

核心思想是：

> **预批准常用安全动作，比关闭保护更好。**

### 9.4 CLI 工具

CLI 往往是最轻的外部交互方式，因为它们不会像常驻 MCP 一样持续占用上下文。

常见例子：

- `gh`
- `aws`
- `gcloud`
- `sentry-cli`

能用轻量 CLI 解决时，不一定要引入常驻上下文的工具层。

### 9.5 MCP

MCP 很强，但要有节制地用。

基本原则：

- 能不用就少用
- 不要同时挂一堆很少用的 server
- 定期审计上下文成本

MCP 适合：

- 确实需要结构化远程能力
- Claude 频繁要访问同类外部资源
- 这份能力值得长期接入

### 9.6 Hooks

Hooks 的意义不在于提醒，而在于**确定性执行**。

适合用来：

- 编辑后自动格式化
- 自动跑 lint / typecheck
- Stop 前阻止“未验证即收工”
- 阻止修改敏感路径

### 9.7 Skills

可以把 skill 理解成：

> **按需加载的工作流和领域知识包。**

它介于纯脚本和纯提示词之间：

- 比脚本更灵活
- 比纯提示词更稳定
- 可以把高频工作流沉淀下来

适合场景：

- 固定调试流程
- 统一实施规范
- 团队内部重复工作流

### 9.8 Subagents

子代理的核心价值不是“更聪明”，而是**上下文隔离**。

适合交给子代理的任务：

- 大范围代码库探索
- 审计与 review
- 并行分析
- 与主任务相对独立的辅助工作

可以把它理解成上下文防火墙。

### 9.9 Worktree

worktree 的价值是给每条任务线一个隔离工作区：

- 避免不同任务互相污染
- 便于并行开发
- 便于多代理分工

对于复杂任务、并行任务或需要高隔离的工作，worktree 很值得用。

### 9.10 Claude Code 的项目文件生态

一个常见的 Claude Code 项目目录可能包含：

```text
your-project/
├── CLAUDE.md
├── .claude/
│   ├── settings.json
│   ├── settings.local.json
│   ├── rules/
│   ├── agents/
│   ├── skills/
│   └── worktrees/
└── .mcp.json
```

这些文件的定位大致是：

- `.claude/settings.json`：Claude Code 行为配置
- `.claude/skills/`：可复用工作流与知识
- `.claude/agents/`：子代理定义
- `.mcp.json`：MCP 接入配置

### 9.11 Headless、并行与规模化

当你不再把 Claude Code 只当作交互式助手，而是把它当作可编排执行单元时，就会进入规模化阶段。

常见方向：

- Headless 模式跑固定任务
- 多会话并行处理不同问题
- worktree 支撑并行任务线
- 批量迁移、批量审计、批量摘要

这些能力最适合放在**结构清晰、验收明确**的工作流之上。

## 10. 常见失败模式与规避策略

### 10.1 厨房水槽式会话

一个会话里同时做：

- bug fix
- 文档修改
- 架构讨论
- 性能调优

最后上下文全混在一起。

**规避方式：** 按任务分 session，必要时 `/clear` 或直接开新会话。

### 10.2 反复在错误路线打补丁

Claude 已经连续两次走错，你还在原上下文里补第三次。

**规避方式：** 重开、回退或换干净上下文，而不是继续叠噪声。

### 10.3 把 `AGENTS.md` / `CLAUDE.md` 写得过长

规则很多，但真正重要的东西被淹没。

**规避方式：** 只保留高价值规则，详细材料按需引用。

### 10.4 信任但不验证

这是最常见也最危险的失败模式。

**规避方式：** 把完成定义绑定到测试、命令、截图、结构化验收，而不是口头回复。

### 10.5 无限探索

没有边界地让 Claude 查代码、查日志、查目录，最后上下文被搜索结果占满。

**规避方式：** 给探索限定范围、目标和产出要求；高噪声探索交给子代理。

### 10.6 AI 过度工作

简单问题被实现成复杂模式，产生本不需要的抽象和配置。

**规避方式：** 明确约束复杂度，坚持 YAGNI，只为当前问题付复杂度成本。

### 10.7 幻觉 API、依赖和实现细节

AI 可能引用根本不存在的 API，或者凭印象造出错误接口。

**规避方式：** 给文档、给路径、给真实实现样例，要求基于可读证据工作。

### 10.8 在同一个上下文里计划、实现、评审、验收

这样很容易让错误路线自我强化。

**规避方式：** 至少把 review 和 verify 与 implement 做一定隔离。

## 11. 推荐工作流模板

### 11.1 个人开发者工作流

适合：自己用 Claude Code 提升产出质量。

推荐流程：

1. 先让 Claude 解释相关代码
2. 明确目标、约束和验证方式
3. 小任务直接改，大任务先做计划
4. 修改后立即跑测试 / typecheck / lint
5. 两次纠偏无果就重开会话
6. 把复用价值高的规则沉淀到 `CLAUDE.md` 或 skill

### 11.2 团队工作流

适合：多人协作、长期维护、希望结果可审计。

推荐流程：

1. 在 `AGENTS.md` 里维护项目合约
2. 对大需求先写 `spec.md`
3. 再写 `plan.md`
4. 拆成 `tasks.md`
5. 用 `verify.json` 定义验收命令
6. 用 `verify-report.md` 记录验证结果
7. 将 review 与 verify 从实现上下文中隔离

### 11.3 一个简洁的 `CLAUDE.md` 模板

```md
# 构建与测试
- 安装：pnpm install
- 开发：pnpm dev
- 测试：pnpm test
- 类型检查：pnpm typecheck
- Lint：pnpm lint

# 项目特有规则
- 修改代码后运行 typecheck
- 不要修改 migrations 下已有文件
- 参考 src/features 下已有实现模式
```

### 11.4 一个简洁的 `AGENTS.md` 模板

```md
# 项目概览
- Web 应用，前后端分离

# 技术栈
- Node.js 20
- TypeScript 5
- PostgreSQL 16

# 项目结构
- src/api: HTTP 接口
- src/service: 业务逻辑
- src/db: 数据访问

# 构建和测试命令
- pnpm test
- pnpm typecheck
- pnpm lint

# 不要做的事
- 不要跨层直接调用数据库
- 不要改历史 migration
```

### 11.5 一个功能开发模板

```text
实现 [功能描述]。

上下文：
- 相关文件：@path/to/files
- 参考实现：@path/to/example

要求：
1. xxx
2. xxx
3. xxx

验证：
- 运行测试
- 运行类型检查
- 如涉及 UI，提供截图或页面验证结果
```

### 11.6 一个 Bug 修复模板

```text
修复 [问题描述]。

复现步骤：
1. xxx
2. xxx
3. 观察到错误 xxx

请：
1. 找到根因
2. 先写失败测试或明确复现检查
3. 修复问题
4. 运行验证命令
5. 输出验证结果
```

### 11.7 一个结构化验收思路

对于中大型需求，可以按下面思路组织：

```text
spec.md        定义需求和验收标准
plan.md        定义实现方案
tasks.md       拆执行步骤
verify.json    定义机器可执行验收
verify-report  沉淀实际验证结果
```

## 12. 总结：把 Claude Code 用成执行引擎，而不是聊天工具

如果只保留最核心的原则，这份指南可以概括成下面几条：

1. **上下文是最稀缺的资源**
2. **验证比自我汇报更重要**
3. **session 是临时执行流，不是长期记忆**
4. **文件才是状态、约束和验收的长期载体**
5. **大需求要分层：spec / plan / tasks / verify**
6. **流程强度必须按任务复杂度和风险升降**
7. **Claude Code 的价值不只是生成代码，而是进入一套可治理的工程流程**

真正高质量的 AI Coding，从来不是“让 AI 自由发挥”，而是：

- 目标清楚
- 约束清楚
- 文件分层清楚
- 验收标准清楚
- 上下文边界清楚

做到这些以后，Claude Code 才会从“会说话的代码生成器”，变成“真正可协作的工程执行引擎”。
