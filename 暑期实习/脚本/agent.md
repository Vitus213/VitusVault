## 🤖 AI Agent 与基础设施技术面试全全手册

### **第一部分：AI 核心基础与 RAG**

**Q7: 如何理解 LLM，Transformer 的核心机制，自注意力的计算过程？**

**A：**

- **LLM 本质**：基于统计学的概率分布采样器，通过上文预测下一个 Token。
- **Transformer 核心**：完全基于注意力机制（Attention），放弃了 RNN 的序列依赖，实现了并行化。
- **自注意力 (Self-Attention) 计算过程**：
  1. **映射**：输入向量经 $W^Q, W^K, W^V$ 矩阵变换得到 Query, Key, Value。
  2. **打分**：$Q$ 与所有 $K$ 计算点积得到相关性得分。
  3. **缩放与归一化**：除以 $\sqrt{d_k}$ 防止梯度消失，通过 Softmax 转化为权重。
  4. **加权求和**：权重作用于 $V$，输出包含上下文信息的特征表示。

**Q11: RAG 核心解决了什么问题？**

**A：**

1. **消除幻觉**：提供可靠的外部证据，让模型“据实回答”。
2. **知识时效性**：无需重训模型，只需更新索引即可掌握最新资讯。
3. **私有数据访问**：在不泄露权重的前提下，让模型理解企业内部文档或个人笔记。

**Q12: 知识库怎么去做增量的方案？**

**A：**

- **指纹对比 (CDC)**：对比文件 Hash，仅对变动文件重新切片（Chunking）。
- **层级监听**：利用 `inotify` 等 OS 机制监听特定目录（如 `.md` 库），触发自动化 Embedding 任务。
- **版本控制结合**：像管理 Git 代码一样管理知识库，记录 Commit ID，支持追溯和部分回滚。

**Q15: 既然知识时效性的问题可以用 RAG 解决，为什么不直接联网搜索呢？**

**A：**

- **覆盖范围**：联网搜索搜不到内网数据、本地文件（如你的 DragonOS 源码）。
- **噪音控制**：RAG 面对的是清洗后的干净数据，而搜索结果充斥着广告和无关信息。
- **成本与响应**：本地向量库检索通常比调用搜索引擎 API 更快且更经济。

**Q21: 向量数据库在选择建索引时用了哪种？为什么？**

**A：**

- **常见选择**：**pgvector (Postgres)**。
- **理由**：对于工程落地，pgvector 允许将业务数据（SQL）与向量数据（Embedding）存储在同一处，保证了事务一致性，且支持复杂的元数据过滤，比纯向量数据库更易维护。

**Q22: 引入 RRF 重排序后，有没有引入模型进行精排？**

**A：**

- **RRF** 是一种无需模型的混合排序（Reciprocal Rank Fusion），能有效平衡关键词搜索和语义搜索。
- **精排引入**：通常在 RRF 后接一个 **Cross-Encoder 模型**（如 BGE-Reranker）。它虽然慢，但能对 Top-10 的片段进行深度的语义相关性打分，显著提升首选答案准确度。

### **第二部分：Agent 架构与实战**

**Q5: Workflow, Agent, Skill 的区别是什么？**

**A：**

- **Skill**：原子能力（函数/API），Agent 的“手脚”。
- **Workflow**：预定义的线性/条件逻辑图（DAG），路径确定。
- **Agent**：具备“大脑”属性，自主规划路径，根据环境反馈决定下一步调用哪个 Skill。

**Q8: Agent 和普通的 LLM 调用的区别？**

**A：**

- **普通调用**：单次“提问-回答”，无状态或简单上下文。
- **Agent**：一个**闭环循环 (Loop)**。包括：感知环境 -> 思考规划 -> 执行行动 -> 观察反馈。

**Q9: 一个 Agent 系统应该有哪些模块？**

**A：**

1. **Brain (LLM)**：核心推理引擎。
2. **Planning**：任务拆解与反思逻辑。
3. **Memory**：短期（Context）与长期（RAG/Database）。
4. **Tools (Skills)**：与现实世界交互的接口。

**Q10: 如果 Agent 多步任务中工具调用出错，怎么设计反思纠错机制？**

**A：**

- **ReAct 模式**：强制模型输出 `Thought`，如果 `Observation` 报错，模型自动解析错误并生成新的 `Action`。
- **自我审视 (Self-Reflection)**：任务完成后，由另一个 Prompt 链路检查结果，不通过则标记重做。

**Q20: 你搭过 Agent 吗？做过 Agent 相关项目吗？**

**A：**

*(以你为例)*：深度参与 **OpenClaw (龙虾)** 项目，将其与 **DragonOS** 开发流结合。通过 **MCP** 协议实现了能读取内核源码并自主建议驱动修改方案的智能体。

**Q21b: OpenClaw 的记忆机制是怎样的？分几层，怎么实现的？**

**A：**

OpenClaw 采用独特的**可读化记忆**：

1. **瞬时记忆**：对话上下文，存在内存。
2. **工作记忆 (MD 文件)**：动态更新的 `memory.md`，记录当前项目进度、用户偏好。
3. **长期记忆 (知识库)**：离线 MD 文档库，通过本地检索加载。

- **优点**：透明可控，用户可以直接修改 MD 文件来“纠正” Agent 的记忆。

### **第三部分：MCP (模型上下文协议)**

**Q16: 什么是 MCP？**

**A：**

**Model Context Protocol**。它是一套标准化协议，将“数据源/工具”与“AI 模型”解耦。模型通过统一的 Client 访问不同的 MCP Servers（如 GitHub、Google Drive、本地文件系统）。

**Q9b: MCP 之前的工具调用流程是怎样的？**

**A：**

开发者必须为每个模型手动编写特定的 JSON Schema 定义，并手动在后端代码中硬编码函数映射（Function Mapping）。换个模型或换个工具就要重写大量集成逻辑。

**Q17: 在 Agent 里用 MCP 和用普通工具相比，有哪些不好的地方？（缺点与挑战）**

**A：**

1. **协议开销**：多层 JSON-RPC 封装带来的通信延迟。
2. **描述溢出**：大量 Server 挂载会导致 System Prompt 被工具说明占满，浪费 Token。
3. **安全风险**：权限控制粒度较粗，容易发生意外的本地文件读写。

**Q11b: MCP 的结果是流式的吗？**

**A：**

标准 MCP 协议目前的工具执行结果多为**原子性返回**（执行完再给结果）。但在复杂的 Agent 封装中，可以通过多轮异步通知或 Resources 监听来模拟流式感知。

**Q18 & 19: 为什么 MCP 会导致上下文过长？与历史记录的关系？**

**A：**

MCP 为了让模型理解如何使用工具，会将所有 Server 的元数据（Schema）塞进上下文。这些静态描述加上多轮调用的 Observation，会迅速堆积 Token，挤占对话历史。

### **第四部分：工程化落地 (LangGraph & 部署)**

**Q12b: 这个多 Agent 项目是主子 Agent 结构吗？**

**A：**

是的。采用 **Supervisor (主控)** 负责调度与任务分配，多个 **Worker (子 Agent)** 负责垂直领域执行（如 Coding Agent, Debug Agent）。

**Q13: 一次会话 Token 大概有多少？超过上限了吗？**

**A：**

典型任务约 **30k-80k Tokens**。在处理大型代码仓库时，通过 **RAG + 动态 Context 修剪**来防止超过 128k 的硬上限。

**Q15b: 子任务失败（如数据获取为空）如何重试或降级？**

**A：**

在 **LangGraph** 中设置条件边（Conditional Edges）。如果节点返回 `None` 或 `Error`，自动跳转至“重试节点”或“兜底搜索节点”，而非终止流程。

**Q16b: 如何实现流式输出并捕获节点执行结果？**

**A：**

利用 **FastAPI + SSE (Server-Sent Events)**。后端异步迭代 LangGraph 的 `app.astream()`，实时截获各个节点的输出，转化为 SSE 流推送到前端。

**Q17b: 为什么选 LangGraph 而非简单 LangChain？**

**A：**

因为 LangGraph 支持**循环 (Cycles)**。传统的 Chain 是单向的，而真正的 Agent 需要反复在各个状态间跳转、回溯，LangGraph 的状态机模型更契合这种复杂逻辑。

**Q18-20: Checkpoint 持久化与状态恢复？**

**A：**

LangGraph 内置 **Checkpointer**。状态被存储在 **PostgreSQL 或磁盘**中。通过 `thread_id` 重新连接，系统能从存储中加载快照，让 Agent 在断点处“起死回生”。

**Q6: Prompt 你会怎么考量去写？**

**A：**

1. **结构化**：使用 Role, Task, Constraints, Examples 明确划分模块。
2. **思维链 (CoT)**：强制模型写出推理过程。
3. **负面约束**：明确“禁止做什么”。
4. **动态注入**：根据 MCP 返回的元数据动态调整提示词，保持精简。
