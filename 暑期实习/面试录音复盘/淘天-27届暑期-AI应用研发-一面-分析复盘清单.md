### 3. loop 子系统与 cgroup 子系统

**问题**：loop 子系统的作用是什么？cgroup 子系统的作用是什么？为什么要实现它？

**我的回答原文**：loop 的作用是做一个抽象层，在 VFS 和具体文件之间把文件封装成一个块设备，所有对块设备的读写会映射到对文件的读写，还做了并发安全的删除等操作。cgroup 最重要的是为了容器进行监测，如果没有 cgroup，内核只能对单进程做资源限制，无法对多进程进行限制和可观测资源，比如 CPU 调度、CPU 占用、内存、IO 读写。为了在上面正确跑容器就需要 cgroup 子系统。

**不足**：回答本身比较完整，但可以更结构化。对 loop 的应用场景可以更丰富（比如 ISO 挂载、镜像构建等）；cgroup 的"监测"应该更准确说成"控制与监测"。

**回答关键词**：抽象层、VFS、块设备、文件映射、并发安全、资源隔离、进程组、容器基础设施

**参考回答**：
loop 设备本质上是一个虚拟块设备驱动。它的作用是把一个普通文件映射成块设备，让操作系统可以像操作硬盘一样操作这个文件。典型场景包括：挂载 ISO 镜像、测试文件系统、构建容器镜像时做读写层映射等。我在实现时主要做了文件到块设备的读写映射，以及并发安全情况下的设备创建和删除。

cgroup 是容器技术的核心基础设施之一。如果没有 cgroup，内核只能对单个进程做资源限制，而无法对一组进程（比如一个容器里的所有进程）统一做 CPU、内存、IO 的限制和监控。我实现的 cgroup V2 框架支持树形层级组织、租户路径隔离，以及 pid 和 CPU 控制器，目的是让容器平台能正确地在这套内核上做资源管理和调度。

### 4. cgroup 租户路径隔离方案

**问题**：你们实现 cgroup 资源控制时，租户路径隔离的方案是怎么样的？

**我的回答原文**：cgroup V2 版本是一棵树，所有 controller 都挂在树上。每个 cgroup 节点会有一条完整路径，从宿主机的 system file system cgroup 一直到当前目录。容器里的进程必须以为自己是根目录运行的，所以需要 namespace 隔离。通过判断它有没有 mount 参数，如果 mount 参数指定了需要以这个为根进行隔离，就会给它返回当前以这个为根的 pid 路径。

**不足**：表述有些绕，"system file system cgroup"这种说法不够准确（应该是 sysfs/cgroupfs 挂载点）；对 mount namespace 和 cgroup namespace 的区别没有讲清楚，容易让面试官混淆是 mount ns 还是 cgroup ns。

**回答关键词**：cgroup V2、树形层级、mount namespace、视图隔离、根路径重定向

**参考回答**：
在 cgroup V2 里，所有资源控制器都挂载在同一棵层级树上。每个 cgroup 节点都有自己的路径，从根节点一直延伸下来。

但容器里的进程需要看到一个"以自己为根"的 cgroup 视图，否则它读取 /proc/self/cgroup 时会看到宿主机的完整路径，这既不安全也不符合容器语义。所以我们做了路径隔离：

当容器启动时，如果 mount 参数里指定了要对 cgroup 做隔离，我们就会利用 mount namespace 把该 cgroup 子树挂载到容器的 /cgroup 根目录下。这样容器内的进程看到的 cgroup 路径就是以自己为根的相对路径，而不是宿主机的绝对路径。

同时我们在 cgroup 框架里也做了路径解析的适配：如果进程处于隔离环境中，返回的 cgroup 路径就是当前 namespace 内的路径，而不是全局路径。

**不足**：提到"G, y, s"时发音不清晰（实际是 GVisor），应该直接说 GVisor 测试套件；整个回答偏长，缺少一个清晰的"是什么 → 为什么 → 怎么做"结构。

**回答关键词**：GVisor 测试套件、多 agent 并行审查、共识投票、对抗性辩论、上下文管理、代码审查自动化

**参考回答**：
bug hunter 是我设计的一个多 agent 代码审查 skill，目标是在系统调用补全和代码提交前，自动化地发现潜在 bug。

背景是我们在补全 GVisor 系统调用测试套件（7000 多条用例）时，审查流程非常固定：要对比 Linux 语义、当前内核实现、以及测试用例源码。这个流程很适合交给 AI 来做。

具体做法是：
1. 启动多个 agent 并行审查同一段代码，每个 agent 赋予不同的审查视角（比如内存安全视角、并发逻辑视角、语义一致性视角）。
2. 为了避免单个 agent 因为上下文限制而钻牛角尖，我用脚本控制上下文顺序、通过共识投票来综合多个 agent 的结论。
3. 如果有分歧，就开启对抗性辩论，让 agent 互相质疑，最后汇总成带优先级的 bug 报告。

整个 skill 的核心价值是用可控的 token 消耗，获得接近人工代码审查的质量。

### 6. bug hunter 的模型选择与 token 优化

**问题**：bug hunter 怎么样保证在尽量少的 token 下实现？用的是一套模型还是多套模型？

**我的回答原文**：会有多套模型。跟文件搜索有关的用轻量模型去筛查；涉及到死锁分析、要调用 gdb/pstack 这种强推理链条的用重磅模型如 gpt-4。同时起多个 agent 保持上下文干净。减少 token 的方式：减少返工、轻量操作用轻量模型、长推理用重磅模型。

**不足**：回答整体不错，但缺少具体的模型名称或能力分层标准（比如什么算"轻量"、什么算"重磅"）；对"上下文干净"的解释可以更具体。

**回答关键词**：模型分层、轻量模型初筛、重磅模型深推理、回调机制、上下文压缩、减少返工

**参考回答**：
我们用的是分层模型策略，核心思想是"该省的地方省，该花的地方花"。

对于文件搜索、代码定位、初步筛查这类不需要复杂推理的任务，用轻量级模型（比如 qwen-2.5-7b 或同等级别）快速完成，成本低、响应快。

对于死锁分析、内存安全验证、需要调用 gdb/pstack 做长链条推理的任务，用重磅模型（比如 GPT-4o 或 Claude 3.5 Sonnet）来保证深度和准确率。

为了控制 token：
1. 每个 agent 只负责一小块任务，保持上下文精简，避免一次性塞太多无关代码。
2. 引入回调机制：先用轻量模型做初筛，如果输出质量不够（比如只找到"没抽象"这种表面问题），再自动升级到重磅模型复评。
3. 多 agent 并行时，每个 agent 的上下文独立，不会互相污染。

### 7. 从轻量级到重量级的上下文策略

**问题**：从轻量级往重量级去做的时候，对上下文的理解是怎样的？是一上来就确定模型，还是轻量级效果不好会换？

**我的回答原文**：会有回调。轻量级模型跑完初步审查，另一个 agent 判断输出。如果觉得不满意（比如只是没抽象、没复用），就认为审查效果不好，换更重量级的。

**不足**：回答太短，没有把"上下文理解"这个关键词展开。面试官想问的可能是模型切换时上下文怎么传递、怎么保持一致性。

**回答关键词**：动态升级、输出质量评估、上下文传递、agent 协作、自动回调

**参考回答**：
不是一上来就定死的，而是动态升级的。

具体流程是：先用轻量模型做第一轮审查，产出一份初步报告。然后启动一个"评估 agent"去判断这份报告的质量，比如检查它发现的 bug 是否有实质性影响、分析是否深入、有没有遗漏关键路径。

如果评估 agent 认为输出太浅（比如只提到"代码可以进一步抽象"但没指出具体问题），就触发回调机制：把前一轮的关键上下文（比如可疑代码片段、初步结论）传递给重磅模型，由它做深度复评。

这样做的好处是，既不让重磅模型从头到尾看完整代码库浪费 token，又能确保关键问题不会被遗漏。上下文传递时，我们会做压缩和摘要，只保留必要的代码块和中间结论。

### 8. callback 后的反馈与投票机制

**问题**：callback 之后会有反馈机制或者打标吗？

**我的回答原文**：有。多个 agent 反馈后会投票，票多者得胜。对于有分歧的问题（比如一个认为是 bug 一个认为不是），会让两个 agent 互相辩论。

**不足**：回答偏短，可以补充投票规则、优先级排序逻辑、以及最终报告格式。

**回答关键词**：多 agent 投票、共识机制、对抗性辩论、优先级排序、分歧处理

**参考回答**：
有的。我们设计了一个多层的反馈和共识机制：

第一层是投票汇总。所有 agent 审查完后，对每个潜在 bug 进行投票。如果超过半数 agent 认为是 bug，就进入高优先级列表；如果只有少数人支持，就进入待确认列表。

第二层是对抗辩论。对于有分歧的问题（比如两个 agent 意见相反），会启动一个专门的辩论环节：让持不同意见的 agent 互相指出对方结论的漏洞，最后由第三个中立的仲裁 agent 根据辩论质量做出裁决。

第三层是优先级和标签。最终报告里每个 bug 都会标注：
- 严重等级（P0/P1/P2）
- 类型标签（如内存泄漏、竞态条件、语义不一致）
- 置信度（基于投票比例）
- 建议修复方案

### 10. 容器隔离机制

**问题**：容器的创建和删除过程中，如果别人再去操作，隔离是怎么做的？

**我的回答原文**：通过健全（JWT 认证）。访问请求带 JWT token 来决定能不能访问容器，如果属于用户就能访问，不属于就不能访问。保证容器之间的租户隔离，容器之间网络也要隔离开来。

**不足**：把"鉴权"说成了"健全"，是个明显的口误；回答混淆了"隔离"和"权限控制"两个概念。面试官问的是"隔离"（isolation），而候选人答的是"权限控制"（authorization）。网络隔离的具体实现没有展开。

**回答关键词**：鉴权、JWT、权限控制、租户隔离、网络隔离、namespace

**参考回答**：
这里需要从"权限隔离"和"运行时隔离"两个层面来说。

权限隔离层面：我们通过 JWT 认证来做访问控制。每个请求都要携带有效的 JWT token，服务端会校验 token 里的用户身份，只有容器所属租户才能对该容器执行创建、删除、查询等操作。这就从权限上阻止了越权操作。

运行时隔离层面：
- 进程隔离：每个容器运行在独立的 PID namespace 里，容器内看到的进程树和宿主机是隔离的。
- 网络隔离：通过 CNI 为每个容器分配独立的网络命名空间，容器之间默认不能互相通信，除非显式配置网络策略。
- 资源隔离：通过 cgroup 限制每个容器的 CPU、内存使用量，防止一个容器耗尽宿主资源影响其他租户。
- 文件系统隔离：用 overlayfs 为每个容器提供独立的可写层，容器对文件系统的修改不会互相影响。

### 12. AI Coding 笔试 - 智能旅行助手

**问题**：构建一个智能旅行助手，需要获取天气、机票、酒店信息，要求保持整体低延迟并行调用。

**我的回答原文**：通过问答形式规定技术栈、语言、需要的库作为硬性约束。测试先行（先写失败测试）。先看完 spec markdown 确定核心目标和禁止事项。生成 plan markdown 分阶段完成。开多个绘画（对话）针对 plan markdown 书写代码。写 plan 时先写测试再写代码再验证测试，按阶段轮巡。但发现千问 3.5 上下文有点短，开太多绘画爆了。

**不足**：回答更像是在描述"我怎么用 AI 写代码"，而不是"这道题我是怎么设计架构和实现的"。面试官想听的是候选人对低延迟并行调用的设计思路、错误处理、超时机制等技术细节，而不是 AI 辅助编码的工作流。

**回答关键词**：并行调用、低延迟、HTTP mock、异步 IO、错误处理、超时控制、结果聚合

**参考回答**：
这道题的核心是"低延迟"和"并行调用"。

我的设计思路是：
1. 并行发起请求：天气、机票、酒店三个接口之间没有依赖关系，所以应该同时发起，而不是串行。可以用 asyncio.gather 或者线程池来并行调用。
2. 异步 IO：如果接口是 HTTP 请求，用 aiohttp 或 httpx 的异步客户端，避免 IO 等待时阻塞线程。
3. 超时控制：每个接口设置合理的超时时间（比如 2-3 秒），如果某个接口超时或失败，不影响其他接口的返回，可以给出降级提示（比如"暂无法获取天气信息"）。
4. 错误处理：每个接口独立 try-catch，记录失败原因，最终聚合结果时把成功和失败的部分一起返回。
5. mock 数据源：如果题目没有提供真实接口，我可以先用 FastAPI 或 Flask 起一个 mock server，模拟天气、机票、酒店的 JSON 返回，保证主逻辑可测试。

如果进一步展开代码结构：
- 一个 TravelAssistant 类，封装三个 fetch 方法（fetch_weather、fetch_flights、fetch_hotels）。
- 一个 aggregate 方法，用 asyncio.gather 并行调用三个 fetch 方法，收集结果。
- 对外暴露一个 get_travel_info 接口，返回聚合后的旅行信息。

时间复杂度上，并行调用后的整体延迟取决于最慢的那个接口，而不是三者之和，这就是实现低延迟的关键。

## 项目重新包装指南

面试官的核心反馈是"项目偏底层 OS/容器，AI 场景结合不足"。下面给出基于 DragonOS 和 faasd-in-rust 源码的具体包装方法，把"操作系统 + Serverless 平台"重新表述为"AI Agent 基础设施 + Multi-Agent 应用"。

### 一、DragonOS：AI Agent 的轻量级安全执行底座

**旧叙事**：我做了一个 Rust 操作系统，实现了 loop 和 cgroup。

**新叙事**：我构建了一个面向 AI Agent 和 Serverless 工作负载的轻量级内核，核心解决的是 **"Agent 代码在用户环境安全执行"** 的隔离问题。

| 内核能力（源码位置） | 对应 AI 基础设施需求 | 面试表达话术 |
|---|---|---|
| **cgroup v2 + namespace** (`kernel/src/cgroup/`, `kernel/src/process/namespace/`) | 为每个 AI Agent 提供**资源受限的沙箱**。限制 CPU/内存/pids，隔离进程、网络、文件系统视图。 | "Agent 调用外部工具时，内核层的 cgroup 和 namespace 是最基础的资源沙箱。我实现的 `unshare`/`setns`/`pivot_root` 这套能力，可以让每个 Agent 任务运行在独立空间里，同时通过 cgroup 防止耗尽宿主资源。" |
| **loop 设备** (`kernel/src/driver/block/loop_device/`) | 为 Agent 提供**快速挂载的块设备抽象**。Agent 镜像、rootfs、工具链可以打包成文件，通过 loop 挂载成块设备供容器使用。 | "loop 设备的意义在于把 Agent 执行镜像接入标准块设备生态。测试文件系统、挂载 rootfs、构建 ISO 这些流程，都是 Agent 执行环境准备的基础设施。" |
| **pivot_root + mount propagation** (`kernel/src/process/namespace/mnt.rs`) | Agent 执行环境需要切换根文件系统，让 Agent 以为自己运行在一个干净的文件系统里。 | "`pivot_root` 和 mount namespace 是容器切换根文件系统的关键。Agent 执行用户代码前，必须把它'关'进一个干净的文件系统视图中。" |
| **runcell 容器运行时集成** (`user/dadk/config/all/runcell_0_1_0.toml`) | 目标明确：让内核能够跑容器运行时，最终支撑 AI Agent 的隔离执行。 | "DragonOS 的最终目标是在上面跑容器运行时 runcell。我负责的基础设施（loop + cgroup + namespace）都是为了这个目标服务的——让 Agent 有一个轻量、安全、可隔离的执行底座。" |

### 二、faasd-in-rust：AI Agent 的 Serverless 运行时编排层

**旧叙事**：我做了一个 FaaS 平台，用 containerd 管理容器。

**新叙事**：我实现了一个面向 AI Agent 函数的 **Serverless 运行时平台**，核心解决 Agent 的**快速启动、弹性扩缩容、多租户隔离**问题。

| 平台能力（源码位置） | 对应 AI Agent 工程化需求 | 面试表达话术 |
|---|---|---|
| **容器生命周期管理** (`crates/faas-containerd/src/impls/container.rs`, `task.rs`) | Agent 函数/工具的**冷启动和销毁**。比如 Agent 调用 Python 脚本分析数据，平台快速拉起容器、执行、回收。 | "faasd-in-rust 负责 Agent 函数的生命周期编排。Agent 每调用一次外部工具，平台就快速创建一个容器实例，执行完立刻销毁，实现类似 AWS Lambda 的按需执行。" |
| **overlayfs snapshot** (`crates/faas-containerd/src/impls/snapshot.rs`) | Agent 环境的**快速克隆和状态管理**。写时复制让 Agent 可以从基础镜像秒级启动。 | "overlayfs snapshot 是平台的核心加速手段。Agent 的执行环境可以通过写时复制从基础镜像秒级克隆，避免每次调用都重新构建整个 rootfs。" |
| **CNI + bridge 网桥** (`crates/faas-containerd/src/impls/cni/`) | 多 Agent **网络隔离和通信**。每个 Agent 函数实例有独立 IP 和网络命名空间。 | "多租户场景下，不同用户的 Agent 必须网络隔离。我用 CNI 为每个函数实例分配独立网络命名空间和 IP，防止 Agent A 窃取 Agent B 的流量或内部服务。" |
| **JWT + BFF 网关** (`crates/gateway/src/`) | Agent 服务的**多租户鉴权和路由**。不同用户的 Agent 只能访问自己的函数实例。 | "网关层统一做 JWT Bearer 鉴权，确保用户只能操作自己的 Agent 函数实例，从权限上阻止越权访问。" |
| **失败回滚** (`provider/function/deploy.rs` 中 `scopeguard`) | Agent 执行失败时的**资源自动回收**，防止容器/网络泄漏。 | "Agent 函数执行可能失败，我用 `scopeguard` 设计了部署失败自动回滚机制，确保镜像、容器、网络在任何一步出错时都能被正确回收，不会泄露资源。" |
