### 5. 密码哈希与加盐

**问题**：相同密码哈希后结果也相同，如果数据库被脱库，攻击者撞出一个密码后，不就能反推出所有相同哈希值的密码了吗？加盐是干什么的？为什么要加盐？

**我的回答原文**：我提到了自己用了 salt，但对为什么加盐、怎么加盐说不清，还把作用理解成“减少碰撞概率”。

**不足**：这题本质在考密码存储安全。你没有明确说出：密码不能只做裸哈希，要使用“随机盐 + 慢哈希算法”；固定盐意义有限；加盐主要是防彩虹表和避免相同密码得到相同结果，而不是“减少碰撞概率”。

**回答关键词**：随机盐、慢哈希、bcrypt、Argon2、彩虹表

**参考回答**：
如果密码只做普通哈希存储，会有两个明显问题。第一，相同密码会得到相同哈希值，攻击者一旦撞出一个常见密码，就能批量识别所有使用这个密码的账户；第二，普通哈希太快，容易被暴力枚举。

所以工程上不能只存裸哈希，一般会用“随机盐 + 慢哈希算法”的方案。随机盐的作用，是让即使两个用户密码一样，最终存下来的结果也不一样，这样攻击者没法通过相同哈希去批量推断用户密码，也能有效抵抗彩虹表攻击。

另外，哈希算法本身也不能选太快的通用算法，通常会选 bcrypt、scrypt 或 Argon2 这种专门用于密码存储的慢哈希算法，让每次试错成本变高。

更标准的做法是：用户注册或修改密码时，服务端为每个用户生成独立随机盐，然后用慢哈希算法对“密码 + 盐”进行处理，把盐和哈希结果一起存储。登录时再取出盐重新计算并比对。

### 6. 固定盐的问题

**问题**：你这个盐是什么时候加的？是固定盐还是随机盐？真正意义上的加盐应该怎么做？

**我的回答原文**：我是一开始写了一个配置，里面固定了一个盐。

**不足**：这是本场一个很明显的失分点。固定盐不能解决“不同用户相同密码产生相同结果”的核心问题。面试官已经明确提醒你，这不算真正意义上的加盐。

**回答关键词**：每用户独立盐、随机生成、和哈希结果一起存储

**参考回答**：
如果整个系统只配置一个固定盐，然后所有用户都用这个盐去哈希，其实安全收益很有限。因为对于两个密码相同的用户，他们最终得到的结果还是一样，攻击者依然能做批量分析。

真正更合理的加盐方式，是每个用户使用独立随机盐。也就是说，用户设置密码时，服务端先生成一个随机盐，然后用这个盐去参与密码哈希，最终把“盐 + 哈希结果”一起存到数据库里。

这样做的好处是：第一，相同密码在不同用户那里结果不同；第二，即使攻击者拿到了数据库，也很难一次性对所有用户做统一撞库分析。

### 7. Token 设计与多端登录

**问题**：如果 Token 和用户信息存在同一行里，一个用户是不是只能有一个 Token？如果用户在电脑和手机同时登录，想只失效其中一个登录态，应该怎么设计？

**我的回答原文**：我是这么搞的。后来在面试官提醒下意识到应该单独弄一张表，存多个 Token。

**不足**：这题考的是登录态建模能力。你一开始的设计把“用户”和“会话”混在一起了，无法支持多端登录、设备级注销、登录态追踪，也不利于扩展。

**回答关键词**：用户表、会话表、多端登录、单端失效、过期时间

**参考回答**：
如果把 Token 直接存在用户表里，那一个用户通常就只能维护一个登录态，这样设计会带来很多问题，比如不支持多端登录，或者无法做到只让某一个设备退出登录。

更合理的设计是把“用户信息”和“登录会话”拆开。用户表负责存用户本身的信息，比如用户 ID、账号、密码哈希等；另外单独建一张 session 或 token 表，用来记录每一次登录行为。

这张表里通常会包含 Token 或 session_id、user_id、设备类型、登录时间、过期时间、状态等字段。这样一个用户可以对应多条会话记录，就天然支持电脑、手机、平板多端同时在线。

如果要让某一个设备失效，只需要定位到对应那条会话记录，把它置为失效即可；如果要让全端退出，就批量失效这个 user_id 下面所有会话。

### 8. Token 校验优化

**问题**：如果每次校验 Token 都查数据库，像微信这种高并发场景数据库扛得住吗？怎么优化？

**我的回答原文**：用 Redis 缓存一下，或者用 CDN，在 CDN 上部署个 Redis。

**不足**：答出 Redis 是对的，但“CDN 上部署 Redis”直接暴露出概念混淆。CDN 是做静态内容分发的，不适合承载频繁变化的登录态数据。这里应该清楚区分：Redis 是业务侧高性能存储，CDN 是边缘静态资源分发。

**回答关键词**：Redis 缓存、Session 存储、热点查询、动态数据、静态资源

**参考回答**：
如果每次请求都去数据库校验 Token，在高并发场景下数据库压力会非常大，所以一般不会这么做。

更常见的做法是把登录态放到 Redis 这类高性能内存存储里。用户登录成功后，把 Token 和对应的用户信息、过期时间、状态等写入 Redis。后续每次请求过来，只需要根据 Token 去 Redis 查一次，就能快速判断这个登录态是否有效。

这样做的好处是读性能很高，而且 Token 校验本身就是高频读、低复杂度查询，特别适合放在 Redis 里。

至于 CDN，它主要适合分发静态资源，比如图片、视频、JS、CSS 这类内容，并不适合承载频繁变化的用户登录态数据，所以这里核心优化点还是 Redis，而不是 CDN。

### 9. CDN 和 Redis 的边界

**问题**：CDN 适合存什么？Redis 应该部署在哪里？

**我的回答原文**：CDN 适合视频流内容、图片、静态网页。Redis 我开始以为像 CDN 节点那样部署，后来在提醒下意识到是和应用服务器部署在一起或作为业务内网服务。

**不足**：这题本质是基础设施常识。后面被纠正后你能反应过来，但面试时最好主动讲清楚：CDN 做边缘静态分发；Redis 是业务侧高速读写存储，通常部署在应用可低延迟访问的内网环境里。

**回答关键词**：静态资源分发、业务内网缓存、低延迟访问

**参考回答**：
CDN 主要适合存放静态内容或者变化不频繁、适合边缘缓存的内容，比如图片、视频、音频、静态网页、JS、CSS 这些资源。它的核心价值是把内容分发到离用户更近的边缘节点，降低回源压力和访问延迟。

Redis 则更像是业务系统内部使用的高性能内存存储，常用来做缓存、会话存储、计数器、分布式锁等。它通常部署在应用服务器可以低延迟访问的内网环境里，而不是像 CDN 一样面向全球边缘分发。

所以两者职责完全不同：CDN 解决的是静态内容分发问题，Redis 解决的是业务运行时的高速读写和状态存取问题。

### 10. HTTPS 与中间人攻击

**问题**：HTTPS 是怎么防止中间人攻击的？怎么判断服务端发过来的证书是合法有效的？

**我的回答原文**：主要通过 CA 证书校验。中间人如果是假冒服务器，就没有权威认证。客户端会用 CA 公钥去解密证书，拿到服务器公钥。如果找不到可信 CA，或者用户不手动点信任，就无法骗过客户端。

**不足**：整体方向对，但表达有些混乱，比如“用 CA 公钥解密证书”这种说法不够严谨。更规范的说法应该是：客户端验证证书签名是否由受信任 CA 签发，同时校验证书链、域名、有效期等。

**回答关键词**：受信任 CA、证书链、签名校验、域名校验、有效期

**参考回答**：
HTTPS 防中间人攻击，核心靠的是证书体系和身份认证，不是只靠加密本身。因为如果没有身份认证，中间人完全可以和客户端、服务端分别建立两条加密连接，照样窃听内容。

真正阻止这种情况的关键是：服务端要向客户端出示一个由受信任 CA 签发的数字证书。客户端收到证书后，不会直接相信，而是会去校验几个关键点：
1. 这个证书是不是由受信任 CA 或其下级机构签发的；
2. 证书链是否完整且能一路验证到本机预置信任的根证书；
3. 证书里的域名是否和当前访问域名匹配；
4. 证书是否还在有效期内。

只有这些都通过，客户端才会相信“我现在连接的真的是目标服务器”，然后再去完成后续密钥协商。

### 11. CA、公钥与证书链

**问题**：CA 是什么？客户端从哪里拿到 CA 的公钥？每建立一个 HTTPS 连接，都要向互联网请求一次证书吗？证书链是怎么工作的？

**我的回答原文**：本机会预置一些根 CA 证书，子级证书可能需要在互联网上查找，我还提到了缓存。后面在面试官提示下才意识到证书链会随着证书一起带过来，不需要每次联网去查。

**不足**：这题你知道一半。知道“本机有根证书”是对的，但误以为中间链路证书要临时联网查，这是失分点。更标准的回答是：客户端本地预置信任根证书；服务端在握手时通常会把自己的证书和必要的中间证书链一起发给客户端；客户端沿链回溯到受信任根即可。

**回答关键词**：根证书预置、中间证书链、握手携带、链式验证

**参考回答**：
CA 可以理解成证书签发机构，它负责对服务器身份做背书。客户端之所以能信任某个服务器证书，不是因为它认识这个服务器，而是因为它信任签发这个证书的 CA 体系。

客户端的信任起点通常来自本机或浏览器预置的根证书列表。这些根证书里就包含了受信任根 CA 的公钥信息，所以客户端并不是每次握手都去网上现查根 CA。

在实际 TLS 握手里，服务端除了发自己的证书，通常还会把必要的中间证书一并发给客户端，组成证书链。客户端做的事情是：从服务器证书开始，逐级验证其签名者，最后看这条链能不能回到本机已经信任的某个根证书。

所以整个过程的关键是：根证书本地预置，中间证书链由服务端在握手时提供，客户端本地完成链式校验。

### 12. 进程和线程

**问题**：说一下进程和线程的区别，能有多细说多细。

**我的回答原文**：进程有独立虚拟内存空间、TLB、堆栈和变量，切换时开销大；线程共享同一个进程的内存空间，有自己的局部变量和函数栈，切换开销小。内核里都由 task_struct 表示，主要区别是 pid 和 tid，CPU 主要按线程调度。

**不足**：整体方向还可以，算是这场里答得相对能展开的一题。但也有几个表述不够严谨：比如“线程有自己的堆”不准确，堆通常是进程共享的；“进程有独立 TLB”这种说法也容易被追问时失真。你知道很多细节，但表达上还要再收敛。

**回答关键词**：地址空间隔离、资源拥有者、调度单位、上下文切换

**参考回答**：
进程和线程最核心的区别，可以从“资源拥有者”和“调度执行单元”两个角度来讲。

进程通常可以看成资源分配的基本单位。它有自己独立的虚拟地址空间，也持有打开的文件、信号处理、页表等一系列运行资源。不同进程之间默认是相互隔离的。

线程则通常是 CPU 调度的基本单位。一个进程内可以有多个线程，这些线程共享进程的大部分资源，比如地址空间、代码段、全局变量、打开的文件等，但每个线程会有自己独立的栈、寄存器上下文和线程局部存储。

所以从切换成本上看，进程切换通常更重，因为往往伴随地址空间切换；线程切换通常更轻，因为同进程内线程共享大部分资源。

如果从 Linux 实现角度讲，可以再补一句：Linux 内核里进程和线程在底层任务表示上很接近，都是 task_struct，只是共享资源的程度不同。

### 13. 协程

**问题**：操作系统能感知到协程的存在吗？你写过协程相关的程序吗？

**我的回答原文**：操作系统感知不到，因为协程是用户态实现，跑在线程下面。协程是协作式调度，线程是抢占式调度。Rust 里用过 tokio。

**不足**：大方向对，但你中间延伸到“协程挂在哪个核心上”这类说法时不够严谨。协程的重点是“用户态调度、由线程承载”，不要额外展开到不必要、且容易讲偏的 CPU 核问题。

**回答关键词**：用户态调度、线程承载、协作式切换、Tokio

**参考回答**：
通常意义上的协程，操作系统是不能直接感知的。因为协程一般是在用户态由运行时或框架自己实现的调度机制，OS 真正看到和调度的还是线程。

也就是说，协程本质上是在线程之上的更轻量执行单元。线程由操作系统抢占式调度，而协程通常由用户态运行时在合适的时机主动挂起和恢复，所以常被称为协作式调度。

协程最大的优势是切换成本低，比较适合高并发 IO 场景。因为当某个协程遇到 IO 等待时，运行时可以迅速切换到其他协程继续执行，而不一定要频繁触发线程切换。

如果结合我的实际经历，我在 Rust 里接触过 Tokio 这类运行时，对协程在 IO 场景下的调度方式有基本使用经验。

### 14. 螺旋数组

**问题**：螺旋数组：按螺旋顺序遍历或填充一个 N×N 的二维数组。

**我的回答原文**：我想直接一步一步把边界缩小，把数组填充起来。面试官认为这样也可以。

**不足**：这题整体问题不大，面试官也接受了思路。说明你对二维数组边界控制还可以。但这类题最终还是看“又快又稳”，不是只要有思路就够。

**回答关键词**：四边界、分层遍历、边界收缩

**参考回答**：
这题我会用四个边界来做，分别表示当前还没处理区域的上、下、左、右边界。每一轮按固定顺序处理四条边：先从左到右，再从上到下，再从右到左，再从下到上；每处理完一条边，就把对应边界向内收缩。

这样做的好处是思路稳定，而且无论 N 是奇数还是偶数都能统一处理。写代码时重点注意两个点：第一，每一轮操作前要判断边界是否仍然有效；第二，某些情况下上下边界或左右边界可能已经交错，这时要避免重复填充。

### 15. 二叉搜索树范围查找

**问题**：二叉搜索树范围查找：给一个二叉搜索树和区间 [low, high]，找出所有值在范围内的节点，并按顺序输出，同时考虑剪枝优化。

**我的回答原文**：一开始对非递归有点卡，后面改成递归。中途在剪枝和中序遍历主干上有些混乱，后来在面试官引导下逐渐对齐：整体仍然是左中右，只是通过条件控制左子树和右子树是否还需要遍历。

**不足**：这题暴露的不是“不会”，而是“现场稳定性不够”。你知道 BST 要中序遍历，也知道可以剪枝，但一到具体实现和表达时会在逻辑主干、剪枝位置、递归结构上反复摇摆，需要面试官不断拉回来。

**回答关键词**：中序遍历、区间剪枝、主干不变

**参考回答**：
这题利用二叉搜索树的有序性来做，核心思路是中序遍历加剪枝。

因为二叉搜索树中序遍历的结果天然是升序，所以只要沿着中序遍历框架去写，输出顺序就满足要求。剪枝点在于：
- 如果当前节点值大于 low，说明左子树里还有可能存在合法节点，此时才需要遍历左子树；
- 如果当前节点值在 [low, high] 范围内，就把它加入结果；
- 如果当前节点值小于 high，说明右子树里还有可能存在合法节点，此时才需要遍历右子树。

这样既保留了中序遍历的主干顺序，又避免访问不可能命中的子树。

## 总结

这场二面的核心问题不是完全没有基础，而是你的优势和岗位需求错位比较明显。

你在操作系统、线程协程、HTTPS 这些偏基础原理题上还能展开，但一旦进入岗位更看重的互联网后台问题，比如密码安全、Session 设计、多端登录、Redis/CDN 边界、数据库与高频校验路径优化，就开始明显吃力。面试官其实已经多次给提示，说明他在试着帮你往正确方向靠，但整体看仍然暴露出“底层背景强，业务后台经验弱”的问题。

如果你能把“虽然主要做底层，但已经做过哪些服务端链路、知道互联网后台这些基础设施各自是干什么的、能把认证登录态设计讲顺”补起来，后面的类似岗位面试会明显好很多。
