### 2. Rust 与 C++ / 服务端语言对比

**问题**：你觉得 Rust 在语言设计上相对于 C++ 有哪些优劣势和特性？与 Go、Python 等服务端语言相比呢？

**我的回答原文**：
- 从生命周期、所有权系统出发，讲了 Rust 在内存安全上的优势：避免悬垂指针、减少手动 free/delete；
- 对比 Java 的 GC，强调 Rust 无 GC 且高效；
- 对于 Go/Python，主要说“更适合写大模型/上层、不适合写底层系统”，因为有 GC、库重、不精细控制等；
- 提到 Linux 内核已经开始引入 Rust 作为内核开发语言之一。

**不足**：
- 对 Go 的评价有些泛，比如只说“不适合写系统”，没举具体场景（如延迟、内存碎片、GC pause）；
- 没有结合“小红书社区工程”这种后端业务说明“如果是纯业务后端，Go/Java 也很适合；Rust 更适合在关键路径、性能敏感的组件中使用”，让面试官看到你能区分不同问题的“合适工具”；
- 可以进一步说明“在团队里如何平衡 Rust 的学习成本与工程效率”，体现工程思维。

**回答关键词**：生命周期、所有权、内存安全、GC、系统编程、服务端语言选择

**参考回答**：
> 相比 C++，Rust 在内存安全上的主要优势在于所有权和借用规则，它在编译期就可以消除大部分悬垂指针和数据竞争问题，不需要依赖运行时的 GC，对像内核这类场景非常友好。
>
> 对比 Go/Python 这类服务端语言，我更倾向这样区分：
> - 如果是业务逻辑为主、对延迟和内存占用没有极致要求，比如大部分 Web 接口、BFF 层，用 Go/Java 是很合适的；
> - 如果是高并发、低延迟、对资源利用率极为敏感的核心组件（比如存储引擎、索引、内核模块），Rust/C++ 更适合，因为可以细粒度控制内存和并发行为。
>
> 在实际工程里，我不会“一刀切”只用 Rust，而是根据模块的性质选语言：对用户产品来说，业务迭代效率和学习成本也很重要，这一点我也很认同。

### 3. 进程 / 线程 / 协程与调度

**问题**：进程、线程和协程的区别是什么？内核线程和用户线程在调度开销上有什么不同？

**我的回答原文**：
- 从进程拥有独立地址空间、切换开销大、需要用户态→内核态切换说起；
- 线程共享进程地址空间，上下文切换开销更小；
- 简要提到用户线程和内核线程、多对一/一对一关系；
- 协程被描述为“在一个线程里模拟多个线程，减少上下文开销”。

**不足**：
- 没有系统地把“线程模型（三种典型：1:1、M:1、M:N）”讲清楚，导致听起来略散；
- 对协程的调度方式（用户态调度、协作式切换）没有展开；
- 在社区工程场景，这块属于“锦上添花”的基础题，答 OK 即可，时间可能有点多。

**回答关键词**：进程、线程、协程、调度、上下文切换、用户态/内核态

**参考回答**：
> 我会这样区分：
> - **进程**：拥有独立的地址空间和资源，是内核调度和资源分配的基本单位。切换进程需要保存/恢复较完整的上下文，开销相对大。
> - **线程**：同一进程内的多个执行流，共享地址空间和大部分资源，切换线程主要是寄存器、栈等，开销比进程小。
> - **协程**：通常由用户态库实现的“轻量级线程”，调度由应用控制，不需要内核参与，切换成本更低，适合 IO 密集场景。
>
> 内核线程和用户线程之间的差异在于：内核线程由内核调度，可以在阻塞时由调度器切换到其他线程继续执行；用户线程如果完全在用户态实现，一旦遇到阻塞系统调用，往往需要配合非阻塞 IO 或 epoll 这类机制，否则会导致整个线程被阻塞。

### 5. 字符串解码算法题

**问题**：实现字符串解码（带数字+中括号、支持嵌套），给出思路并实现，尽量写出可运行代码。

**我的回答原文**：
- 给出了用栈解决嵌套的思路：遇到非右括号字符全部入栈，遇到右括号时弹出直到左括号，获取重复次数，将中间字符串按次数重复后再压栈；
- 使用 C++ + VS Code 实现，依赖补全调整代码；
- 能清楚解释逻辑，并指出可优化的点：当前是按字符入栈，可以改为按字符串降低复杂度。

**不足**：
- 一开始对开发环境不熟，显得有些手忙脚乱；
- 依赖补全较多，暴露出平时纯手写 C++ / 算法的练习量不足；
- 没有主动写多组测试用例验证边界（如多位数字、深度嵌套、空串等）；
- 对时间复杂度、空间复杂度的总结可以更系统一些。

**回答关键词**：栈、嵌套解码、字符 vs 字符串、时间复杂度、边界情况

**参考回答**：
> 这题可以用“两个栈”或“一个结构化栈”的思路来做：
> - 一个栈存前缀字符串；
> - 一个栈存重复次数；
> - 遍历字符串，遇到数字累积成整数，遇到 `[` 将当前前缀和次数入栈，清空当前前缀；遇到 `]` 时弹出次数和上一个前缀，把当前前缀重复次数次再接回去；普通字符则追加到当前前缀。
>
> 这样可以避免逐字符压栈，代码更简洁、复杂度更清晰。时间复杂度是 O(n * k)（其中 k 为最大重复倍数的平均值），空间复杂度 O(n)。

## 总结

这次小红书社区工程一面，失败的核心原因不是技术深度不够，而是“方向错位”：你展示的是“内核 + AI 开发工作流专家”，岗位需要的是“社区产品工程 + 全栈应用开发”。

后续再遇到类似岗位（特别是偏产品/社区/全栈的），需要在三方面提前调整：
1. **讲法调整**：用“能为业务/用户/团队带来什么”的语言讲你的底层经验，而不是只是展示技术炫技；
2. **项目准备**：哪怕只做一两个小的 Web/中后台项目，也要有可讲的前后端经验，让面试官看到你真的做过工程应用；
3. **职业定位**：在表达上更明确“我愿意做工程应用，并且会补足前端/产品侧的短板”，而不是给人一种“我其实想写内核，只是顺便来试试社区工程”的感觉。
