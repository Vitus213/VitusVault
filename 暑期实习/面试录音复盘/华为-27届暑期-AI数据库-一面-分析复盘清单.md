### 3. cgroup 原理与资源隔离

**问题**：简单介绍一下容器相关的 cgroup 原理，它是怎么做到资源隔离的？用了 Linux 的哪些能力？

**我的回答原文**：从自己实现的 cgroup v2 出发，先讲用一棵 cgroup_node 树表示 v2 的单树结构，通过 cgroup_root 做 ID 自增保证每个节点唯一；然后搭建了一个专门的 cgroup filesystem，通过 VFS 来封装和暴露 cgroup_node；在 PCB 中引入 task_cgroup 的弱引用，让进程从创建开始就指向对应的 cgroup 节点，并支持 fork 时继承；补充说明了 cgroup_netns 保障不同租户的路径隔离，以及在迁移过程中做 PID max 配额检查。

**不足**：
- 回答几乎完全基于“自己的实现”，对 Linux cgroup 的几个关键能力（多控制器、层级继承、与 namespace / capability 的组合）提及较少。
- 没有从“资源隔离”这个问题本身出发，总结 CPU / 内存 / I/O / 网络等维度的典型做法。
- 对于 AI 数据库场景，可以顺带讲讲如何用 cgroup 控制一个数据库实例的资源、防止 noisy neighbor，但当场没有展开。

**回答关键词**：cgroup v2、cgroup_node 树、cgroup filesystem、VFS、task_cgroup、net namespace、PID 限额

**参考回答**：
> 从原理上讲，cgroup 的核心就是：**给一组进程打上“控制组”的标签，然后对这组进程整体做资源限制、隔离和统计**。在 Linux 里，它主要配合几类能力实现资源隔离：
> 1. **层级化的控制组树**：cgroup v2 用一棵树表示控制组层级，子 cgroup 继承父级的一些限制，这样可以很自然地表达“一个租户下多个服务实例”的结构。
> 2. **多种控制器（controller）**：比如 CPU、内存、IO、pids 等，每个控制器负责一个资源维度。通过在 cgroup 节点上配置这些控制器，就可以为一组进程设置 CPU 配额、内存上限、IO 限速等。
> 3. **与 namespace 组合**：cgroup 本身侧重“资源配额和统计”，真正的隔离效果往往要结合 PID / NET / MOUNT 等 namespace，一起构成容器看到的“虚拟世界”。
>
> 在我的实现里，我按 v2 的思路，用一棵 cgroup_node 树和一个 cgroup filesystem 来表达这个结构：
> - cgroup filesystem 挂到 VFS 上，对用户和上层 runtime 暴露目录结构和配置接口；
> - PCB 里维护一个 task_cgroup 弱引用，让每个进程从出生开始就挂在某个节点上，fork 时继承父进程的 cgroup；
> - 通过 net namespace 和 PID 限额实现基本的租户隔离和配额控制。
>
> 对于数据库 / 向量检索场景，可以用 cgroup 把不同租户或不同服务组件（比如前端服务、向量索引构建、后台 compact 任务）放在不同 cgroup 里，分别设置 CPU / 内存权重，避免后台任务抢占前台查询的资源，这也是 AI infra 场景下比较典型的用法。

### 4. loop 设备状态机设计

**问题**：再讲讲 loop 设备子系统中的状态机实现，为什么要这样设计？

**我的回答原文**：说明在最初实现 loop 设备时，测试经常出现死锁，原因是删除设备时只回收了设备号和文件描述符，没有考虑正在进行的 I/O；因此后来引入状态机，把 loop 设备拆成 unbound、bound、run、draining、deleting 等状态：创建时是 unbound，可以绑定文件；运行时是 run；删除时先进入 draining 状态，拒绝新的 I/O，等所有 I/O 回调完成后再进入 deleting，最终回到 unbound，从而保证并发场景下删除过程安全。

**不足**：
- 回答已经比较完整，但可以再补充一点“如何统计正在进行的 I/O（比如用原子计数）”以及“与 Linux 实现的对比优势”，加强说服力。
- 没有明确把这套设计和“向量数据库 / 存储系统中的文件句柄管理、后台任务管理”等联系起来。

**回答关键词**：loop 设备、状态机、unbound / bound / run / draining / deleting、并发删除、原子计数

**参考回答**：
> loop 设备这块，我当时遇到的核心问题是：在并发 I/O 场景下删除设备，容易出现死锁或者 use-after-free。最初版本只是在删除时回收设备号和文件描述符，但没有跟踪正在进行的 I/O，导致测试经常卡住。
>
> 后来我引入了一个更明确的状态机，把 loop 设备划分为：
> - **unbound**：刚创建还没有绑定文件，可以接受绑定请求；
> - **bound / run**：已经绑定文件，正常接受读写请求；
> - **draining**：准备删除，拒绝新的 I/O，只等待现有 I/O 完成；
> - **deleting**：确认没有在飞行的 I/O 后，执行资源回收，回到 unbound。
>
> 配合一个原子 I/O 计数器，每次提交 I/O 前加一，完成后减一。删除流程是：先把状态切到 draining，阻止新 I/O，再等计数器归零后进入 deleting 做真正的清理。这避免了在 I/O 过程中释放底层资源的风险。
>
> 类似的思想在数据库和存储系统里也很常见，比如关闭一个表、索引或分片之前，要确保没有活跃的查询或写入，通常也会用状态机 + 计数器的方式来保证迁移和清理过程安全。

### 5. Rust 生命周期与所有权

**问题**：简单介绍一下 Rust 里的生命周期和所有权概念，它们分别解决了什么问题？

**我的回答原文**：强调 Rust 和 C++ 都没有 GC，C++ 需要手动管理指针释放和析构；Rust 通过生命周期让编译器在编译期了解引用的有效范围，从而在静态阶段决定何时释放；所有权系统带来 move 语义，在多线程中需要用 Arc 等智能指针来共享数据；所有权还能避免创建过多拷贝，减少内存开销。

**不足**：
- 表达方向大致正确，但术语使用不够严谨，例如“生命周期就是告诉编译器释放时机”会让人混淆生命周期和 Drop 的关系。
- 没有提到借用规则（不可变/可变借用），也没有明确说明这些规则如何在编译期阻止数据竞争和悬垂指针。

**回答关键词**：所有权、借用、生命周期、move 语义、Arc、数据竞争

**参考回答**：
> 在我理解里，Rust 解决内存安全问题的核心有三块：所有权、借用和生命周期。
> 1. **所有权**：每个值在任意时刻有且只有一个所有者，离开作用域时自动 Drop。通过 move 语义，编译器可以在没有 GC 的情况下确定资源的释放时机。
> 2. **借用**：在不转移所有权的前提下，可以对一个值做不可变借用（&T，多读）或者可变借用（&mut T，独占写）。编译器保证同一时刻要么有任意多个不可变借用，要么只有一个可变借用，从而在编译期就避免了数据竞争。
> 3. **生命周期**：是对引用有效范围的显式描述，编译器会检查引用的生命周期不能超过被引用值的生命周期，这样可以在编译期阻止悬垂指针。
>
> 这些规则组合在一起，让 Rust 在没有运行时 GC 的情况下，依然能在编译期保证大部分内存安全和并发安全问题被提前发现。

### 6. 并发场景下的智能指针修改

**问题**：在实际编程场景中，要对一个智能指针里的内容做修改，并且涉及多线程并发控制，怎么保证内部数据不会被并发修改？

**我的回答原文**：回答思路是使用 Arc 把数据在多线程之间共享，然后在 Arc 内部再包一层锁；读多写少场景下可以使用读写锁，读的时候加读锁允许多读，写的时候加写锁排斥其他读写；这样就可以避免在写的时候被其他线程读到不一致数据，或者在读的时候被写破坏一致性。

**不足**：
- 思路正确，但没有提到 Rust 里具体的锁类型（比如 Mutex / RwLock）以及 Send / Sync trait 的要求。
- 没有顺势提到“尽量减少锁粒度”和“避免在持锁期间做阻塞 IO”等工程实践点。

**回答关键词**：Arc、Mutex、RwLock、读写锁、数据一致性、多线程

**参考回答**：
> 在 Rust 里，如果我要在多线程之间共享并修改某个值，典型做法是用 `Arc<Mutex<T>>` 或 `Arc<RwLock<T>>`。
> - `Arc` 负责在多线程之间安全地共享所有权（原子引用计数）；
> - `Mutex` 或 `RwLock` 负责在同一时刻只允许一个写者，或者允许多读单写。
>
> 读多写少的情况下，我会选择 `Arc<RwLock<T>>`：
> - 读线程用 `read()` 拿到读锁，可以并发读取；
> - 写线程用 `write()` 拿到写锁，在写的期间阻止其他读写；
> - 写完释放锁后，其他线程才能继续访问。
>
> 在实现时还会注意两点：
> 1. 尽量缩小锁的作用域，把加锁时间控制在必要的代码片段内；
> 2. 避免在持锁状态下做阻塞 IO 或长时间计算，以减少锁竞争和死锁风险。

### 7. C++ 虚类 / 虚函数与 vtable

**问题**：简单讲讲 C++ 里的虚类 / 虚函数的作用是什么？底层是怎么实现的？

**不足**：
- 没有抓住“运行时多态”这个核心概念。
- 对 vtable 的实现方式、虚函数调用的动态绑定过程描述不清楚。

**回答关键词**：虚函数、抽象类、运行时多态、vtable、vptr、动态绑定

**参考回答**：
> 在 C++ 里，虚函数的主要作用是支持**运行时多态**。我们可以在基类里声明虚函数，在派生类里 override；当通过基类指针或引用调用虚函数时，实际执行的是对象动态类型对应的实现。
>
> 底层实现通常依赖 **虚函数表（vtable）** 和 **虚表指针（vptr）**：
> - 每个含有虚函数的类，编译器会为它生成一张 vtable，里面存放各个虚函数实现的地址；
> - 每个对象实例里会有一个隐藏的 vptr 指向这张 vtable；
> - 当通过基类指针调用虚函数时，实际上是通过 vptr 找到 vtable，再从 vtable 中取出对应的函数指针并调用。
>
> 这样就可以在运行时根据对象的实际类型，选择正确的函数实现，实现多态行为。

### 8. 指针与引用的区别

**问题**：指针和引用的区别是什么？在函数参数传递时有什么不同？

**我的回答原文**：回答比较含糊，大致提到“传引用可以减小开销，不需要新的指针”，但没有从语义和使用约束上做系统比较。

**不足**：
- 没有说明引用必须绑定到一个有效对象、不能为空，以及不能随意 reseat；
- 没有解释指针可以为 null、可以进行算术运算等特点；
- 没有提到在函数参数中引用看起来像传值，但实际上是别名。

**回答关键词**：空指针、别名、不可 reseat、语法糖、参数传递

**参考回答**：
> 简单说，引用可以理解为一个“必须绑定到某个对象的别名”，而指针更像是一个可以为空、可以修改的地址值。
> 1. **空值和绑定**：引用在初始化后必须绑定到一个有效对象，不能为 null，也不能重新绑定到另一个对象；指针可以为 null，也可以在生命周期中多次改变指向。
> 2. **语法使用**：引用在使用时像普通变量一样，不需要解引用操作符 `*`，而指针访问内容需要显式解引用。
> 3. **参数传递**：函数参数传引用在语法上像按值传递，但其实是给实参取了一个别名，在函数内部修改会反映到外部；传指针则需要在调用处显式取地址，语义更“显式”。
>
> 实际编程中，如果希望函数可以修改实参，又不想显式暴露指针操作，通常会优先使用引用；如果需要表示“可能为空”或需要在运行时动态改变指向，则可以使用指针。

### 9. LRU 缓存实现

**问题**：手写 LRU 缓存：在给定模板基础上，实现 get / put 等接口，保证 O(1) 访问与更新，并在 get 时更新最近使用顺序。

**我的回答原文**：采用了经典的哈希表 + 双向链表设计：定义一个节点结构，包含 key、value、prev、next；用一个 map 从 key 映射到节点指针；插入新节点时插到表头；删除节点时通过 prev / next 调整链表；当容量超过限制时从表尾删除最久未使用的节点；get 时在 map 中查找 key，找到则返回 value，没找到返回 -1。面试官提醒 get 也需要更新 LRU 顺序。

**不足**：
- 主体思路正确，但实现中遗漏了“在 get 命中时，把节点移动到表头”的步骤，这会导致经常访问的 key 依然被认为是旧数据。
- 链表和 map 的操作可以进一步封装成辅助函数，避免重复代码，提高可读性。

**回答关键词**：LRU、哈希表、双向链表、O(1)、表头/表尾、命中更新

**参考回答**：
> 标准的 LRU 实现是“哈希表 + 双向链表”：
> - 哈希表负责在 O(1) 时间内找到 key 对应的节点；
> - 双向链表按访问时间从新到旧保存所有节点，表头是最近使用的，表尾是最久未使用的。
>
> 关键操作有三个：
> 1. **get(key)**：
>    - 在 map 中查找 key，找不到直接返回 -1；
>    - 找到后，把对应节点从链表原位置摘下，移动到表头；
>    - 返回节点的 value。
> 2. **put(key, value)**：
>    - 如果 key 已存在：更新 value，并把节点移动到表头；
>    - 如果 key 不存在：
>      - 如果容量已满：从表尾删除一个节点，并在 map 中删除对应 key；
>      - 创建新节点，插入表头，并在 map 中建立映射。
> 3. **辅助函数**：实现 `remove_node` 和 `add_to_head` 两个函数，简化链表操作，减少出错概率。
>
> 这样可以保证所有操作都是 O(1)，同时正确维护最近使用顺序。
