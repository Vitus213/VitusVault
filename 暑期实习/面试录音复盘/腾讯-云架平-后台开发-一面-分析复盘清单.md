### 1. 项目介绍与落地情况

**问题**：先简单介绍一下自己。你这两个项目做完之后，现在有人在用吗？有没有收到过实际反馈、功能升级诉求或者使用反馈？

**我的回答原文**：我来自华南理工大学，做过两个和 Joviy OS 开源社区相关的项目。一个是转写 Linux 里的 loop 设备和 Cgroup MVP 版本，也研究配置了 Nix 统一工具链，还调优了一个 bug hunter skill。另一个是 serverless 平台，让开发者不用管理服务器，只写函数代码，通过 HTTP 请求得到回复。关于使用情况，fast 项目只在内部使用，还没有落地。loop 和 Cgroup 是为了容器化，现在已经能在自己写的 Joviy OS 上跑 runC、起容器了，这部分算落地；serverless 平台暂时还没有落地，准备后面和容器放在一起做成一个产品。

**不足**：回答里信息很多，但层次有点散；“哪些已经落地、哪些还没有、分别价值是什么”没有一开始就讲清楚；对面试官最关心的“真实用户价值、反馈闭环、后续演进”回答偏弱，容易让人觉得项目还停留在实验室阶段。

**回答关键词**：项目背景、落地情况、内部使用、runC、容器化、后续规划

**参考回答**：
我主要做过两个方向的项目。一个是操作系统和容器化相关的底层能力建设，另一个是 serverless 平台。

先说已经有阶段性落地的部分。操作系统项目里，我参与了 loop 设备和 Cgroup 的实现，这些能力的目标不是单独存在，而是为了支撑容器化场景。现在比较明确的阶段性成果是，我们已经能在自己写的系统上跑 runC、启动容器，这说明这部分工作已经不只是“写了代码”，而是确实支撑了上层场景。

### 2. Joviy OS 和 Linux 对比：最核心缺什么

**问题**：你觉得这个系统如果和 Linux 比，最核心还缺什么？如果真要落地，最大的短板在哪？你们现在调度的问题具体是什么？

**我的回答原文**：现在最大的问题是调度。虽然在 QEMU 虚拟机里分了八个核心，但它还是只能用一个核心调度，不能做多核调度。这会很大程度限制落地。现在虽然已经在推进 runC 和容器化，但调度肯定是很大的硬伤。

**不足**：方向答对了，能抓到“多核调度是核心短板”，这点不错；但后续没有继续展开“为什么多核调度做不好会严重影响容器和生产可用性”，导致回答停在现象层。对于这类问题，要从“场景影响”讲到“工程后果”。

**回答关键词**：多核调度、单核瓶颈、容器化、可扩展性、落地限制

**参考回答**：
如果让我选一个当前最影响落地的问题，我会优先说调度能力，尤其是多核调度。

现在系统虽然已经能在一些场景下跑起来，比如 runC 和容器化流程能通，但如果调度层面还只能有效利用单核，那它在真正面向服务部署时会遇到很大瓶颈。因为容器场景天然要求并发、多任务和资源隔离，如果底层调度不能把多个核心真正利用起来，吞吐、时延和资源利用率都会受到非常明显的限制。

也就是说，这个问题不只是“性能差一点”，而是会直接影响系统是否能承接更复杂、更真实的业务负载。所以从工程落地角度看，多核调度能力是一个很关键的门槛。

如果再往下讲，可以补一句：和 Linux 比，我们现在不是某个局部模块不够优，而是一些关键基础能力还在补齐阶段，调度就是其中最影响整体可用性的部分。

### 3. 为什么 Linux 更强、你们怎么改

**问题**：Linux 在这些问题上是怎么做的？为什么它能做得更稳定？如果要解决你们现在的问题，你有思路吗？

**我的回答原文**：Linux 因为面向服务器，又要向前兼容，所以积累了很多历史设计。我们用 Rust 重写时可以不兼顾旧代码，可以舍弃一些冗余设计。之前为了方便，在 Joviy OS 里用了大量自旋锁，导致进到 tty 等场景时，跑两个进程很容易死锁。现在在逐步把很多自旋锁改成读写锁和原子化。Linux 做得好的点在于锁的颗粒度更细，会尽量锁 inode 里的某几个字段，慎用自旋锁，也会通过软中断和硬中断去减少锁使用。

**不足**：这里有真实经验，但回答有两个问题。第一，把 Linux 的强归因到“历史包袱多”这个方向有点偏，面试官其实在问“为什么它还能跑得好”；第二，对“你们要怎么改”的答案还不够结构化，应该明确讲“现状问题 → 原因 → 优化路径”。

**回答关键词**：锁粒度、自旋锁、读写锁、原子操作、调度稳定性、结构化表达

**参考回答**：
如果从锁和调度角度讲，我理解 Linux 更强的一个关键点，是它在并发控制这件事上做了非常长期、非常细致的工程优化。

比如在很多路径上，它不会简单地用一个大锁把整段逻辑包起来，而是尽量把锁粒度做细，只保护真正需要保护的数据结构和关键字段。这样做的好处是，一方面减少锁竞争，另一方面也降低了因为锁范围过大导致的性能抖动和死锁风险。

我们目前遇到的问题，核心不是“调度算法名字不够先进”，而是基础并发控制还不够成熟。比如之前为了尽快把系统跑起来，用了比较多的自旋锁，这在原型阶段是能理解的，但到后面就会放大问题：锁范围过大、锁持有时间过长、多个路径之间容易相互影响。

如果说优化思路，我会按三步来做：
第一，先把热点路径找出来，明确哪些锁最影响并发和调度；
第二，把粗粒度自旋锁拆成更细粒度的读写锁、原子变量或者更局部的保护机制；
第三，再去结合实际场景做压测和 benchmark，看吞吐、延迟和锁竞争情况有没有改善。

这样讲会比单纯说“Linux 更成熟、我们用 Rust 可以优化”更有说服力，因为它把问题、原因和方案串起来了。

### 4. Rust、unsafe 和语言优势

**问题**：Rust 虽然强调内存安全，但你们项目里是不是也会用 unsafe？用了 unsafe 以后，和 C/C++ 的差别还剩多少？

**我的回答原文**：项目里还是有 unsafe 的。unsafe 就只能自己保证了，我们尽量减少。毕竟有些地方还是会看到别人写的 unsafe。这不就是 Rust 的哲学吗？它给你写 unsafe 的能力，但写不写看你自己。

**不足**：这题回答比较被动，而且有一点“顺着面试官质疑往下掉”。虽然说法不算错，但没有守住核心论点：Rust 的价值不是“完全没有 unsafe”，而是把不安全边界显式化、可审计化、可收缩化。这里如果答得好，其实是能扳回来的。

**回答关键词**：unsafe 边界、显式化、可审计、最小化封装、语言价值

**参考回答**：
是的，系统级项目里完全不用 unsafe 通常不现实，尤其是和硬件、内核底层数据结构、FFI 或一些底层指针操作打交道的时候。

但 Rust 的价值并不在于“绝对没有 unsafe”，而在于它把不安全边界显式标出来了。也就是说，默认代码是安全的，只有在确实需要突破编译器约束的时候，才进入 unsafe 区域。这样做的好处是，风险点是可见的、可审计的，而且可以被限制在很小的局部范围内。

和 C/C++ 相比，差别就在这里：C/C++ 里很多地方默认就是不安全的，风险是弥散的；Rust 则更像是把不安全操作收口到少量边界，并尽量用安全抽象把外层包起来。这样即使项目里存在 unsafe，也不等于整体退化成 C/C++ 的风险模型。

所以更好的工程目标不是“完全禁止 unsafe”，而是“让 unsafe 尽可能少、尽可能集中、尽可能容易审查”。

### 5. Cgroup 在 Linux 里怎么生效

**问题**：你写的 Cgroup 机制，在 Linux 里到底是怎么生效的？你已经讲了 pid 限制，那运行过程里的 request 和 limit 你是怎么控制的？

**我的回答原文**：Cgroup 本质上在内核里是一个虚拟文件系统。我实现的是通过 Cgroup namespace 管理 pid 限额，在 PCB 里给每个进程加一个 task Cgroup 结构，让它指向一个 Cgroup node。进程创建时检查这个 Cgroup node 的计数是否超过 max，超过就拒绝 fork，不超过就创建并加入。迁移进程时会检查权限和任务关系，再修改 PCB 对应结构。进程结束后也会实时更新。用户态通过系统文件系统里的 Cgroup 文件夹去观测这些数据。

**不足**：你对自己实现的那部分其实比较熟，但回答容易在细节里绕进去，没有先给一个总框架；另外面试官问 request 和 limit，本质上想看你是否理解“资源控制何时检查、何时生效、如何观测”，而不只是数据结构怎么挂。

**回答关键词**：虚拟文件系统、控制组、任务归属、fork 检查、迁移检查、资源限制、生效时机

**参考回答**：
Cgroup 可以理解成 Linux 提供的一套资源分组和限制机制。它的外部接口通常表现为一个虚拟文件系统，用户空间通过读写这些文件来配置资源限制和查看状态；内核内部则在进程创建、迁移、调度、资源分配等关键路径上读取这些配置并执行限制逻辑。

如果拿 pid 限制举例，它的生效点通常就在 fork 或创建任务的时候。也就是说，当一个进程准备创建子进程时，内核会先判断它所属的 Cgroup 当前计数和配置上限，如果已经达到上限，就直接拒绝创建。

如果是迁移场景，也不是简单改个指针就结束，而是要检查目标组是否允许接收这个任务、迁移后是否会超出限制、相关权限是否满足，然后才真正完成归属变更。

所以更完整的理解应该是：Cgroup 不是“靠某个后台线程统一管理”，而是在资源相关操作发生的关键路径上即时检查并执行限制。用户能看到的文件系统接口只是配置和观测手段，真正让它生效的是内核在各个资源路径上的钩子和检查逻辑。

### 6. Cgroup 版本差异与局限

**问题**：Linux 里的 Cgroup 发展到现在有几个版本？差异是什么？现在还有什么限制不了、或者满足不了某些场景需求的地方吗？

**我的回答原文**：最开始是 V1，现在主流是 V2。V1 是每个 controller 一棵树，所以一个线程可能同时分布在 CPU 树、内存树、pid 树里，管理起来比较不优雅、空间开销也大。V2 把它们统一成一棵树，每个节点管理任务集合，再对 CPU、memory、pid 这些做统一管理。我还提到 domain 之类的限制，比如有些层级下不能同时既当分配节点又直接挂任务。后来面试官追问有没有实际场景，我一时没想出来，只举了一个“容器外进程和容器里进程共同享受同一个 CPU 调度”的极端例子，但面试官也指出工业界其实没这个需求。

**不足**：前半段版本差异其实答得还行，说明你对 V1/V2 的结构差别有理解；真正失分点在后半段——你没有把“机制限制”转成“真实需求限制”，导致回答停在抽象层，面试官听不到工程意义。后面硬举例反而把自己带进死胡同。

**回答关键词**：V1/V2、单树模型、controller、工程场景、需求导向、机制与价值对应

**参考回答**：
Cgroup 主要可以分成 V1 和 V2 两代。

V1 的特点是每个 controller 基本独立组织，比如 CPU、memory、blkio 各自维护自己的层级结构。这样做的好处是早期实现直观，但问题是同一个任务可能在多个层级里分别维护，配置和管理比较分散，语义也容易不一致。

V2 更强调统一层级模型，把大部分控制能力收拢到一棵树里，让任务归属和资源控制语义更统一，管理上也更清晰。这也是为什么现代容器体系更倾向基于 V2 来做资源治理。

至于局限，回答这类问题时最好不要只谈“结构上有什么限制”，而要把它转成工程问题。比如可以这么说：Cgroup 已经能覆盖 CPU、内存、IO、pid 等很多典型资源治理场景，但它也不是万能的。一些更复杂、更高层的调度目标，比如跨容器、跨节点、结合业务优先级做全局资源编排，就不是单靠 Cgroup 本身就能解决的，往往还需要调度器、编排系统和监控反馈机制一起配合。

这样回答会更贴近工业界，而不是陷在纯机制讨论里。

### 7. 网络隔离与网络限额描述

**问题**：现在的 Cgroup 能描述网络隔离吗？比如一个容器限制 5G 带宽、另一个限制 2G 带宽，这种能表达吗？如果能，它大概怎么做？如果要写一个网络限额规则，它的描述对象应该是什么？

**我的回答原文**：我说标准实现是可以，但我自己没写出来，具体怎么做也不太清楚。后来面试官继续追问描述单元，我先说可以直接限制 IP 的流量，到额度就切断；面试官指出 IP 不是稳定抽象。后面我又说可以给每个新设备分配一个 minor 和设备号，再记录这个 IP 对应设备号的流量，到限额就中断。

**不足**：这是本场另一个明显短板。最开始承认自己没研究到这里，其实没问题；但后面被追问时开始猜，而且猜的抽象不稳定，越答越偏。这里最重要的教训不是“要全会”，而是“不会的边界要守住，先回答自己确定的部分”。

**回答关键词**：不会硬答、稳定抽象、网络限速、容器网络、控制对象、接口边界

**参考回答**：
这部分如果我自己没有完整研究过，我会先把确定的内容说清楚，再明确边界。

比如可以这样答：我知道标准体系里，容器网络资源是可以做限速和隔离的，但这部分通常不只是 Cgroup 单独完成，而是会和网络设备、qdisc、tc、容器网络插件这些机制一起配合。我自己目前对 CPU、pid 这类 controller 研究得更深，网络限速的具体实现细节还没有系统看过，所以不想在细节上乱讲。

如果面试官继续追问“那你推断一下描述对象是什么”，更稳妥的说法是：我会优先从“网络接口或流量控制规则”这种更稳定的抽象去想，而不是直接用 IP 这种动态属性去描述，因为 IP 不适合作为统一资源对象。对于容器场景，更可能围绕 veth、网卡队列、流量整形规则这类对象去做约束。

这样回答的重点不在于把所有细节答出来，而在于你能体现出抽象意识，并且不会在不确定的地方越说越错。

### 8. 算法题：1 到 n 中数字 1 出现的次数

**问题**：做一道题，统计从 1 到 n 中数字 1 出现的次数。可以先写一个暴力解，再想怎么优化。如果按数位拆分、按每一位出现 1 的组合来思考，你能不能推一下？如果写成算法，大概是什么思路？

**我的回答原文**：我先写了一个暴力解，中间还把 1 到 12 中 1 的个数数错了，后面修正了。暴力解对了之后，我说可以用 vector 存历史状态，类似 dp，用空间换时间。面试官提示按数位和组合来想后，我大概能跟上他的意思，比如把 129 按位拆开，考虑首位、十位、个位出现 1 的情况，但最后没有把这个思路抽象成一个完整算法，只说自己感觉还不是很清楚。

**不足**：算法题失分很明显。第一，暴力解阶段连样例都数错，暴露紧张和不够细；第二，优化方向一开始没抓到数位 DP / 数位统计的本质，先往普通 DP 上想偏了；第三，在面试官给了比较明显提示后，仍然没能收束成可执行算法，说明这类题型积累不够。

**回答关键词**：数位拆分、高位当前位低位、分类讨论、暴力解、临场推导、稳定性

**参考回答**：
这题的核心不是枚举每个数去统计，而是按数位单独计算每一位出现 1 的次数。

一个常见做法是，依次考虑个位、十位、百位……对于当前位，用 high、cur、low 三部分来描述：
- high：当前位左边的高位数字；
- cur：当前位本身的数字；
- low：当前位右边的低位数字；
- digit：当前处理的是哪一位，比如 1、10、100。

然后分三种情况：
1. 如果 cur == 0，那么当前位出现 1 的次数就是 high * digit；
2. 如果 cur == 1，那么次数就是 high * digit + low + 1；
3. 如果 cur > 1，那么次数就是 (high + 1) * digit。

这样把每一位的贡献加起来，就能在 O(log n) 时间内得到答案。

如果在面试里讲，我会先举 129 这种例子，把个位、十位、百位分别怎么算说清楚，再总结成公式。这样既容易让面试官跟上，也更容易自己写对。

## 复盘

### P0

**工程价值表达**
- 关键词：工业需求、卖点、benchmark、overhead、为什么有意义
- 练习方向：以后讲项目时，强制自己从“做了什么”升级到“为什么要做、解决了什么、比原来好在哪、代价是什么”四步表达

**不会的部分不要硬答**
- 关键词：边界感、承认未知、先答确定部分、稳定抽象
- 练习方向：模拟面试时专门练“不会题”的答法，先说明自己掌握到哪，再给有限推断，避免被追问后越答越偏

**数字类算法题补齐**
- 关键词：数位统计、high-cur-low、分类讨论、O(log n)
- 练习方向：把“1 到 n 出现次数”“数位 DP/数位统计”这一类题系统刷一遍，至少做到看到题就知道是按位贡献而不是暴力/普通 DP

### P1

**项目讲述结构化**
- 关键词：背景、问题、方案、效果、局限
- 练习方向：每个项目准备一版 1 分钟讲法和一版 3 分钟讲法，尤其准备“如果和 Linux 比还差什么”“为什么这样设计”这类追问

**系统问题的场景化表达**
- 关键词：机制、场景、需求、限制、工程后果
- 练习方向：回答 Cgroup、调度、网络限速这类问题时，先说“解决什么场景”，再说“机制怎么支撑”，不要只停留在数据结构层面

### P2

**性能测试与评价意识**
- 关键词：benchmark、对标 Linux、吞吐、时延、锁竞争
- 练习方向：给自己做过的模块都补一个“怎么评估它做得好不好”的模板，哪怕没有实测，也要知道理论上该看哪些指标

**表达聚焦与抗压能力**
- 关键词：少绕弯、先结论后展开、样例别数错、提示后尽快收束
- 练习方向：限时口述训练，每题先用一句话给结论，再展开两三点，不要边想边散着说

## 总结

这场挂掉不是因为你“没做事”，而是因为你做过的东西还没有被你转化成足够成熟的工程表达。

你的问题不是项目浅，而是回答常常停留在“我怎么实现的”，却没有切换到面试官更在意的那一层：这个机制为什么存在、它在工业界解决什么问题、它现在还有什么不足、你如何评价它做得好不好。

另外，这场也暴露了一个非常关键的面试习惯问题：不会的点一旦被追问，容易开始猜，最后把自己带偏。后面你最该练的，其实不是继续堆更多底层知识，而是把已有项目抽象成工程语言，再补上 benchmark 视角、场景意识和“不会题的稳定答法”。做到这一步，你这类项目经历的含金量才真正能在面试里打出来。
