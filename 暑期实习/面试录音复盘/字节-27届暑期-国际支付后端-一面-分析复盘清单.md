### 2. 最近一次提交与 Cgroup 实现

**问题**：发一下 GitHub 项目链接和你的主页链接，我看一下你的贡献情况。选一个你最近的提交，讲讲里面的代码逻辑和核心改动。你这个 Cgroup 的数据结构和方法设计，主要参考了什么？是参考教材、Linux 还是自己设计的？实现完之后，怎么验证这些代码的正确性？有没有做性能相关验证？

**我的回答原文**：最近这个 PR 主要是为了解决容器化过程中的资源管理问题。没有 Cgroup 的话，一个内核只能同时管理一个进程的资源调度；有了 Cgroup 就可以把很多线程放到一块统一做 CPU 和内存分配。我主要把整个 Cgroup 的框架搭了起来，搭了文件系统，实现了 pid 的配额检查，也补充了一些测试。核心数据结构是 Cgroup node，整个框架是一棵树，由 root 统领整个树，每个 node 管理父子节点、任务以及可开启的控制器。设计主要参考 Linux，对标先做一个 MVP，先让它具备管理进程的可用性。验证上主要是写单测，先做功能可行性验证，还没做 benchmark 和性能开销分析。

**不足**：讲提交逻辑时有点像“边看边说”，缺乏固定模板；“没有 Cgroup，一个内核只能同时管理一个进程资源”这句话不准确，容易被抠细节；验证手段只说单测不够，最好补上场景测试、边界测试和后续性能计划；“先做 MVP”是对的，但可以更清楚地说明你是怎么裁剪范围的。

**回答关键词**：Cgroup、树形结构、父子节点、资源限制、MVP、Linux 对标、单元测试、场景验证

**参考回答**：
这次我讲的提交主要和 Cgroup 能力建设有关，目标是给容器场景补上基础的资源管理能力。

先说为什么做这件事。容器场景里，不能只关注单个进程，而要能对一组进程做统一的资源隔离和限制，比如 CPU、内存、进程数这些维度。Cgroup 本质上就是为这个目标服务的，所以它是容器能力落地时一个很关键的基础模块。

我这次的核心工作主要有三块。第一块是把 Cgroup 的整体框架搭起来，包括核心数据结构和层级关系；第二块是把它和文件系统接口打通，让资源组管理具备可操作入口；第三块是先补一个比较基础但有代表性的控制能力，比如进程数限制相关检查。

在数据结构上，我用了树形组织方式。根节点负责管理整棵 Cgroup 树，每个节点记录自己的父子关系、关联任务以及启用的控制器。这样设计的原因是，Cgroup 天然就是层级化的，树形结构比较容易表达资源组继承、子组管理和遍历操作。

设计时我主要参考了 Linux 的 Cgroup 思路，但没有一开始就追求完全对齐，而是按 MVP 的思路先保证“能用”。也就是说，先围绕容器场景最需要的管理能力做出最小可运行版本，再逐步补齐更复杂的控制器和优化项。

验证上，我目前主要做了功能正确性验证，包括单元测试和场景测试，比如创建资源组、维护父子关系、任务挂载、限制检查这些基本流程。性能 benchmark 还没展开，如果后续继续往生产级能力推进，我会进一步补性能测试和压力测试，评估资源限制逻辑对调度和系统开销的影响。

### 4. 死锁定义与避免

**问题**：什么是死锁？怎么避免？

**我的回答原文**：死锁的话，比如两个事务都需要对 C 和 D 做操作，一个先做 C 再做 D，一个先做 D 再做 C，两个事务都抢占式调度，这样 A 拿 C 时还需要 D，B 拿 D 时还需要 C，所以会产生死锁。避免的话，可以尽量串行化，不让它们长时间持有锁，或者拿这个锁还想拿别的锁时释放掉，也可以通过信号量让它们顺序读同一个变量。

**不足**：例子能说明问题，但定义不够标准；避免方式偏散，没有明确落到最常见的工程方法上；没有提死锁四个必要条件，也没有突出“统一加锁顺序”这个最重要答案。

**回答关键词**：互斥、占有并等待、非抢占、环路等待、统一加锁顺序、超时、死锁检测

**参考回答**：
死锁是指多个线程、进程或者事务在竞争资源时，彼此都占有了一部分资源，同时又等待对方释放资源，最后形成循环等待，导致所有参与方都无法继续执行。

从理论上讲，死锁通常要同时满足四个必要条件：互斥、占有并等待、非抢占和环路等待。只要破坏其中任意一个条件，就可以避免死锁。

工程上最常见、也最实用的做法有几种。第一是统一加锁顺序，比如所有资源都按 ID 从小到大获取锁，这样就很难形成环路等待。第二是尽量缩短持锁时间，减少长事务。第三是加锁失败时做超时和重试，避免无限等待。第四是像数据库这样，在系统层面做死锁检测，一旦发现环，就主动回滚其中一个事务。

如果面试里让我优先给一个最落地的方案，我会先说统一加锁顺序，因为它简单、稳定，而且很适合推广到具体业务代码里。

### 5. 转账死锁场景题

**问题**：支付系统里一个经典场景：A 给 B 转账、B 同时给 A 转账，如果两个请求分别先锁住自己的账户，再去锁对方账户，就会死锁。你会怎么避免？

**我的回答原文**：我先想到通过时间戳，按先发起交易的人先完成操作；后来又想把加钱和扣钱拆成两个操作。但面试官指出时间戳极端情况下可能一样，而且拆成两个操作会破坏原子性。最后面试官给出的思路是按用户 ID 排序，不管 A 给 B 还是 B 给 A，都先操作 ID 小的账户。

**不足**：这是本场最明显短板。问题本质是资源获取顺序不一致导致环路等待，但你最开始没有抓住这个本质；时间戳方案不稳，拆操作方案破坏原子性；中间还有多次和面试官问题对不齐，说明业务场景题经验明显不足。

**回答关键词**：按 ID 排序、统一加锁顺序、原子性、账户转账、事务、一致性

**参考回答**：
这个问题的本质是，两个并发转账请求在获取账户资源时顺序不一致，所以形成了环路等待。最标准的做法就是统一加锁顺序。

具体来说，无论是 A 给 B 转账，还是 B 给 A 转账，都不要按照“付款方先锁、收款方后锁”的业务顺序获取锁，而是按照账户 ID 做全局排序。比如永远先锁 ID 较小的账户，再锁 ID 较大的账户。这样只要涉及同一对账户，所有请求的加锁顺序都是一致的，就不会形成死锁。

真正执行时，可以这样做：
1. 收到转账请求后，拿到付款账户和收款账户两个 ID；
2. 先比较两个 ID 的大小；
3. 按照从小到大的顺序获取锁；
4. 在同一个事务里完成余额校验、扣款、加款和流水写入；
5. 提交事务后统一释放锁。

这样做有三个好处：第一，能从根源上避免死锁；第二，不破坏转账操作的原子性；第三，规则简单，代码里容易统一执行。

如果面试官再追问分布式场景，可以补充：哪怕账户分布在不同节点上，也应该保持一致的资源排序规则，再结合分布式锁或者事务协调机制，保证所有请求按同一顺序获取资源。

### 6. Linux 进程状态

**问题**：Linux 常见的进程状态有哪些？

**我的回答原文**：就绪、阻塞和等待吧。如果一个 IO 读取，分配 CPU 时间片后开始执行，碰到 IO 时 CPU 对它进行软中断，然后变成阻塞状态，等数据到了之后再回到就绪状态。

**不足**：回答太口语化，也不够完整；Linux 里常见的说法最好带一点内核术语；漏掉停止态和僵尸态；“CPU 对它进行软中断然后阻塞”这个表述也不严谨。

**回答关键词**：运行态、可中断睡眠、不可中断睡眠、停止态、僵尸态、Linux 内核术语

**参考回答**：
如果从 Linux 内核视角讲，常见进程状态主要有几类。

第一类是 TASK_RUNNING，表示进程正在运行，或者已经处于可运行状态、等待调度器分配 CPU。也就是说，平时我们口头说的“运行态”和“就绪态”，在 Linux 里很多时候都会归到这一类。

第二类是睡眠态。比较常见的是可中断睡眠，也就是进程在等待某个事件，比如 IO 完成，这时候如果收到信号，是可以被唤醒的。还有一种是不可中断睡眠，通常出现在某些关键内核等待场景里，这时候不会轻易响应普通信号。

第三类是停止态，比如进程收到 SIGSTOP 之后暂停执行。

第四类是僵尸态，也就是进程本身已经退出了，但父进程还没有回收它的退出状态，所以还会保留少量进程信息。

如果面试官只是问“常见状态”，我会按运行/可运行、睡眠、停止、僵尸这几个层次来回答，既简洁又比较规范。

### 7. 键盘按键到屏幕显示

**问题**：在 Linux 里，从键盘按下一个键到这个按键显示在屏幕上，大致经历了哪些操作？

**我的回答原文**：键盘控制器会捕获字节流，因为键盘是实时操作，不像磁盘有 page cache，会直接往总线发，然后触发中断，CPU 实时捕获信息，再交给对应输出流输出出来。

**不足**：大方向对，但回答过粗；中间缺了输入子系统、TTY/终端、应用层处理和显示系统这些关键环节；最后“交给输出流输出”太泛，像没讲完。

**回答关键词**：键盘中断、扫描码、输入子系统、TTY、终端模拟器、显示系统

**参考回答**：
这个过程可以分成硬件输入、内核处理和用户态显示三段来理解。

第一步，用户按下键盘后，键盘控制器会产生对应的扫描码，并通过中断通知 CPU。

第二步，CPU 响应中断后，内核里的键盘驱动会把扫描码读出来，再交给 Linux 输入子系统做进一步处理，比如解析出具体是哪一个键、是按下还是释放、有没有组合键修饰。

第三步，如果当前是在终端环境下，这些输入事件会继续进入 TTY 子系统。TTY 的行规程会决定怎么处理输入，比如回显、退格、回车换行，或者把字符交给前台进程。

第四步，前台应用程序，比如 shell 或终端里的某个程序，从标准输入读取这个字符，并根据自己的逻辑决定怎么处理。

第五步，如果需要把字符显示出来，终端模拟器会把它渲染成图形字符，再通过图形栈和显示系统交给显卡，最终输出到屏幕上。

所以从链路上看，输入和显示其实是两条不同路径，只不过在终端场景下被应用程序和 TTY 机制串起来了。

### 8. TCP 慢启动与拥塞控制

**问题**：什么是 TCP 的慢启动？你再细说一下 TCP 的拥塞控制。

**我的回答原文**：慢启动主要体现在拥塞控制中，为了判断接收窗口大小，防止一次性发送过多的包。从零开始，每收到一个 ACK 就增长，整体是指数增长；达到限额后进入线性增长；收到三个重复 ACK 会骤减并快速恢复；如果一直收不到 ACK，链路断了就从零开始。

**不足**：整体答得不差，主流程基本在线；但“慢启动是为了判断接收窗口大小”这个表述不准确，容易把接收窗口和拥塞窗口混淆；如果面试官抠细节，可能会因此扣分。

**回答关键词**：拥塞窗口 cwnd、慢启动阈值 ssthresh、指数增长、线性增长、快速重传、快速恢复、AIMD

**参考回答**：
TCP 慢启动是拥塞控制的一部分。它的核心目标不是探测接收方窗口，而是探测当前网络能够承受的发送速率，避免连接一建立就向网络里注入过多数据。

具体做法是，连接建立后，发送方会从一个较小的拥塞窗口 cwnd 开始发数据。每收到一个 ACK，cwnd 就会增长，所以在一个 RTT 维度上看，慢启动阶段通常呈现近似指数增长。

当 cwnd 增长到慢启动阈值 ssthresh 后，就会进入拥塞避免阶段。这个阶段不再指数增长，而是更平滑地线性增长，避免把网络迅速推向拥塞边界。

如果出现丢包，TCP 会认为网络可能拥塞。这里常见有两种情况：
- 如果是超时重传，说明拥塞可能比较严重，这时通常会把 ssthresh 调小，并把 cwnd 重置到较小值，重新进入慢启动；
- 如果是收到三个重复 ACK，说明很可能有报文段丢失，但网络不一定完全堵死，于是会触发快速重传，并进入快速恢复，避免等待超时带来的吞吐损失。

整体上，TCP 拥塞控制可以概括为：慢启动阶段指数增长，拥塞避免阶段线性增长，检测到拥塞后再做乘性减小，这就是经典的 AIMD 思路。

### 9. HTTP、HTTPS 与 TLS 握手

**问题**：HTTP 和 HTTPS 的区别是什么？TLS 加密握手的细节说一下。

**我的回答原文**：HTTP 和 HTTPS 的主要区别是有没有 TLS 加密。HTTP 是明文请求，HTTPS 有 TLS 加密。TLS 握手里有 RSA 和 ECDHE，RSA 没有前向安全性。如果服务器私钥泄露，之前抓到的报文也能解密。握手过程大概是 TCP 建连后，客户端发 client hello，带版本、套件、随机数；服务端回 server hello，返回随机数、证书和公钥；客户端用 CA 公钥校验证书，然后生成主随机数，用服务端公钥加密发过去；服务端解密后双方得到会话密钥，之后用这个密钥加密通信。

**不足**：回答总体不错，是本场网络题里的强项；但如果想更稳，可以把 HTTPS 的三个价值点明确说成机密性、完整性、身份认证；另外 TLS 握手流程里“访问 CA”这种说法可以更严谨一点，重点应该是使用本地信任链验证证书。

**回答关键词**：TLS、机密性、完整性、身份认证、证书校验、RSA、ECDHE、前向安全性

**参考回答**：
HTTP 和 HTTPS 的区别，不只是“有没有加密”，而是 HTTPS 在 HTTP 和 TCP 之间增加了一层 TLS，用来解决三类问题：机密性、完整性和身份认证。

HTTP 是明文传输，如果链路被监听，请求内容、Cookie、Token 都可能被直接拿到。HTTPS 通过 TLS 对链路做保护，既能防止窃听，也能降低篡改和伪造服务端的风险。

TLS 握手大致可以这样理解：
第一步，客户端发起 ClientHello，带上支持的 TLS 版本、加密套件以及一个随机数。
第二步，服务端返回 ServerHello，选定协议参数，并返回证书、服务端随机数等信息。
第三步，客户端验证证书是否合法，比如是否由受信任 CA 签发、域名是否匹配、证书是否过期。
第四步，双方完成密钥协商，得到会话密钥。
第五步，后续应用数据使用这个会话密钥进行对称加密通信，因为对称加密效率更高。

如果展开讲 RSA 和 ECDHE 的区别，RSA 是客户端生成预主密钥，再用服务端公钥加密传给服务端；而 ECDHE 是双方通过临时密钥交换协商出共享密钥。ECDHE 的优势是具备前向安全性，也就是即使服务端私钥将来泄露，历史会话通常也不能被回溯解密，所以现代 TLS 更常用这种方式。

### 10. 数据包从应用层到网卡发出

**问题**：一个数据包从应用层产生到网卡发出的全过程是什么？

**我的回答原文**：从应用层产生之后，如果是 TCP/UDP，会在传输层封装对应头部，然后到 IP 层封装 IP 头，按 MTU 判断要不要分片，再到链路层打上 MAC 地址，然后找路由器和交换机，发到目标 IP。

**不足**：主干没问题，但还不够细；“找路由器交换机”更像出网之后的转发过程，不是“到网卡发出”为止的重点；缺少 socket、路由查找、ARP、驱动和 DMA 这些更有辨识度的点。

**回答关键词**：socket、传输层封装、IP 层、路由查找、ARP、链路层、网卡驱动、DMA

**参考回答**：
这个过程可以按三层来讲：应用层交数据、内核协议栈封装、网卡发送。

第一步，应用程序通过 socket 接口，比如 send 或 write，把数据从用户态交给内核。

第二步，内核在传输层处理。如果使用 TCP，就根据连接状态、发送窗口和拥塞窗口决定当前能发多少数据，并加上 TCP 头；如果是 UDP，就加 UDP 头。

第三步，网络层给报文加上 IP 头，同时根据路由表判断应该从哪个网卡发出、下一跳是谁。如果报文太大，还可能涉及分片。

第四步，链路层在真正发出去之前，需要知道下一跳设备的 MAC 地址。如果本地 ARP 缓存里没有，就先做 ARP 解析。拿到 MAC 后，再封装以太网帧。

第五步，封装好的数据交给网卡驱动。驱动把缓冲区和发送描述符交给网卡，网卡再通过 DMA 从内存里把数据取走，最终发送到物理介质上。

如果只问“到网卡发出”，讲到驱动和 DMA 这里就够完整了。

### 11. 三数之和算法题

**问题**：三数之和：给定一个整数数组 nums，返回所有和为 0 且不重复的三元组。先讲思路、分析时间复杂度，再写代码并跑题目里的 case。

**我的回答原文**：我想到一个 N 方的做法，先排序，然后固定一个位置 K，再让 I 和 J 从后面和末尾往中间遍历。如果当前和小于目标值就让 I++，大于就让 J--，等于就记录。相同的数就跳过。时间复杂度是 N 方。后面实现时因为重复元素和顺序问题调了比较久。

**不足**：思路本身是标准解，但口头表述里把目标值说成了 nums[k]，表达略乱；真正扣分点不在思路，而在编码稳定性和调试效率；面试官最后明确反馈“代码熟练度这块要提升”。

**回答关键词**：排序、枚举、双指针、去重、O(n²)、编码稳定性

**参考回答**：
这题的标准做法是排序加双指针。

先对数组排序。然后固定第一个数 nums[k]，接下来就在它右边用两个指针 i 和 j 去找另外两个数，使得三数之和为 0。

因为数组已经有序，所以如果当前三数之和小于 0，说明总和偏小，需要把 i 右移；如果大于 0，说明总和偏大，需要把 j 左移；如果等于 0，就把这个三元组记录下来，然后同时移动 i 和 j，并跳过重复元素。

这题最关键的是去重。第一层枚举 k 的时候，如果 nums[k] 和前一个数相同，就直接跳过；找到答案后，i 和 j 也都要跳过相同元素，否则结果会重复。

时间复杂度方面，排序是 O(n log n)，外层枚举加内层双指针是 O(n²)，整体复杂度由 O(n²) 主导。

如果在面试里写代码，我会特别注意三个地方：第一是外层去重；第二是找到答案后双指针的去重顺序；第三是边界条件，比如 i < j 时再做去重判断。这样能大幅降低调试时间。
