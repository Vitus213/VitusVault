### 3. 笔试里为什么先做一个 skill

**问题**：你在笔试里一上来先让模型实现一个 skill，这个 skill 的思路是什么？你希望它达成什么效果？

**我的回答原文**：我觉得模型思维能力不是很强，所以想先限定一个 skill。先做最基础的规范，比如技术栈、语言这些硬约束，再让它通过提问明确需求，列出 task，再落成 plan markdown，然后循环去读 plan，先写测试、再实现代码、再验证测试，尽量减少人工干预。

**不足**：整体思路其实很好，但开头“模型思维能力不是很强”这种表述容易显得在怪模型；更好的说法应该是“为了提高稳定性和复现性，所以先把 workflow 显式化”。

**回答关键词**：需求澄清、约束前置、任务拆解、plan、TDD、workflow 固化、减少人工干预

**参考回答**：
我一开始先做 skill，本质上不是为了多一个形式，而是为了把整个开发 workflow 显式化、可重复化。

因为我发现，如果直接把题目丢给模型，它很容易在需求理解、实现顺序、测试方式、验收标准这些地方自由发挥。这样看上去很快，但稳定性很差，尤其在考试场景下，一旦走偏，人工纠偏成本会很高。

所以我的思路是先做三件事。第一，把硬约束前置下来，比如技术栈、语言、项目结构、输入输出形式。第二，让它先做需求澄清和任务拆解，而不是直接开始写代码。第三，把拆解结果沉淀成 plan，再让它按固定流程推进，比如先测试、再实现、再验证、再反馈。

我想达成的效果，其实就是把一次性的 prompt 变成一个可复用的执行流程。这样做的价值在于：第一，减少模型随意发挥；第二，降低我重复盯过程的成本；第三，让它在执行时更接近一个被约束的 agent，而不是一个只会一次性生成答案的聊天模型。

### 4. 最后跑不起来，问题出在哪

**问题**：到了最后验收的时候东西跑不起来，而且你自己也不太清楚应该怎么跑、怎么测，你觉得哪个环节出了问题？

**我的回答原文**：当时我不太确定邮箱那个题到底需不需要 UI，在环境里好像也不太能接 UI。AI 写了终端测试，但我再让它单独写启动脚本时就会出问题，所以最后一直在调启动脚本。

**不足**：回答到了“现象”，但没有把问题抽象成“需求定义不清 + 最终交付标准不清 + 运行入口不清”这三个更高层的问题；这也是面试官后面一直在追问的核心。

**回答关键词**：需求不清、交付形态不清、运行入口、验收标准、环境约束

**参考回答**：
如果复盘这个问题，我现在会把它拆成三个层面。

第一，最前面的需求定义不够清楚。我虽然知道题目要做什么功能，但没有在一开始就明确“最终产物到底是 CLI、TUI、Web UI，还是一个纯命令行程序”。一旦最终形态没有定义清楚，后面的项目结构、启动方式、测试方式都会跟着摇摆。

第二，运行入口和验收方式没有前置约束。我后面之所以一直追着 AI 问“怎么跑”“怎么测”，说明这个东西从一开始就没有被定义成一个明确的交付标准。比如本来就应该先明确：启动命令是什么、输入输出是什么、成功标准是什么、演示路径是什么。

第三，到了后期我已经进入了局部修补状态。也就是说，我开始围着启动脚本打补丁，而不是回到需求和交付标准重新校准。这会让问题越来越像“工具故障”，但本质上其实是前面 specification 没收紧。

所以如果让我重新来一次，我会先固定最终交付形态，再固定运行入口和验收条件，然后才进入实现，这样后面的链路会稳很多。

### 5. 这是环境问题，还是上下文和流程问题

**问题**：这个问题主要是环境问题，还是其他问题？

**我的回答原文**：我觉得更像是上下文窗口比较小，又累积了很多上下文，导致模型产生幻觉。其实应该新建一个会话，用 sub agent 或者更干净的上下文去分任务。

**不足**：对“上下文污染”的判断是对的，但容易把锅主要甩给模型窗口；更完整的答案应该是“环境问题只是表象，真正问题是任务拆分粒度、上下文治理和阶段隔离做得不够”。

**回答关键词**：上下文污染、任务拆分、阶段隔离、sub agent、会话管理、幻觉

**参考回答**：
我现在回看，会觉得环境问题只是表象，更核心的是上下文治理和流程切分的问题。

因为如果 workflow 设计得足够清楚，即使工具本身能力一般，也不至于在后期完全失控。真正导致它跑偏的，是我把太多阶段堆在了同一个上下文里：前面的需求讨论、计划、实现、中间调试、启动脚本修补，全部混在一起了。这样一来，模型很容易把旧结论、错误路径、已经失效的假设继续沿用下去，最后看起来像“环境有问题”，但实际上是上下文已经不干净了。

所以我会把原因排序为：第一是流程切分和上下文管理不到位；第二是交付标准不够明确；第三才是具体环境和工具能力限制。如果重新做，我会尽量让不同阶段分会话、分任务，必要时让不同 agent 或 worktree 去处理不同问题，避免所有事情都堆在一个线程里。

### 6. 反馈链路怎么打通

**问题**：如果 AI 连怎么测试、怎么使用都不清楚，那你设计的六个阶段怎么真正跑起来？尤其 feedback 这条链路怎么打通？

**我的回答原文**：可以用 hook 这种方式。每次回复时让它继续往下走，写完测试、测试通过后再 reference 前面的 TDD 模式，用 hook 连回来，多次调优后就能稳定跑。

**不足**：方向是对的，但回答里“hook 能连回来”还是偏概念，没有说清楚 feedback 的客观输入是什么、停止条件是什么、失败时怎么回流到哪个阶段。

**回答关键词**：hook、反馈闭环、自动推进、客观信号、停止条件、阶段回流

**参考回答**：
要让这条链路真正跑起来，关键不是“有没有 hook”，而是 feedback 必须绑定到客观信号上。

我现在理解的正确做法应该是这样的：先定义每个阶段的输入输出。比如设计阶段的输出是 plan 文档；测试阶段的输出是可执行的 fail case；实现阶段的输出是让测试从 fail 变成 pass；验收阶段的输出是固定命令下的运行结果。只有这样，hook 才不是单纯“让它继续往下做”，而是“拿着一个明确的结果去决定下一步”。

换句话说，feedback 不能只是模型自己说“我觉得完成了”，而要变成：测试是否通过、覆盖率是否达标、启动命令是否成功、关键场景是否能跑通。如果这些条件没满足，就明确回流到上一个阶段，比如测试定义有问题、实现有问题，还是运行入口有问题。

所以 hook 是连接器，不是答案本身。真正决定闭环能不能成立的，是每个阶段有没有明确、可检查、可回流的标准。

### 7. AI 中途做错了什么，你怎么处理

**问题**：整个过程中 AI 有没有做出你觉得不对的事情？你是怎么处理的？

**我的回答原文**：有。因为上下文窗口小，我后来手动让它按一个任务一个任务执行，避免一次执行太多。到后面执行 4 和 5 的时候，它把 4.2 到 4.7 都跳过了，我认为是上下文导致它觉得前面已经做过了。

**不足**：问题识别得不错，但补救策略偏被动；如果能再说出“如何防止跳步”，会更完整，比如显式 checklist、阶段产物校验、禁止跨步执行。

**回答关键词**：跳步执行、上下文污染、任务粒度、显式 checklist、阶段校验

**参考回答**：
有，而且这个问题很典型，就是模型会在长流程里“自认为已经做过某一步”，于是直接跳步。

我当时观察到它在执行某个阶段时，把中间几个子任务直接略过去了。这个现象本质上说明两件事：第一，任务边界没有被强约束；第二，阶段完成状态没有被显式记录和校验。

我当时的处理方式是先把任务粒度降下来，让它一次只做一个任务，避免它在大任务里自由发挥。这种方法能止血，但并不是最优解。

更好的做法应该是：每个阶段都输出 checklist，完成一个就打一个；没有对应产物就不能进入下一步；必要时让它先复述“当前只允许做哪一步、完成标准是什么”。这样可以显著降低跳步和幻觉式补全的问题。

所以这类问题我现在的经验是，不要只靠人工盯过程，而是把“不能跳步”本身也设计进 workflow 里。

### 8. 你平时用什么模型，分别适合做什么

**问题**：你平常自己一般都用什么模型？你觉得它们分别适合做什么事情？

**我的回答原文**：最近会用 GPT 5.4，也会用 Opus 4.6 去做比较难的问题推理，比如研究调用链和死锁，或者先做计划；再让更适合写代码的模型执行。实验室也会发国产 API，我会接到工具里用。

**不足**：方向很好，说明你已经在做“模型分工”；但回答略口语化，可以更结构化，比如按“规划 / 推理 / 执行 / 成本”四个维度讲。

**回答关键词**：模型分工、规划、推理、执行、成本、工具链

**参考回答**：
我现在不会把所有模型都当成同一种能力来用，而是更偏向按任务类型做分工。

比如在规划和复杂推理阶段，我更倾向用推理能力更强、上下文处理更稳的模型。像分析调用链、定位死锁、梳理系统方案、先把一个 plan 写清楚，这类任务更吃抽象能力和结构化表达，我会优先用更强的推理模型去做。

到了执行阶段，比如按照已经比较明确的 plan 写代码、补实现、推进具体任务，我会更倾向用代码生成效率更高、响应更快的模型。因为这个阶段最重要的是吞吐和执行效率，不一定需要过强的开放式推理。

如果涉及日常高频但成本敏感的场景，我也会考虑更便宜或者更稳定接入的模型。也就是说，我的思路不是“哪个模型最好就全用它”，而是让不同模型分别承担规划、推理、执行、成本控制这几类角色，这样整体效率会更高。

### 9. 你为什么要继续优化 skill，优化后有什么变化

**问题**：你中间花了不少轮去调 skill，还尝试让它用 skill creator 一类的方式继续优化。你觉得问题主要出在 skill 描述本身吗？后来优化完之后效果有变好吗？

**我的回答原文**：我觉得主要是 skill 太耦合了，一开始生成得太笼统，甚至还是 JSON 格式。后来我发现应该把阶段解耦，每个阶段只用同一个入口 markdown，再多给 example 和 collection 去约束它。优化之后它执行命令的明确度高了很多，也更能遵守测试先行。

**不足**：整体回答不错，但还可以再往上抽象一层，说清楚“为什么耦合会导致模型不 follow”。

**回答关键词**：解耦、阶段化、入口统一、example、约束、可执行性

**参考回答**：
我后来会觉得，问题很大一部分确实出在 skill 描述本身，尤其是它一开始写得太耦合、太笼统。

耦合的问题在于：当一个 skill 同时想负责需求澄清、计划生成、实现、测试、反馈时，模型其实很难判断当前最重要的动作是什么。这样它虽然“看起来什么都知道”，但实际执行时会在阶段之间来回漂移，不稳定，也不容易复现。

所以我后来做的优化，本质上就是把 skill 从“大而全的总指令”改成“分阶段、分入口、强约束的流程描述”。比如每个阶段只解决一个问题，输入输出更清楚，同时给 example，让它知道什么叫正确执行；给 collection 或辅助文档，让它知道有哪些固定约束不能越过。

优化之后最大的变化，不是它变聪明了，而是它变稳定了。比如它更容易按测试先行的顺序执行，执行命令时也更明确，不像之前那样容易在不同阶段之间跳来跳去。这说明对 agent 来说，描述质量很多时候比“多说几句 prompt”更重要。

### 10. AI 自己写测试是否可靠

**问题**：你有 review 过 AI 写的测试吗？如果 AI 在同一个上下文里既写代码又写测试，这样的约束真的足够吗？

**我的回答原文**：我以前也发现如果先写实现再写测试，测试会很迎合它自己的实现。后来我改成测试先行，先写 fail test，再写实现代码。最好的方式还是多个 worktree 或 sub agent，让测试和代码分开。

**不足**：这一题答得不错，但可以更完整地区分“测试先行能缓解什么”和“测试隔离才能真正解决什么”。

**回答关键词**：测试先行、fail test、自证偏差、代码与测试隔离、独立验收

**参考回答**：
我现在的看法是，如果 AI 在同一个上下文里既写实现又写测试，那确实很容易出现“自证正确”的问题。因为它天然会沿着自己刚刚写出来的代码结构去设计测试，最后看起来测试都通过了，但其实只是测试贴合了实现，不代表实现真的对。

测试先行能缓解这个问题，因为它至少让测试在实现之前出现。这样测试不是事后为了迎合代码补出来的，而是先定义预期行为，再让实现去满足这些行为。这一步很关键。

但测试先行也不是万能的，因为如果仍然是同一个模型、同一个上下文完成全部工作，它依然可能在写测试时就把预期往自己擅长的方向收缩。所以更彻底的方案，是把“写测试”和“写实现”在上下文上隔离开。比如用不同会话、不同 worktree，甚至不同 agent 来做，让测试尽量保持独立性。

所以我的结论是：测试先行是必要但不充分条件；如果想让反馈更可信，还需要上下文隔离和独立验收。

### 11. 现在 AI 参与 coding 的比例，以及你怎么 review

**问题**：你现在在项目里让 AI 参与 coding 的比例大概有多少？你会详细 review AI 最终的代码吗？

**我的回答原文**：我觉得已经很高了，大概 80% 左右。前面人工干预够好、计划足够明确的话，它写的代码一般问题不大。我一开始会比较细 review，最近更多是看框架链路、测试代码和最终的流水线结果，社区也有大量测试用例和 action 在兜底。

**不足**：回答很真实，但“最近就不太会细 review 了”这句话风险较大，容易让面试官担心你对最终质量把关不够；更好的表达是“review 的重点发生了变化，从逐行转成架构、接口、关键风险和验收结果”。

**回答关键词**：80% 参与度、review 重心、计划质量、测试兜底、质量把关

**参考回答**：
如果从代码产出量和实际开发时间来看，AI 现在在我日常开发里的参与比例已经很高了，我会估计在 70% 到 80% 这个量级。尤其是当需求边界比较明确、计划写得足够清楚的时候，它在实现阶段的效率非常高。

但这并不意味着我把质量完全交给 AI。更准确地说，我的 review 重心发生了变化。以前可能更偏逐行看代码，现在我更关注四件事：第一，整体设计和模块边界有没有跑偏；第二，关键链路和异常路径是否覆盖到；第三，测试是否真正验证了核心行为；第四，最终的 CI、回归和运行结果是否符合预期。

也就是说，我不会机械地逐行 review 所有代码，但我会重点 review 高风险部分和最终交付质量。因为在 AI 参与度很高的情况下，人最重要的职责不是和它比手速，而是把住方向、边界和验收这几个关键点。

### 12. 你对 MCP 和 skill 的理解，以及它们的差别

**问题**：你能谈一下你对 MCP 和 skill 的认识吗？它们的区别、各自优势和劣势是什么？

**我的回答原文**：MCP 更像一个中转服务器，封装外部工具接口，多个 agent 可以共用；skill 更像新时代的脚本，介于 bash 和 prompt 之间，既有约束又留有思考空间。MCP 更固定，skill 更灵活，但灵活也意味着可能出错。

**不足**：方向基本正确，但可以更严谨。MCP 的核心是标准化工具调用协议，skill 的核心是工作流与行为约束模板；两者不是完全同层次的对比，一个更偏“能力接入”，一个更偏“执行方式定义”。

**回答关键词**：工具协议、能力接入、工作流模板、行为约束、确定性、灵活性

**参考回答**：
我会把 MCP 和 skill 看成两个不同层面的东西。

MCP 更偏“能力接入层”。它的核心价值是把外部工具、服务或环境能力，用一套标准协议暴露给 agent。这样不同 agent 不需要各自为每个工具重新发明一套调用方式，而是通过统一接口去访问浏览器、文件系统、数据库或者其他服务。它最大的优势是标准化、可复用、确定性强，缺点是接口边界相对固定，灵活性没那么高。

skill 更偏“工作流和行为约束层”。它不是在给 agent 增加一个外部能力，而是在告诉 agent：遇到某类任务时，应该按什么步骤做、优先看什么、输出长什么样、哪些规则必须遵守。它的优势是灵活、贴近实际任务、能把经验沉淀成 workflow；缺点是如果描述不够清楚，就很容易被模型自由发挥，稳定性不如硬接口。

所以在我看来，MCP 解决的是“你能做什么”，skill 解决的是“你应该怎么做”。前者更像标准化工具能力，后者更像结构化的方法论和执行模板。两者不是互相替代关系，而是经常要配合使用。

### 13. 你怎么看 AI 革命和“程序员会不会被取代”

**问题**：这几个月面对这次 AI 革命，你自己的感受是什么？你怎么看“程序员会被 AI 取代”这样的趋势？

**我的回答原文**：我觉得模型越来越强，各种 skill 和 MCP 都在诞生，agent 确实替代了很多工程工作，也让开源社区更活跃。但更重要的是去拥抱它、利用它、沉淀自己的 skill。AI 只是 agent，你的 idea 是它想不到的。

**不足**：观点方向是对的，但可以少一点口号式表达，多一点“哪些能力会被替代，哪些能力更重要”的层次感。

**回答关键词**：拥抱变化、提效工具、需求定义、约束能力、方法论沉淀、人的角色

**参考回答**：
我觉得这次变化和过去几轮 AI 浪潮最大的不同，是它已经真正进入了工程生产流程，而不只是停留在模型演示层面。无论是代码生成、测试、文档整理，还是方案讨论、问题定位，AI 都已经开始承担一部分真实工作，这一点和以前很不一样。

但我不觉得它会简单地“取代程序员”，更准确的说法是，它会重塑程序员的职责结构。那些高度重复、边界明确、可以被充分约束的工作，会越来越多地被 AI 承担；而需求澄清、目标定义、架构取舍、约束设计、质量把关、最终责任承担，这些事情反而会更重要。

所以我觉得关键不是抵制 AI，而是尽快学会怎么和它协作。谁更早掌握约束它、拆解任务、设计 workflow、建立验收标准的能力，谁就会在这个时代有更高的杠杆。人的价值不会消失，但会从“亲手做所有事”逐渐转向“定义问题、组织流程、把住结果”。

## 复盘

### P0

**最终产出定义不清**
- 关键词：交付形态、运行入口、验收标准、specification
- 练习方向：以后遇到 AI Coding 题，先明确最终产物是什么、怎么启动、怎么验收，再开始做 plan 和实现

**feedback 缺少客观信号**
- 关键词：pass/fail、覆盖率、启动命令、阶段回流、停止条件
- 练习方向：把每个阶段的输入输出写清楚，训练自己用“可检查条件”而不是“模型自我判断”来驱动闭环

**岗位匹配表达不够稳定**
- 关键词：AI 工程师、Agent 开发、AI Infra、系统能力迁移
- 练习方向：准备一套稳定表述，把自己的 OS/云原生背景和 AI Infra 岗位强绑定，不要在不同说法间漂移

### P1

**skill 设计需要进一步解耦**
- 关键词：分阶段、单一入口、example、collection、强约束
- 练习方向：复盘自己已有 skill，把需求澄清、计划、实现、测试、验收分成更清晰的步骤，减少“大而全”的描述

**模型分工表达可以更工程化**
- 关键词：规划、推理、执行、成本、吞吐
- 练习方向：把“不同模型适合做什么”总结成固定框架，避免临场只凭感觉描述

**review 策略要从“少 review”改成“重点 review”**
- 关键词：模块边界、关键链路、异常路径、CI、最终责任
- 练习方向：统一口径，不说“最近不太 review”，改成“review 重心从逐行转向高风险和验收结果”

### P2

**MCP 和 skill 的概念边界还可更严谨**
- 关键词：能力接入、协议层、workflow、行为约束
- 练习方向：准备一版更标准的定义，避免把它们简单说成两个插件

**趋势题可以减少口号，多讲方法论**
- 关键词：职责重构、可替代工作、不可替代工作、人机协同
- 练习方向：把“AI 不会完全取代人”展开成更有层次的三段论表达

## 总结

这场面试的强项非常明显：你不是泛泛而谈 AI，而是真的在工程里长期使用 AI，并且已经开始主动设计 workflow、思考测试先行、上下文治理、skill 解耦、模型分工这些更深入的问题。这一点在同类候选人里是有辨识度的。

真正需要补的，不是“会不会用 AI”，而是把你的实践经验进一步抽象成更稳定、更工程化、更可面试表达的方法论。尤其是三点：第一，把最终产出和验收标准先定义清楚；第二，把 feedback 闭环建立在客观信号上；第三，把你的系统背景和 AI Infra 岗位的契合度讲得更稳。只要这三点补齐，你这类面试的说服力会再上一个台阶。
