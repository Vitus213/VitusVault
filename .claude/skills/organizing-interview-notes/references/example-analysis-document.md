### 3. 什么是死锁，怎么避免

**问题**：说一下什么是死锁，怎么去避免？

**我的回答原文**：死锁就是两个对象需要对同一个资源进行操作。比如事务A和事务B同时需要对C和D做操作，一个先C再D，一个先D再C，两个事务都是抢占式调度，A拿C时需要D，B拿D时需要C，就会产生死锁。避免方式：尽量串行化，不能长时间持有锁...

**不足**：死锁定义不够准确，应该强调多个线程/事务之间因相互等待资源而无法继续推进；回答避免方式时偏泛，没有给出工程里最常用、最落地的方案；没有提到死锁四个必要条件。

**回答关键词**：互斥、占有并等待、非抢占、环路等待、统一加锁顺序、超时、死锁检测

**参考回答**：
死锁是指多个线程、事务或进程在竞争资源时，因为彼此都持有一部分资源、同时又等待对方释放资源，最终形成循环等待，导致所有参与方都无法继续执行。

从理论上讲，死锁发生需要同时满足四个必要条件：
1. 互斥：资源同一时刻只能被一个执行单元占有。
2. 占有并等待：已经拿到部分资源后，还在等待其他资源。
3. 非抢占：资源不能被强行夺走，只能主动释放。
4. 环路等待：多个执行单元之间形成资源等待环。

避免死锁的思路，本质上就是破坏其中任意一个条件。工程上最常见的是：
- **统一加锁顺序**：比如都按资源ID从小到大加锁，这样不会形成环路等待。
- **控制持锁时间**：拿到锁后尽快完成逻辑，避免长事务。
- **超时与重试**：获取锁失败时超时返回，再由上层决定重试。
- **死锁检测**：数据库这类系统会维护等待图，检测到环之后主动回滚其中一个事务。

如果在业务系统里让我选一个最实用的方案，我会优先说统一加锁顺序，因为这是最简单、最稳定、最容易推广的做法。

### 4. 转账死锁问题（重点短板）

**问题**：支付系统里有一个经典问题。比如类似支付宝的钱包，A和B互相转账，A给B转1块（先扣A再加B），B给A转2块（先扣B再加A）。如果同时发起，A先锁自己账户再去锁B，B先锁自己账户再去锁A，就死锁了。怎么避免？

**我的回答原文**：通过时间戳，按先发起交易的人先保护...（被否）把加钱和扣钱分成两个操作...（被否）

**不足**：思路偏离题目本质。时间戳方案没有真正解决资源获取顺序不一致的问题；把加钱和扣钱拆成两个操作会破坏转账的原子性，业务上不可接受；没有抓住“统一加锁顺序”这个核心点。

**回答关键词**：按ID排序加锁、统一加锁顺序、原子性、环路等待、分布式锁

**参考回答**：
这个问题的本质是：两个并发转账请求对同一组资源加锁时，顺序不一致，从而形成环路等待。所以最直接、最标准的解法就是**统一加锁顺序**。

具体做法是：无论A给B转，还是B给A转，都不按照“付款方在前、收款方在后”来加锁，而是按照账户ID排序。比如总是先锁ID较小的账户，再锁ID较大的账户。这样所有涉及同一对账户的转账操作，加锁顺序都一致，自然就不会形成死锁。

如果进一步展开，可以这样说：
1. 收到转账请求后，先拿到fromAccountId和toAccountId。
2. 比较两个账户ID大小。
3. 先锁较小ID对应的账户，再锁较大ID对应的账户。
4. 在同一个事务里完成扣款、加款、写流水。
5. 提交事务后统一释放锁。

这样做的优点是：
- 简单直接，容易实现；
- 从根源上破坏了环路等待条件；
- 不影响转账操作的原子性。

如果面试官追问分布式场景，可以补充：如果账户数据分布在不同节点上，也要保持全局一致的资源排序规则，配合分布式锁或事务协调机制，保证所有请求都按同一顺序获取资源。

### 5. Linux常见进程状态

**问题**：Linux常见的进程状态有哪些？

**我的回答原文**：就绪、阻塞和等待。就绪是准备执行，分配CPU时间片后开始运行；碰到IO读取时CPU软中断变成阻塞状态；阻塞完成后数据准备好，回到就绪状态。

**不足**：状态名称不够准确，Linux内核里的状态需要用更规范的术语；漏掉了僵尸态、停止态；对运行态和就绪态的关系没有讲清楚。

**回答关键词**：TASK_RUNNING、TASK_INTERRUPTIBLE、TASK_UNINTERRUPTIBLE、TASK_ZOMBIE、TASK_STOPPED

**参考回答**：
Linux里常见的进程状态可以从内核视角来讲：

- **TASK_RUNNING**：表示进程处于运行态或者可运行态。也就是说，要么正在CPU上执行，要么已经准备好，等待调度器分配CPU。
- **TASK_INTERRUPTIBLE**：可中断睡眠。进程在等待某个事件，比如IO完成，在这期间如果收到信号，可以被唤醒。
- **TASK_UNINTERRUPTIBLE**：不可中断睡眠。通常也是在等待某些内核事件，但此时一般不会响应普通信号，常见于一些关键内核态等待场景。
- **TASK_STOPPED**：停止态。比如进程收到SIGSTOP后会暂停执行。
- **TASK_ZOMBIE**：僵尸态。进程已经退出，但退出信息还没被父进程回收，所以PCB等少量信息仍然保留。

如果面试里想讲得更自然一些，可以补一句：从用户视角常说运行、就绪、阻塞，但在Linux内核里，运行和就绪通常都归到TASK_RUNNING这类状态中。

### 6. 键盘按键到显示的系统流程

**问题**：在Linux里按下一个键，到按键显示在屏幕上，大致有哪些操作？

**我的回答原文**：键盘控制器捕获字节流，因为是实时操作不像磁盘有page cache，直接通过总线往上发。总线触发中断，CPU实时捕获信息，然后交给对应的输出流输出。

**不足**：回答过于粗略，缺少输入子系统、驱动层、TTY层、终端模拟器、显示链路等关键中间层；“交给输出流输出”这个说法太模糊，难以体现系统理解深度。

**回答关键词**：键盘中断、扫描码、输入子系统、TTY层、行规程、终端模拟器、帧缓冲/显示系统

**参考回答**：
这个过程可以按“硬件输入 → 内核处理 → 用户态显示”三层来理解。

第一步，**按键触发硬件中断**。用户按下键盘后，键盘控制器会产生对应的扫描码，并通过中断通知CPU。

第二步，**键盘驱动读取扫描码**。CPU响应中断后，内核中的键盘驱动会把扫描码读出来，并交给Linux输入子系统处理。

第三步，**输入子系统进行按键解析**。输入子系统会把底层扫描码转换成更高层的按键信息，比如某个键被按下、释放，是否带有Ctrl、Shift等修饰键。

第四步，**TTY层和行规程处理**。如果当前是在终端环境下，按键信息会进入TTY子系统。TTY的行规程会决定如何处理输入，比如回显、退格、换行，或者是否立即把字符交给前台进程。

第五步，**用户态程序接收输入**。比如shell或终端前台程序从标准输入读取字符，然后决定如何处理。如果只是普通输入，终端一般会把字符回显出来；如果是某些控制字符，可能触发特定行为。

第六步，**终端模拟器完成显示**。在图形界面中，终端模拟器会把字符渲染成字形，交给图形栈和显示系统，再通过显卡输出到屏幕上；在更底层场景下，也可以理解成写入帧缓冲，最终由显卡刷新显示。

如果想答得更像系统方向候选人，可以补一句：整个链路里，输入和显示其实是两条链路，中间是TTY或应用程序把它们连接起来。

### 7. TCP慢启动 & 拥塞控制

**问题**：什么是TCP的慢启动？细说一下拥塞控制。

**我的回答原文**：TCP慢启动主要体现在拥塞控制中，为了判断接收窗口大小，防止一次性发送过多包。从零开始，每收到一个ACK表明对方有能力接收，就增长cwnd。每过一个轮次以2的倍数增长...（后续详细讲了拥塞避免、快速恢复）

**不足**：整体基础不错，但有一个表述容易混淆：慢启动主要是为了探测网络拥塞能力，对应的是拥塞窗口cwnd，不是接收窗口；如果把接收窗口和拥塞窗口混在一起，容易丢分。

**回答关键词**：cwnd、ssthresh、慢启动、拥塞避免、快速重传、快速恢复、AIMD

**参考回答**：
TCP拥塞控制的核心目标，是避免发送方一下子向网络中注入过多数据，导致链路拥塞、丢包加剧、吞吐下降。它主要依赖拥塞窗口cwnd来控制发送速率。

**慢启动**阶段：
连接刚建立时，发送方并不知道当前网络的承载能力，所以不会一开始就发很多数据，而是从较小的cwnd开始。每收到一个ACK，cwnd就增加，近似呈指数增长。这样做的目的是快速探测当前网络还能承受多少流量。

当cwnd增长到慢启动阈值ssthresh后，就进入**拥塞避免**阶段：
cwnd不再指数增长，而是线性增长，通常表现为每经过一个RTT增加大约1个MSS。这是典型的加性增大，目的是更平滑地探测网络剩余容量。

如果发生丢包，TCP会认为网络可能已经拥塞。处理方式分两种：
- 如果是**超时重传**，说明拥塞可能比较严重，通常会把ssthresh设为当前窗口的一半，并把cwnd重置到较小值，重新进入慢启动。
- 如果是收到**三个重复ACK**，说明有报文段丢失，但网络不一定非常拥堵，于是触发**快速重传**，立即重传丢失报文，而不用等超时；随后进入**快速恢复**，把ssthresh调整为当前窗口的一半，cwnd也做相应收缩，再继续进入拥塞避免。

整体上，TCP拥塞控制可以概括为：
- 慢启动：指数增长；
- 拥塞避免：线性增长；
- 检测到拥塞后：乘性减小。

这就是经典的AIMD，也就是加性增大、乘性减小。

### 8. HTTP/HTTPS & TLS

**问题**：HTTP和HTTPS的区别？TLS加密的细节说一下。

**我的回答原文**：主要区别是有没有TLS加密。HTTP是明文请求，HTTPS有TLS加密。TLS握手主要分RSA和ECDHE，RSA缺少前向安全性...（后续详细讲了握手流程）

**不足**：整体基础不错，但如果想拿高分，除了“有没有加密”，还要讲清楚认证、完整性保护、证书校验，以及为什么ECDHE更常见。

**回答关键词**：明文传输、加密、身份认证、完整性校验、证书、RSA、ECDHE、前向安全性

**参考回答**：
HTTP和HTTPS最核心的区别，不只是“有没有加密”，而是HTTPS在HTTP和TCP之间增加了一层TLS，主要解决三类问题：
1. **机密性**：数据传输过程中被加密，避免明文泄露；
2. **完整性**：通过消息认证机制防止数据被篡改；
3. **身份认证**：通过数字证书确认服务端身份，避免中间人伪装。

HTTP本身是明文协议，如果链路被监听，用户请求内容、Cookie、Token都可能被直接看到。HTTPS通过TLS保护这条链路。

TLS握手大致流程可以这样讲：
1. 客户端发起连接，请求支持的TLS版本、加密套件、随机数等信息；
2. 服务端返回证书、公钥、选择的加密套件以及服务端随机数；
3. 客户端验证证书是否合法，包括是否由受信任CA签发、域名是否匹配、是否过期；
4. 双方协商出会话密钥；
5. 后续应用数据使用对称加密传输，因为对称加密效率更高。

RSA和ECDHE的区别在于密钥协商方式：
- **RSA**：客户端生成预主密钥，用服务端公钥加密后发给服务端。它实现简单，但如果服务端私钥泄露，历史会话有被解密风险，不具备前向安全性。
- **ECDHE**：双方通过椭圆曲线Diffie-Hellman临时交换参数，各自生成共享密钥。即使以后服务端私钥泄露，也无法反推出过去的会话密钥，所以具备前向安全性。

因此现代TLS更常见的是ECDHE方案。

### 9. 数据包从应用层到网卡

**问题**：一个数据包从应用层产生到网卡发出的全部过程。

**我的回答原文**：应用层产生数据 → 传输层封装TCP/UDP头部 → 网络层封装IP头部，根据MTU分片 → 链路层打MAC地址 → 通过路由器交换机找到目标

**不足**：回答主干是对的，但还不够完整；缺少socket到内核协议栈的过程、ARP解析、路由查找、网卡驱动、DMA等细节；“通过路由器交换机找到目标”属于发出后的网络转发过程，不是“到网卡发出”为止的重点。

**回答关键词**：socket、TCP/UDP、IP、路由查找、ARP、MAC、网卡驱动、DMA、MTU

**参考回答**：
这个过程可以按“应用层写数据 → 内核协议栈封装 → 网卡发送”来讲。

第一步，应用程序通过socket接口调用send/sendto/write之类的方法，把数据从用户态交给内核。

第二步，传输层处理。如果是TCP，内核会根据连接状态、发送窗口、拥塞窗口等决定当前能发多少数据，并给数据加上TCP头；如果是UDP，就直接加UDP头。

第三步，网络层处理。内核给报文加上IP头，确定源IP和目标IP，并根据路由表决定从哪个网卡发出、下一跳是谁。如果报文大小超过MTU，IP层可能还会涉及分片问题。

第四步，链路层处理。在真正发到二层网络前，需要知道下一跳设备的MAC地址。如果ARP缓存里没有，就要先发ARP请求，拿到目标MAC。然后链路层封装以太网帧，加上源MAC、目的MAC以及帧尾校验等信息。

第五步，进入网卡驱动。封装好的数据会交给网卡驱动，驱动把发送描述符、数据缓冲区等信息写给网卡。

第六步，网卡通过DMA从内存中把数据取走，发送到物理介质上，比如网线或光纤。

如果面试官继续追问，可以再补：发送完成后网卡通常会通过中断或轮询机制通知内核发送结果，这样发送路径就闭环了。

### 10. 三数之和

**问题**：三数之和：给定一个整数数组nums，判断是否存在三元组[i,j,k]满足i≠j≠k且nums[i]+nums[j]+nums[k]=0，返回所有和为0且不重复的三元组。

**我的回答原文**：先排序，遍历k从0到n-1，每次用双指针i在k+1、j在末尾...（实现时调试较久）

**不足**：思路本身正确，但编码时调试时间过长；重复元素跳过逻辑不够熟练，边界处理容易写错；面试里不仅要会做，还要在限定时间内稳定写对。

**回答关键词**：排序、双指针、去重、O(n²)、边界处理

**参考回答**：
这题的标准做法是**排序 + 枚举一个数 + 双指针找另外两个数**。

思路如下：
1. 先对数组排序。
2. 固定第一个数nums[k]。
3. 在k右边用两个指针i和j分别从左右向中间逼近。
4. 如果nums[k] + nums[i] + nums[j] < 0，说明和太小，i右移；
5. 如果和 > 0，说明和太大，j左移；
6. 如果和 = 0，记录答案，然后同时移动i和j，并跳过重复元素。

去重是这题的关键：
- 枚举k时，如果nums[k] == nums[k-1]，直接跳过；
- 找到一个解后，i要跳过和当前相同的值，j也要跳过和当前相同的值。

时间复杂度是O(n²)，因为排序是O(n log n)，外层枚举加内层双指针是O(n²)，整体由O(n²)主导；空间复杂度如果不算结果集，一般是O(1)。

参考代码：
```python
def threeSum(nums):
    nums.sort()
    res = []
    n = len(nums)

    for k in range(n - 2):
        if k > 0 and nums[k] == nums[k - 1]:
            continue

        i, j = k + 1, n - 1
        while i < j:
            s = nums[k] + nums[i] + nums[j]
            if s < 0:
                i += 1
            elif s > 0:
                j -= 1
            else:
                res.append([nums[k], nums[i], nums[j]])
                i += 1
                j -= 1
                while i < j and nums[i] == nums[i - 1]:
                    i += 1
                while i < j and nums[j] == nums[j + 1]:
                    j -= 1

    return res
```

如果想答得更完整，可以补一句：这题的本质是把三数之和降成“固定一个数后的两数之和”问题。
