## AI Coding 工程实践经验

### 1.名词解释

* **agents.md**：官方介绍：[AGENTS.md](https://agents.md/) ；核心思想为作为一个不同AI厂商开发生态中的中立支持，即不同厂商的AI代理均可阅读的**项目合约**，其中描述了项目的概述、简洁语言表述的AI在进行本项目开发时所需遵循的操作规范、安全边界、测试说明等

* **spec.md**：简单来讲，一份实际的项目的说明文档，描述项目背景、用户需求等

* **plan.md**：一份工程层面的、针对需求实现的技术文档，回答了“怎么从技术上实现spec”，包含了技术栈说明、模块划分、数据结构等，

* **task.md**：将plan拆解为AI可以逐步执行的具体任务列表，是单次AI对话需要执行的任务

* **Prompt Caching**：现代AI API都支持的一个机制：如果请求的前缀和上一次一样，就命中缓存，提高速度降低成本

  ```
  固定层(系统提示) + 半固定层(agents.md) = 缓存前缀
  动态层(对话) = 每次变化的部分
  ```

  



### 2. 核心原则

* **（1）上下文预算管理**：AI Agent本身的工作流程为：”上下文收集--决策--行动--验证“ 的循环，而模型本身的上下文窗口是固定的，在不断对话的过程中，上下文在不断膨胀，一旦某一次超过了模型上下文窗口上限，就会开始信息丢失、工作质量下降、产生幻觉等，因此上下文本身需要被精细管理
* **（2）AI 行动结果的兜底验证**：有些时候，当AI在执行一些复杂任务时，AI本身通过对话框告诉我们的结果，并不一定代表他真的执行了，例如让他根据需求编写一段代码，他可能会通过对话告诉你他已经完成了高质量的代码编写云云，但AI自己本身其实并没有去执行代码、跑测试、对比预期结果等，因此需要一套人为可观测的验证兜底逻辑
* **（3）session不应该被当成一个“越来越懂项目的长期记忆体”**：当一次session过长时，意味着模型的上下文已经存在丢失、噪声污染的情况，在此情况下继续执行任务只会提高失败可能性；session应该被当成可随时销毁的无状态执行流，真正的状态应该由文件来做管理
* **（4）不同规模的需求应该有不同的流程**：当需求本身比较简单时，套用复杂流程会导致流程本身>需求，因此需要衡量需求的复杂程度来实际选择一次任务流的执行流程应该是怎样



### 3.具体细节

#### 上下文预算管理

要对上下文做比较精细的管理，首先需要知道一次对话中的上下文由哪些部分组成：

* 固定的、每次对话都会注入上下文窗口的、基本不会改动的内容：System Prompt、MCP工具定义、Skills description
* 每次对话都会注入上下文窗口的、可以由你自由修改的内容：AGENTS.md
* 按需加载的：各类文档如spec.md、plan.md等
* 每次注入且动态增长的：对话历史、文件读取与修改、工具执行结果等

搞清楚了上下文的具体条目，就该清楚到底怎么算账。在上面的各类条目中，大部分内容都是比较固定的无法做修改裁剪、或者形如按需加载的文档需要尽可能保证详细以保证工作效果的，但仍然有一部分是可以被操作的空间，比如MCP工具定义列表里，可以减少少用或不用的MCP工具，再比如AGENT.md

名词解释里已经提及过，agent.md是一份AI在执行工作时需要遵守的一份**项目合约**，所谓“合约”，更多指执行操作时的具体规范，而非详细说明（这是项目文档该做的事），在知道agent.md每次都会注入上下文的前提下，我们能够得出一个结论：agent.md应该越精简越好

举个例子，假设我们希望AI在编码时遵循一定的实现规范，我们并不需要在agent.md里粘贴一段几百行的示例代码（这会在每次都注入上下文），而只需要写“参考xxx的实现”，让AI自己去按需读取

一个好的agent.md必须遵循以下规范：

* 每一行说明都能对AI的行为有实际的影响
* 不能包含经常变化的信息，防止破坏Prompt Caching

举例来讲，一个是前文提及的想要让AI遵循某种编码实现规范，只需要告诉他“”参考xxx“即可而不是大段粘贴代码；再比如：”dao查询时where查询条件必须携带userID“ 与 ”dao查询时where查询条件携带userID，因为xxx“，这里前者更优，因为对于一份合约来讲，AI不需要知道原因，只需要知道约束

agents.md推荐结构：

```
# 项目名称

## 技术栈(一行一个,注意写版本号)
## 项目结构(目录 + 职责,行数不要太多)
## 编码规范(只写项目特有的,不写通用的)
## 构建和测试命令(可复制粘贴直接跑的)
## 不要做的事(反模式清单)
## 分层调用规则(Controller -> Service -> DAO)
```

描述尽量精简，减少行数

#### AI行动结果的兜底验证

AI是不能够自己去验证自己的，在对话框里告诉你的文本不一定是真实的，可能存在以下几种情况：

* AI说已完成，但是没有执行验证，也就是工作没有经过测试
* AI审查自己的代码倾向于认为没有bug
* 你问AI行不行，AI回答你”you‘re absolutely right！“

因此AI执行工作时需要一套人为可观测的兜底验证逻辑

**核心思想：把主观判断变为机器判断，消除AI的自由裁量空间**

逻辑是人为定义，但具体的验证流程还是AI做的，因此AI在执行这一套兜底逻辑时需要知道背景/目标、具体验证手段、最后输出人为可观测的结果

* 做什么算结束：可以在spec.md中定义Acceptance Criteria
* 怎么检查：执行测试命令
* 检查结束的证明：输出一份verify-report，包含每条执行结果和输出

基于不同场景的粒度，可以把验证逻辑分为两类：

* **Hook**--轻量级，用于不需要完整验收流程的微型改动。每次编辑后自动触发，做的是确定性检查：编译通不通过、规范符不符合，这些都有明确的是/否答案。

  好的 hook 和坏的 hook，区别只在于：**结果是机器给出的，还是 AI 自己判断的**

  ```
  # 好：命令跑完退出码决定结果，AI 没有解释空间
  after_edit:
    - "mvn compile -pl ${module} -am"
    - "mvn checkstyle:check -pl ${module}"
  
  # 坏：AI 自己来判断，等于没有约束
  after_edit:
    - "请检查是否有性能问题"
  ```

* **Verify.json**--重量级，面向功能，用于有明确验收标准的任务。它的关键不是那些描述字段，而是 `test_cmd`，一个可以直接执行的命令，AI 不需要判断"并发有没有问题"，只需要跑命令，看是不是 PASSED

  举例：

  ```
  {
      "id": "AC-1",
      "name": "用户注册接口返回201",
      "phase": "phase-1",
      "status": "passing",
      "acceptance": "POST /api/register 返回 HTTP 201，body 含 userId 字段",
      "test_cmd": "mvn test -Dtest=UserApiTest#testRegisterSuccess"
  }
  ```

  而这种验证规范之所以使用json而不是markdown来描述，一个原因是md本身还是属于自然语言，AI依赖自然语言解析就有可能出现误读的情况，而json格式结构严格，不存在解析歧义；还有一个原因是对于md格式的checklist来说，AI可能存在先“勾选”的情况，即使没有真正完成验证，而json的test_cmd字段明确要求先跑命令，通过了才修改status

#### session不应该被当成一个“越来越懂项目的长期记忆体”

AI Coding的重要指标是上下文的质量，因此在multi-agent结构中，上下文隔离是非常重要的，一个干净的、只包含必要信息的上下文，产出的代码质量一定远高于一个被历史废案、搜索结果等无关信息污染的上下文产出的结果，**隔离是multi-agent的核心价值**

因此在一个需求从定义开始到AI完成验收工作的整体流程中，session应该基于不同的阶段来去做不同的拆分，计划阶段--编码阶段--review阶段--verify阶段

值得一提的是至少对review阶段来说，其必须与编码阶段分离session，因为编码阶段的上下文已经被AI自己产出的结果填充了，我们不能指望一个已经存在相关记忆的AI去自我审查出他自己的bug，在这里做review必须要隔离上下文

#### 不同规模的需求应该有不同的流程

在前文提及过几个文件：spec.md  plan.md  tasks.md  verify.json  verify-report.md  这些东西设计的很完整，但是并不等同于高效，具体流程选择还是需要基于对需求的规模判断来决定

举个例子，一个只有两行代码变更的简单的bug-fix 如果也要走 specify--plan--build--review--verify 这些阶段写多个文件，那流程本身就比需求重得多，流程本身变成了负担，因此需要根据需求复杂度来决定规范强度，来做一个**渐进式规范**

一点参考方案：

* 对于一些比较简单的需求，比如只修改了一两个文件，且没有影响到项目架构，，直接让AI修改+验证即可，可以配合hook自动检查

* 对于一些需要修改几个文件，涉及单一模块的需求，可以走build+verify，结果使用verify.json来验证，但是不需要specify或plan，因为只是针对单一模块内的修改，需求和上下文大概并不复杂
* 对于跨模块或者架构变更的需求，那就走完整的阶段流程

值得一提的是，不同规范强度的判断不应该只是看文件修改范围，还应该看作出修改后的影响，比如一个需求修改只涉及了一两个文件，但是涉及了并发安全，那也应该看情况来“升档”；反之，如果一个需求涉及了多文件，但都只是简单的机械填充DAO操作与字段，那也不需要那么高的流程复杂度



### 4. “人”的定位

AI Coding不是简单的"你看着AI写，有错误指出来再修改"，这是一种低效的，需要反复来回交互的协作方式

在AI Coding的流程中，人应该负责：

* 做什么与不做什么
* 方案拍板（可以是自己决定，也可以让AI给方案，但最后必须由人来决定）
* 定义验收标准
* 查看验收

并且，基于AI的已知的缺陷，人在与AI协作的过程中也必须予以补齐：

* 对于你问AI行不行，AI只会回答你“you're absolutely right”的情况，人可以把提问方式改成“请你列出该方案的几个风险点”
* AI可能习惯于制造幻觉，例如给你一个根本不存在的API，人应该在给AI的参考文档里明确给出API对应的文档链接
* 过度工作：对于简单的功能实现，AI可能会用到复杂的设计模式，当确定项目不需要这么高的复杂度时，需要人在文档里明确指出AI应该遵守的东西
* ......

总结：模型能力有限，但可以超出大部分人类，人类基于AI Coding所能达到的上限，除了模型能力以外，还取决于人与AI的协作方式，AI能力越好，**人的判断力越重要**，AI做的事情是帮你把你计划的事情高效实现，而实现的效果取决于你所给出的上下文的质量（需求明晰程度、操作规范精确程度等），因此，AI Coding的能力越强，人月应该花时间在需求与架构规划上
