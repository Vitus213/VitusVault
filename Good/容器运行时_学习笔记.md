# 容器运行时学习笔记

> 基于博客《浅析容器运行时》（cnblogs 张明成），结合自己的理解整理。

---

## 1. 容器运行时是什么？

**核心观点：容器本质上是「被隔离和受限的进程」。**

- 隔离：依靠 **Linux Namespace**
  - `UTS`：主机名隔离
  - `PID`：进程 ID 空间隔离
  - `MNT`：挂载点 / 文件系统视图隔离
  - `NET`：网络设备 / IP / 端口隔离
  - `IPC`：进程间通信隔离
  - `USER`：用户和权限隔离
- 资源限制：依靠 **cgroups（control groups）**
  - 限制 CPU、内存等资源使用

容器和虚拟机的关键区别：

- 容器与宿主机 **共享同一个内核**，只是进程被隔离和限流；
- 虚拟机是完整的操作系统，包含自己的内核，通过虚拟化层与宿主机交互。

**容器运行时（runtime）= 用来运行和管理这些“容器进程 + 它们的文件系统 / 网络 / 资源”的工具。**

它负责：

- 拉取 / 管理镜像
- 准备容器的 rootfs（文件系统）
- 设置 namespace / cgroups 等
- 创建、启动、停止、删除容器进程

## 2. 容器运行时的分类：高层 vs 低层

文中把运行时分为两层：

### 2.1 低层运行时（low-level runtime）

特点：

- 直接和 **宿主机内核 / 系统调用** 打交道；
- 负责按照规范（例如 OCI）真正「起一个容器」；
- 关心的是“进程怎么跑起来、怎么隔离、怎么限制资源”。

典型实现：

- **runc**（最主流）
  - 基于 Linux Namespace + cgroups 实现
  - 接受标准命令：`create`、`start`、`kill`、`delete` ……
  - 是 Docker、containerd 默认使用的低层 runtime
- **runv**
  - 基于虚拟机 hypervisor 的运行时
  - 通过 guest kernel 提供隔离，边界清晰
  - Kata Containers / Firecracker 这类项目的底层思路
- **runsc**（gVisor）
  - runc + safety 的思路
  - 拦截应用程序的所有系统调用，在沙箱里实现 syscall，提供更高隔离度

### 2.2 高层运行时（high-level runtime）

特点：

- 负责「整体生命周期管理」和「整合镜像 / 网络 / 存储」；
- 上接编排系统（如 Kubernetes / Docker Daemon）；下接低层运行时（如 runc）。

典型实现：

- **containerd**
  - CNCF 托管项目
  - 提供：容器生命周期管理、镜像管理、存储 / 快照管理、网络集成等
  - 通过 gRPC API 暴露给上层（Docker、Kubelet 等）
- **CRI-O**
  - 针对 Kubernetes 的轻量级高层运行时
  - 实现 Kubernetes 的 CRI（Container Runtime Interface）
  - 底层一般也用 runc

**重要关系：**

- runc 是 Docker 和 containerd 的 **共同底层组件**：
  - Docker Engine 调用 containerd
  - containerd 再调用 runc 来真正起容器

## 3. 高层运行时与低层运行时怎么协作？

可以从一个典型容器的生命周期来看：

1. **镜像管理（高层）**
   - 高层运行时从镜像仓库（如 Docker Hub）拉取镜像。
   - 解压镜像层（layers），准备好可挂载的 rootfs（文件系统）。
   - 生成好元数据：镜像 ID、配置、文件系统位置等。

2. **容器配置（高层）**
   - 接收来自上层的配置信息：
     - 环境变量
     - 端口 / 网络配置
     - 挂载卷 / 存储
     - 资源限制（CPU / 内存）
   - 生成容器的运行时配置（通常符合 **OCI runtime spec**）。

3. **容器启动（低层）**
   - 高层把“镜像已经就绪 + 容器配置”交给低层运行时。
   - 低层运行时（runc 等）负责：
     - 设置 namespace（UTS / PID / NET / MNT / IPC / USER 等）
     - 设置 cgroups 限制资源
     - 挂载 rootfs
     - 在隔离环境中 `exec` 容器进程

4. **生命周期管理（高层 + 低层协作）**
   - 高层发出 “start / stop / delete” 等命令；
   - 低层执行具体操作，并把状态上报给高层；
   - 高层再反馈给更上层（比如 Docker CLI、Kubernetes）。

整体可以抽象为：

> 高层运行时：准备好“跑一个容器”所需的一切并管理容器对象；
>
> 低层运行时：在内核层面把这件事真正做出来，让那个进程在隔离环境里跑起来。

## 4. 典型实现：Docker 的分层架构

### 4.1 从「只有 Docker Daemon」到「containerd + runc」

早期 Docker 版本（1.11 之前），整个容器生命周期几乎都是 Docker Daemon 直接管理的。后面为了架构拆分和扩展性，引入了：

- 高层：**containerd**
- 中间垫片：**containerd-shim**
- 底层：**runc**

现在的分工大致是：

- **Docker Daemon**
  - 负责 CLI / API 层
  - 管理镜像、卷、网络等更上层的抽象
  - 对外提供 “docker run/ps/logs…” 这些用户体验
- **containerd**
  - Docker 的一个组件，同时又是独立项目
  - 负责具体的容器生命周期管理
  - 提供 gRPC 接口给 Docker Daemon / 其他上层（如 Kubelet）
- **containerd-shim**
  - 每个容器对应一个 shim 进程
  - 作用：
    - 作为容器进程的父进程，负责回收子进程、维持 fd（如 stdin/stdout）
    - 让容器不直接以 containerd 为父进程
    - 即使 containerd 挂了，容器也能继续跑（因为 shim 还在）
- **runc**
  - 纯粹、专注的低层 runtime
  - 读入 OCI runtime spec（config.json）和 rootfs
  - 按OCI规范执行 create/start/kill/delete
  - 启动完容器后自己退出，由 shim 管理容器进程

### 4.2 为什么要有 containerd-shim？

原因：

- 如果容器的父进程直接是 containerd：
  - containerd 挂掉 → 所有容器的父进程消失 → 行为不可控
- 引入 shim：
  - 每个容器拥有自己的“看护人”（shim）
  - shim 很轻量，专职管理容器进程的生命周期细节
  - containerd 只负责“控制平面”，可以崩溃 / 升级，而容器不受到直接影响

启动过程的时序图可以简化为：

```text
Docker CLI → Docker Daemon → containerd → containerd-shim → runc → 容器进程
```

其中：

- runc 启动完容器后就退出
- containerd-shim 作为容器进程的父进程常驻

### 4.3 Docker 与规范（OCI）的关系

- OCI（Open Container Initiative）定义了两大规范：
  - 对镜像的规范（Image spec）
  - 对运行时的规范（Runtime spec）
- runc 是 OCI Runtime Spec 的参考实现
  - Docker 把自己的 libcontainer 捐出来，改名为 runc
  - Kata、gVisor 等 runtime 也都兼容 OCI

这样一来：

- 高层实现（Docker、containerd、Kubernetes）
  - 只要按 OCI 定义的结构写好 `config.json` 和 rootfs
  - 就可以调用任意符合 OCI 的 runtime 来运行容器

## 5. 整体总结

1. **容器 = 特殊进程**
   - Namespace 负责“看起来像是独立系统”
   - cgroups 负责“资源不可随便乱占”

2. **容器运行时分层**
   - 低层 runtime（如 runc）：
     - 直接操作 namespace / cgroups / rootfs
     - 按 OCI runtime spec 真正启动容器进程
   - 高层 runtime（如 containerd、CRI-O）：
     - 管理容器的生命周期、镜像、网络、存储
     - 向上暴露 API 给 Docker/Kubelet 等

3. **Docker 的实现方式**
   - Docker Engine 不是直接“自己干到底”，而是：
     - CLI & API → Docker Daemon
     - 控制平面和生命周期管理 → containerd
     - 每容器一个看护进程 → containerd-shim
     - 真正创建容器 → runc （或其他 OCI runtime）

4. **设计上的好处**
   - 模块化：
     - 低层 runtime 可替换（runc / Kata / gVisor 等）
     - 高层 runtime 可交给 Kubernetes / Docker / CRI-O 等组合
   - 稳定性：
     - shim 的存在让 containerd 可以重启，容器不必跟着死
   - 标准化：
     - 通过 OCI 规范，行业内的容器生态可以互操作

这篇文章本身偏概念和架构，适合作为：

- 入门时理解「容器运行时」到底是什么
- 搭配更细粒度源码阅读（比如 `containerd` / `runc` / `faasd-in-rust` 项目）来理解“这段代码对应哪一层、在干什么”。
